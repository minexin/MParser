# MParser v0.12 Scope

MParser v0.12 adds executable bytecode region contracts. Optimization
candidates now carry concrete instruction boundaries, data-flow summaries,
side-effect classifications, and an explicit typed-execution eligibility
decision.

## Added Since v0.11

- New `BytecodeRegionAnalyzer` and `BytecodeRegionContract`.
- Half-open bytecode ranges for each optimization candidate.
- Separate loop-body boundaries for closed `for` regions.
- Stack input/output counts at the region boundary.
- Region read, external input, write, and observable output name sets.
- Region call-target collection.
- Conservative classifications for calls/dynamic indexing, indexed or member
  mutation, unsupported control flow, and unsupported operations.
- Closed scalar loop eligibility for numeric load/store, unary, binary, and
  scalar postfix operations.
- Exact-PC contracts for call and assignment candidates; these remain
  ineligible until expression slicing can make them closed stack regions.
- Typed IR `region-contract` and `reject-region` operations.
- Guard decisions now require both successful guards and an eligible region.
- CLI plan, typed IR, and guard-check output now expose region contracts.
- New pure scalar loop sample plus dedicated region smoke coverage.
- Project version and CLI version bumped to `0.12.0`.

## Why This Matters

Before v0.12, a stable scalar guard could say that a loop looked suitable for
specialization, but there was no proof that the corresponding instruction
range was complete or safe to replace. v0.12 makes that boundary explicit:

```text
profile candidate
  -> locate bytecode region
  -> summarize reads/writes/calls/control flow
  -> require closed stack boundary
  -> combine region eligibility with runtime guards
  -> enter typed path or fall back
```

Guard success alone is no longer enough. A loop containing `kernel(i)`,
dynamic indexing, mutation, nested control flow, or an unsupported operation is
rejected even when all observed values are scalar numbers.

## Eligible Example

```powershell
build\mparser.exe --plan-bytecode samples\typed_region_demo.m
build\mparser.exe --typed-ir-bytecode samples\typed_region_demo.m
build\mparser.exe --check-typed-ir-bytecode samples\typed_region_demo.m
```

The hot loop reports a contract similar to:

```text
region pc=[7,15), body=[8,14), closed=yes, typedEligible=yes, stack=1->0
inputs=[y], outputs=[i, y], writes=[i, y], calls=[]
regionReason=eligible closed scalar loop region
```

The guard check must report:

```text
regionEligible=yes, enterTypedPath=yes
```

The existing call-heavy profiling sample demonstrates rejection:

```powershell
build\mparser.exe --check-typed-ir-bytecode `
  samples\bytecode_profile_demo.m
```

Its `i` loop reports `regionEligible=no` because the region contains a call.

## Current Pipeline

```text
HIR
  -> bytecode
  -> bytecode VM profile
  -> optimization candidates
  -> bytecode region contracts
  -> typed IR
  -> region eligibility + runtime guards
  -> typed path or bytecode fallback
```

The typed path is still descriptive; v0.12 identifies regions that may be
executed but does not replace VM instructions yet.

## Remaining Before v1.0

- Execute eligible scalar loop bodies through a typed region interpreter.
- Integrate that executor into VM dispatch and skip replaced bytecode ranges.
- Preserve VM fallback when entry guards or typed execution fail.
- Capture entry-time values instead of relying only on final runtime variables.
- Slice closed call and assignment expressions.
- Add profile-off execution after a region is specialized.
- Expand MATLAB runtime coverage for objects, cells, structs, complex values,
  sparse arrays, dynamic dispatch, and broader builtin behavior.

## Next Iteration

The next milestone should execute the first eligible contract:

- Build a scalar stack executor for the closed loop body.
- Accept a numeric range and scalar variable frame at region entry.
- Commit all region outputs only after successful execution.
- Return an explicit fallback result without partial writes on failure.
- Compare typed-region output against normal bytecode execution in tests and
  benchmarks.
