# MParser v0.17 Scope

MParser v0.17 makes adaptive tiering self-correcting. Typed-region fallbacks
are tracked across invocations, stale modules can be invalidated, and failed
regions must pass a conservative retraining proof before installation is
allowed again.

## Added Since v0.16

- Configurable consecutive fallback invalidation threshold.
- Per-region fallback streak tracking keyed by source bytecode PC.
- Successful typed execution resets the corresponding fallback streak.
- Atomic whole-module invalidation after a region reaches the threshold.
- Automatic return to the full profiling tier after invalidation.
- Stale cumulative profile removal at the invalidation boundary.
- Region-level retraining state retained after the module is removed.
- Retraining proof for every external region input.
- Required stable `number` kind with `1x1` shape before a failed region can be
  reinstalled.
- Conservative rejection when an input is vector/matrix/string/mixed or has no
  assignment observation.
- Duplicate retraining-rejection event suppression.
- Deterministic event history for promotion, typed execution, typed fallback,
  invalidation, and retraining rejection.
- Per-invocation promotion/invalidation flags and lifetime counters.
- CLI option `--adaptive-fallback-limit=N`.
- CLI event-history report.
- Tests covering successful execution events, repeated fallback, invalidation,
  profile reset, resumed profiling, retraining rejection, and session reset.
- Project version and CLI version bumped to `0.17.0`.

## Invalidation Model

```text
typed invocation
  -> region executes: reset its fallback streak
  -> region falls back: increment its fallback streak
       -> below threshold: keep installed module
       -> threshold reached:
            record invalidation event
            remove complete module atomically
            clear stale cumulative profile
            mark failed source for retraining
            resume full profiling next invocation
```

The invocation that triggers invalidation still completes through the normal
transactional fallback path. Module removal affects only later invocations.

## Retraining Proof

After invalidation, heat alone is insufficient to reinstall the failed source.
For every `BytecodeRegionContract::inputs` entry, the new cumulative profile
must contain assignment observations that are all:

- present;
- stable;
- kind `number`;
- shape `1x1`.

If any input fails, the candidate region is marked ineligible for that planning
cycle and the session remains in the profiling tier. Other independently
executable regions may still be installed.

## CLI Demonstration

```powershell
build\mparser.exe --run-adaptive-bytecode --adaptive-runs=4 `
  --adaptive-hot-loop=10 --adaptive-fallback-limit=2 `
  samples\typed_region_fallback_demo.m
```

Expected transition:

```text
invocation=1, tier=profiling, promoted=yes, invalidated=no
invocation=2, tier=typed, typedFallbacks=1, invalidated=no
invocation=3, tier=typed, typedFallbacks=1, invalidated=yes,
  installedRegions=0, invalidations=1
invocation=4, tier=profiling, promoted=no, invalidations=1
```

Expected event order:

```text
promotion
typed-fallback
typed-fallback
invalidation
retraining-rejected
```

The final vector result remains correct because both typed failures resume the
unchanged baseline bytecode loop.

## Stable Typed Workload

```powershell
build\mparser.exe --run-adaptive-bytecode --adaptive-runs=5 `
  --adaptive-hot-loop=10 --adaptive-fallback-limit=2 `
  samples\adaptive_tiering_demo.m
```

After promotion, every later invocation emits `typed-execution`; no
invalidation occurs and the VM remains profile-off.

## Current Limitations

- Invalidation removes the complete typed module, not only one native region.
- Retraining evidence currently comes from assignment profiles. Function
  parameters and external workspace values do not yet have dedicated entry
  observations.
- The CLI repeats a fresh program invocation with no mutable external inputs.
- Retraining happens synchronously at invocation boundaries.
- There is no background compilation, code cache, cooldown, or OSR.
- The typed executor is portable scalar C++, not native machine code.
- Only closed scalar `for` loops are executable typed regions.

## Remaining Before v1.0

- Add explicit entry/workspace value observations.
- Support parameterized repeated function calls and persistent workspaces.
- Reinstall a replacement specialization when external values stabilize.
- Add per-region module replacement instead of whole-module invalidation.
- Add native LLVM ORC compilation on Windows and ARM Linux.
- Define native frame maps, deoptimization state, and bytecode resume PCs.
- Extend optimized regions to conditionals, calls, indexing, and arrays.
- Expand MATLAB classes, objects, containers, and numeric compatibility.

## Next Iteration

The next milestone should make repeated execution accept changing external
state:

- Add an explicit initial workspace to VM runs.
- Preserve workspace values across adaptive invocations when requested.
- Profile region inputs at entry, not only through assignments.
- Demonstrate invalidation followed by successful retraining and re-promotion.
- Keep script/function scope boundaries explicit and deterministic.
