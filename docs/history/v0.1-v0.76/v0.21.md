# MParser v0.21 Scope

MParser v0.21 adds a module-level adaptive runtime with independent state per
named entry function. Multiple functions can now warm, promote, execute typed
regions, fall back, invalidate, retrain, and re-promote without disturbing one
another.

## Added Since v0.20

- `AdaptiveModuleRuntime` over one reusable `CompiledModule`.
- Lazy adaptive-session creation keyed by named entry function.
- Independent argument vectors and optional persistent workspaces per function.
- Independent cumulative profiles, typed modules, fallback counters,
  invalidations, retraining evidence, and event histories.
- `AdaptiveModuleFunctionState` summaries for installed tier, invocations,
  promotions, typed executions, typed fallbacks, invalidations, and events.
- Function-state lookup and ordered module-wide state snapshots.
- Targeted `resetFunction()` and complete `resetAll()` APIs.
- Validation failures that do not create partial function state.
- `--run-module-runtime` CLI mode.
- Repeatable `--module-call=name[:value...]` call sequences with scalar, string,
  and row-vector runtime literals.
- Per-call execution-tier output and final per-function tier summaries.
- `samples/adaptive_module_runtime_demo.m` with independently hot `hot_a` and
  `hot_b` entries.
- A thirteenth CTest target proving alternating promotion, isolated
  invalidation, unaffected typed execution, independent retraining and
  re-promotion, validation, and targeted reset.
- Project and CLI version bumped to `0.21.0`.

## State Partition

```text
CompiledModule (immutable source + HIR + bytecode)
  |
  +-- AdaptiveModuleRuntime
        +-- hot_a session
        |     profile -> typed module -> fallback/invalidation -> retraining
        +-- hot_b session
              profile -> typed module -> steady typed execution
```

An entry function's invalidation erases only its own installed typed module and
accumulated observations. Other sessions continue from their current tier.

## Alternating Promotion

```powershell
build\mparser.exe --run-module-runtime --adaptive-hot-loop=10 `
  --adaptive-fallback-limit=2 --module-call=hot_a:2 `
  --module-call=hot_b:3 --module-call=hot_a:2 `
  --module-call=hot_b:3 --module-call=hot_a:2 `
  --module-call=hot_b:3 samples\adaptive_module_runtime_demo.m
```

Expected final state:

```text
hot_a: invocations=3, installedTier=typed, promotions=1,
  typedExecutions=1, typedFallbacks=0, invalidations=0
hot_b: invocations=3, installedTier=typed, promotions=1,
  typedExecutions=1, typedFallbacks=0, invalidations=0
```

## Isolated Invalidation

After warming both functions, invoke `hot_a` twice with `[1,2]` and then invoke
`hot_b` again:

```powershell
build\mparser.exe --run-module-runtime --adaptive-hot-loop=10 `
  --adaptive-fallback-limit=2 --module-call=hot_a:2 `
  --module-call=hot_a:2 --module-call=hot_a:2 `
  --module-call=hot_b:3 --module-call=hot_b:3 `
  --module-call=hot_b:3 --module-call=hot_a:[1,2] `
  --module-call=hot_a:[1,2] --module-call=hot_b:3 `
  samples\adaptive_module_runtime_demo.m
```

The final state reports `hot_a` back in profiling with one invalidation while
`hot_b` remains typed and records another successful typed execution.

## API Sketch

```cpp
auto module = mparser::CompiledModule::compile(source);
mparser::AdaptiveModuleRuntime runtime(
    module, mparser::AdaptiveModuleRuntimeOptions{10, 2});

auto a1 = runtime.invoke("hot_a", {scalarA});
auto b1 = runtime.invoke("hot_b", {scalarB});
auto a2 = runtime.invoke("hot_a", {scalarA});
auto b2 = runtime.invoke("hot_b", {scalarB});

auto aState = runtime.functionState("hot_a");
auto allStates = runtime.functionStates();
```

The compiled module must outlive the module runtime and all sessions it owns.

## Current Limitations

- The module runtime accepts named top-level same-file functions only.
- Calls execute synchronously; thread safety and concurrent function sessions
  are not defined yet.
- State is in memory only and cannot be serialized between processes.
- Each function owns one adaptive specialization lineage; polymorphic variants
  for multiple stable argument signatures are not cached simultaneously.
- Requested output counts, `nargout`, `nargin`, and `varargin` are not yet
  implemented.
- Typed execution remains portable scalar C++, not native machine code.

## Remaining Before v1.0

- Add requested output counts and MATLAB function introspection variables.
- Add polymorphic per-signature specialization caches with bounded eviction.
- Add a stable serialized bytecode/module cache with compatibility metadata.
- Add package/path lookup and method/constructor entry resolution.
- Add native LLVM ORC compilation on Windows and ARM Linux.
- Define native calling conventions, frame maps, deoptimization values, and
  resume PCs.
- Extend typed regions to calls, indexing, arrays, matrices, and conditionals.
- Expand MATLAB classes, objects, containers, and builtin coverage.

## Next Iteration

The next milestone should implement MATLAB's function call introspection and
requested-output contract:

- Carry requested output counts into top-level and local function frames.
- Implement `nargin` and `nargout` values for active calls.
- Add `varargin` and `varargout` cell-style argument/result handling.
- Allow callers to request zero, one, or multiple declared outputs.
- Preserve these semantics through ordinary, adaptive, and module runtimes.
