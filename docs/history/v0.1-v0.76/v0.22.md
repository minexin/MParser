# MParser v0.22 Scope

MParser v0.22 implements the first complete MATLAB-style function call
introspection contract. Callers select how many outputs they need, function
frames observe the actual input and requested output counts through `nargin`
and `nargout`, and every execution tier returns the same requested prefix.

## Added Since v0.21

- `BytecodeVmOptions::requestedOutputCount`.
- `BytecodeVmResult::requestedOutputCount`.
- Zero-output, partial-output, and default all-declared-output top-level calls.
- Pre-execution diagnostics when a caller requests more outputs than declared.
- Numeric `nargin` and `nargout` values initialized in entry-function frames.
- Local-call `nargout` derived from assignment target count.
- Local-call `nargin` derived from the actual positional argument vector.
- Shared public function-signature parsing in the HIR interpreter and VM.
- Matching interpreter local-call introspection and output-prefix semantics.
- Requested output propagation through profiled, profile-off, and typed VMs.
- Mutable requested output count in long-lived adaptive sessions.
- Requested output propagation through `CompiledModule` preflight/invocation.
- Per-call requested outputs in `AdaptiveModuleRuntime`.
- `--outputs=N` CLI option, including `--outputs=0`.
- Typed steady-state execution now inherits the complete selected entry,
  arguments, workspace, and output request from its baseline call.
- `samples/function_contract_demo.m`.
- A fourteenth CTest target covering top-level 0/1/2/all outputs, excessive
  requests, local `nargin`/`nargout`, adaptive request changes, typed execution,
  and module-runtime reuse.
- Project and CLI version bumped to `0.22.0`.

## Call Contract

```text
declared signature: function [a, b, c] = f(x, y)
actual arguments:   2              -> nargin  = 2
requested outputs:  0..3           -> nargout = requested count

execute complete function frame
return only [a, b, c][0:requested count]
```

Requesting four outputs from this signature produces a diagnostic before the
function body runs. Omitting the request preserves the existing API behavior
and returns all three declared outputs.

## CLI Example

```powershell
build\mparser.exe --run-bytecode `
  --entry-function=function_contract_demo --argument=2 --argument=4 `
  --outputs=2 samples\function_contract_demo.m
```

Expected public results:

```text
Function outputs (function_contract_demo):
  total = 20
  input_count = 2
```

The diagnostic variable snapshot also reports `nargin=2`, `nargout=2`, and
`output_count=2`, proving that the function body observed the caller's request.

## Local Calls

For a local call such as:

```matlab
single = probe(7);
[code, in_count, out_count] = probe(7);
```

the first invocation sees `nargin=1`, `nargout=1`; the second sees `nargin=1`,
`nargout=3`. The interpreter and bytecode VM derive these counts from the same
structured assignment and signature data.

## Adaptive Calls

An `AdaptiveBytecodeVmSession` can change its requested count between
invocations with `setRequestedOutputCount()`. Profiling, promotion, and typed
execution continue normally because output demand is call-frame state rather
than a reason to discard a loop specialization. `AdaptiveModuleRuntime::invoke`
accepts the count per call and preserves the function's independent tier state.

## Current Limitations

- `nargin` and `nargout` currently represent the active call only; querying
  another function's declared arity is not implemented.
- Function calls used purely as statements still lower through the existing
  single-result-and-discard path rather than true `nargout=0` local calls.
- `varargin` and `varargout` are not implemented. Correct support requires a
  heterogeneous Cell runtime, brace indexing, comma-separated list expansion,
  and variable result packing.
- Positional arguments remain fixed-arity.
- Class methods, constructors, packages, and path-resolved functions are not
  executable entry targets yet.
- Typed execution remains portable scalar C++, not native machine code.

## Remaining Before v1.0

- Add heterogeneous Cell values and executable brace indexing.
- Add comma-separated list expansion plus `varargin` and `varargout`.
- Lower statement calls with a true zero-output request.
- Add polymorphic per-signature specialization caches with bounded eviction.
- Add package/path lookup and method/constructor entry resolution.
- Add native LLVM ORC compilation on Windows and ARM Linux.
- Define native calling conventions, frame maps, deoptimization values, and
  resume PCs.
- Extend typed regions to calls, indexing, arrays, matrices, and conditionals.
- Expand MATLAB classes, objects, containers, and builtin coverage.

## Next Iteration

The next milestone should establish MATLAB Cell and variable-argument runtime
semantics as one coherent capability:

- Add recursive heterogeneous Cell values and shape metadata.
- Execute cell literals and one/two-dimensional brace indexing.
- Implement comma-separated list expansion at call and assignment boundaries.
- Bind excess inputs into `varargin` and pack excess outputs from `varargout`.
- Preserve Cells and variable arity through interpreter and bytecode frames.
