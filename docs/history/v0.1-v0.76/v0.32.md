# MParser v0.32 Scope

MParser v0.32 gives inherited properties stable declaring-class-local runtime
identity. A subclass can now define a property with the same surface name as a
private superclass property without merging their values, defaults,
validation, accessors, or mutations.

## Major Capability

- Every concrete property descriptor receives a stable
  `DeclaringClass::Property` storage key.
- Effective class property tables map a surface name to an ordered candidate
  set instead of flattening it to one descriptor.
- Repeated diamond paths to the same storage identity merge once.
- A subclass may add a same-name property only when every inherited candidate
  has both `GetAccess` and `SetAccess` set to effective private access.
- `Access = private`, separate private get/set attributes, and an empty or
  fully unresolved class access list all satisfy the effective-private rule.
- A property with only `SetAccess = private`, only `GetAccess = private`, or a
  nonempty class access list remains non-private for redeclaration purposes.
- A method defined by a superclass resolves its declaring class's property,
  while a subclass method resolves the subclass-local property.
- External member access selects the unique non-private candidate, preserving
  the visible subclass property while the private base slot stays hidden.
- Base and subclass constructors write their own same-name slots through the
  existing construction context.
- Explicit and implicit defaults, validation, constants, dependent get/set
  methods, and `AbortSet` operate on the selected descriptor.
- Value-object copies isolate every qualified slot; handle aliases share the
  complete qualified field map without collapsing same-name values.
- Multiple inherited properties with the same name are compatible when all or
  all but one are fully private. Two non-private candidates remain ambiguous.
- Project and CLI version are `0.32.0`; CTest now contains 24 targets.

## Layout Model

The old flattened layout could represent only one field named `Value`:

```text
Derived.properties["Value"] -> one descriptor
object.fields["Value"]      -> one value
```

v0.32 separates surface lookup from storage identity:

```text
Derived.properties["Value"]
  -> Base::Value       (private)
  -> Derived::Value    (public)

object.fields
  Base::Value          -> 2
  Derived::Value       -> 1
```

Runtime selection is lexical where MATLAB requires it:

```text
Base method       -> exact Base::Value candidate
Derived method    -> exact Derived::Value candidate
external access   -> unique non-private candidate
```

This also handles multiple inheritance. Private candidates from unrelated
bases remain independently addressable by methods declared in each base. One
additional non-private candidate can provide the externally visible property;
a second non-private candidate is diagnosed as ambiguous.

The behavior follows MATLAB's documented property modification and multiple
inheritance rules:

- <https://www.mathworks.com/help/matlab/matlab_oop/modify-superclass-properties.html>
- <https://www.mathworks.com/help/matlab/matlab_oop/subclassing-multiple-classes.html>
- <https://www.mathworks.com/help/matlab/matlab_oop/property-attributes.html>

## Example

```powershell
build\mparser.exe --run-bytecode samples\class_property_identity_demo.m
```

Expected values include:

```text
base_before = 6
visible_before = 7
base_after = 9
visible_after = 10
original_base = 6
original_visible = 7
handle_base = 11
handle_visible = 22
```

The value-class half proves that base and visible slots mutate independently
and that copying isolates both. The handle-class half proves that aliases share
both slots while base methods still select the private base value.

## Runtime Storage Contract

`RuntimeValue::fields` and `RuntimeValue::sharedFields` now store class object
fields by qualified descriptor identity rather than surface property name.
Embedding code should treat these maps as VM storage, not as a reflection API.
Public property access continues through bytecode member operations and keeps
using MATLAB surface names.

## Diagnostics Covered

- Redeclaring an inherited public or protected property.
- Redeclaring a property with only private set access.
- Redeclaring a property with a nonempty class access list.
- Inheriting two unrelated non-private properties with the same name.
- Existing missing, cyclic, and ambiguous class hierarchy diagnostics.
- Validation failure on a hidden base slot without mutating either slot.

## Current Limitations

- Class loading remains limited to definitions in one compiled source.
- Private methods still use the single effective method-name table. MATLAB
  permits unrelated private same-name methods to coexist, which needs the same
  declaring-class identity treatment now used for properties.
- Runtime metadata introspection and a public reflection view over qualified
  storage are not implemented.
- N-dimensional arrays, additional property validators, events, listeners,
  dynamic properties, object arrays, and handle lifecycle callbacks remain
  outside the executable class subset.
- The reference HIR interpreter and typed/JIT tiers do not execute class
  objects. Qualified property storage currently executes in the bytecode VM.
- Native machine-code JIT remains future work; current optimization tiers use
  portable typed-region execution and bytecode fallback.

## Next Iteration

- Give private methods declaring-class-local identity so unrelated private
  methods can coexist across subclassing and multiple inheritance.
- Preserve exact superclass-qualified dispatch for those private method
  candidates and keep public/protected ambiguity diagnostics unchanged.
- Continue toward persistent cross-file/package class loading and runtime
  metadata over the effective class graph.
- Continue multidimensional Cell and comma-separated-list semantics while
  preserving bytecode fallback for future native JIT tiers.
