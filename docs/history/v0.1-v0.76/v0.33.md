# MParser v0.33 Scope

MParser v0.33 gives private methods stable declaring-class-local runtime
identity. Same-name private methods can now coexist across subclassing and
multiple inheritance, and a call made by a class method selects that class's
private implementation without disabling normal dynamic dispatch for visible
methods.

## Major Capability

- Effective class metadata now separates the unique dynamically dispatched
  method table from declaring-class-qualified private method candidates.
- `Access = private` and the equivalent empty access list `Access = {}` create
  independent private identities.
- A named class access list remains an override contract. If all listed
  classes are unresolved, subclasses still cannot silently redefine the
  method as though it had been explicitly declared private.
- Private candidates are deduplicated by declaring class when a diamond
  hierarchy reaches the same definition through more than one path.
- An unqualified object call made inside a class method first checks for the
  private candidate declared by that class.
- If no lexical private candidate applies, public, protected, and class-list
  methods retain most-specific dynamic dispatch.
- Method references now carry the selected declaring class through the operand
  stack. Invocation executes that exact declaration instead of resolving the
  surface name a second time.
- The same identity rules cover instance and static private methods.
- Multiple unrelated private methods with the same name are compatible. One
  additional non-private method can provide the visible dispatch target, while
  two unrelated non-private definitions remain ambiguous.
- Private access is still enforced outside the defining class, and `Sealed`
  still rejects a same-name declaration in a subclass.
- Project and CLI version are `0.33.0`; CTest now contains 25 targets.

## Dispatch Model

The visible method map remains intentionally singular:

```text
Derived.methods["step"] -> Derived::step (public override)
```

Private methods use a candidate set:

```text
Derived.privateMethods["code"]
  -> Base::code       (private)
  -> Derived::code    (private)
```

Selection is context-sensitive without becoming name-ambiguous:

```text
Base method calling obj.code()       -> Base::code
Derived method calling obj.code()    -> Derived::code
external code calling obj.code()     -> access diagnostic
Base method calling obj.step()       -> Derived::step
```

The selected `DeclaringClass::Method` identity is retained in the stack method
reference, so the call boundary cannot accidentally switch to another
same-name candidate.

This behavior follows MATLAB's documented method-access and multiple
inheritance rules:

- <https://www.mathworks.com/help/matlab/matlab_oop/method-attributes.html>
- <https://www.mathworks.com/help/matlab/matlab_oop/selective-access-to-class-methods.html>
- <https://www.mathworks.com/help/matlab/matlab_oop/subclassing-multiple-classes.html>
- <https://www.mathworks.com/help/matlab/matlab_oop/modifying-superclass-methods-and-properties.html>

## Example

```powershell
build\mparser.exe --run-bytecode samples\class_method_identity_demo.m
```

Expected values include:

```text
base_code = 10
child_code = 20
dynamic_code = 2
left_code = 3
right_code = 4
```

The first two values prove lexical private selection across one inheritance
edge. `dynamic_code` proves that a public virtual call made by the base still
selects the child override. The final two values prove that unrelated private
methods survive multiple inheritance independently.

## Diagnostics Covered

- Calling a private method from outside its defining class.
- Inheriting two unrelated non-private methods with the same name.
- Redefining a sealed private method in a subclass.
- Overriding a method whose resolved named access list excludes the subclass.
- Overriding a named access-list method after every listed class fails to
  resolve.
- Existing exact-access override, abstract-method, hierarchy, and constructor
  diagnostics.

## Current Limitations

- Class loading remains limited to definitions in one compiled source.
- Methods in separate class files, `@class` folders, namespace/package lookup,
  and persistent cross-module class metadata are not implemented.
- Function-form method invocation and the broader MATLAB method-precedence
  rules remain outside the executable class subset; v0.33 covers bytecode
  member calls and class-qualified static calls.
- Runtime metadata introspection, events, listeners, dynamic properties,
  object arrays, and handle lifecycle callbacks are not implemented.
- The reference HIR interpreter and typed/JIT tiers do not execute class
  objects. Private method identity currently executes in the bytecode VM.
- Native machine-code JIT remains future work; current optimization tiers use
  portable typed-region execution and bytecode fallback.

## Next Iteration

- Introduce a persistent source/module loader so class definitions and methods
  can be resolved across files without flattening the existing class metadata.
- Preserve declaring-class property and method identities across that loader,
  including namespace-qualified class names and deterministic cache invalidation.
- Continue multidimensional Cell and comma-separated-list semantics while
  preserving bytecode fallback for future native JIT tiers.
