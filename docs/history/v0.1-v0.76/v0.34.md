# MParser v0.34 Scope

MParser v0.34 introduces a source graph and removes the single-file boundary
for the executable class subset. Scripts can construct a class defined beside
the entry file, inherit from another class found on a configured class path,
and preserve the declaring-class property and method identities established by
v0.32 and v0.33.

## Major Capability

- `SourceUnit` pairs source content with a stable display name, while every
  `SourcePosition` can retain the unit's source ID.
- `CompiledModule::compile(vector<SourceUnit>)` parses each source separately,
  preserves file-local line and column positions, merges top-level declarations
  for semantic analysis, and lowers one reusable bytecode program.
- Duplicate top-level class names are rejected before semantic analysis, with
  the diagnostic attached to the second declaration's file.
- `SourceLoader` begins with one entry file and recursively follows simple,
  statically visible class dependencies.
- Dependencies include constructor/static-style identifier calls, superclass
  lists, meta-class expressions and attribute lists, and property class
  constraints.
- Lookup checks the referring source directory first, then the entry directory,
  then repeatable class paths in their supplied order.
- A candidate `ClassName.m` is accepted only when it declares `ClassName` as a
  top-level class. Unreferenced files are not parsed into the compiled module.
- Cross-file inheritance reuses the existing constructor, access, property
  identity, private method identity, abstract/sealed, and dynamic dispatch
  metadata without a second class model.
- `--class-path=DIR` is repeatable and is honored by HIR, bytecode, execution,
  profiling, typed/adaptive, benchmark, and module CLI modes.
- `--tokens` and syntax-only output intentionally inspect only the requested
  entry file.
- `--module-info` lists the ordered source closure, byte counts, and file-aware
  top-level function locations.
- Compile and runtime diagnostics now print `file:line:column: message` whenever
  the originating source is known.
- Project and CLI version are `0.34.0`; CTest contains 28 tests.

## Source Graph Model

The loader and compiler have distinct responsibilities:

```text
entry path + class paths
  -> SourceLoader dependency closure
  -> ordered SourceUnit vector
  -> per-source lex/parse with sourceId
  -> merged compilation unit
  -> shared semantic class registry
  -> bytecode/runtime
```

The entry source is always source ID 0. Newly discovered classes are appended
in deterministic dependency-name and search-path order. The compiler does not
flatten source text, so a line number remains local to its original file and a
diagnostic does not need to reverse-map offsets from a synthetic concatenation.

## MATLAB Alignment

This milestone follows MATLAB's class-file convention that a class definition
is normally stored in a same-named `.m` file and found through folders on the
search path. The current implementation deliberately covers the simple class
file form first:

- <https://www.mathworks.com/help/matlab/matlab_oop/create-a-simple-class.html>
- <https://www.mathworks.com/help/matlab/matlab_oop/organizing-classes-in-folders.html>
- <https://www.mathworks.com/help/matlab/ref/classdef.html>
- <https://www.mathworks.com/help/matlab/matlab_oop/methods-in-separate-files.html>

## Example

The entry and derived class are in `samples/cross_file_classes`; the base class
is in its `lib` subdirectory:

```powershell
build\mparser.exe --run-bytecode `
  --class-path=samples\cross_file_classes\lib `
  samples\cross_file_classes\run_demo.m
```

Expected values include:

```text
base_code = 105
child_code = 207
dynamic_code = 2
```

`base_code` and `child_code` prove that same-name private properties and methods
retain their declaring-class identities across files. `dynamic_code` proves
that a visible call made in the loaded base class still dispatches to the
derived override.

Inspect the resolved source closure with:

```powershell
build\mparser.exe --module-info `
  --class-path=samples\cross_file_classes\lib `
  samples\cross_file_classes\run_demo.m
```

## Diagnostics Covered

- Parse diagnostics mapped to a non-entry source file.
- Duplicate top-level classes across two source units.
- Cross-file inheritance and superclass construction.
- Declaring-class-local private property and method selection across files.
- Visible dynamic method dispatch from a loaded base to a loaded child.
- Class-path discovery outside the entry directory.
- Ignoring a malformed but unreferenced `.m` file.
- CLI execution of a three-source class graph.

## Current Limitations

- Discovery currently accepts simple, unqualified class names only. MATLAB
  package folders (`+pkg`) and namespace-qualified names are not resolved.
- `@class` folders and method implementations in separate files are not loaded.
- Ordinary function files are not discovered; top-level/local function behavior
  remains within sources already in the class dependency closure.
- The first existing `ClassName.m` at the deterministic lookup location wins.
  A mismatched file is not bypassed in favor of a later path.
- MATLAB's full current-folder, project, package, private-folder, and toolbox
  path precedence is not modeled yet.
- The source graph is rebuilt per CLI invocation; persistent file metadata,
  timestamps, hashes, invalidation, and compiled-code caches remain future work.
- Native machine-code JIT remains future work. Current optimization uses
  portable typed-region execution with bytecode fallback.

## Next Iteration

- Add package-qualified names and `+package` folder resolution without losing
  deterministic source identity.
- Introduce persistent source metadata and dependency invalidation so repeated
  compiles can reuse unchanged frontend artifacts.
- Model separate method files and ordinary function-file lookup as explicit
  source graph node kinds rather than flattening them into module scope.
