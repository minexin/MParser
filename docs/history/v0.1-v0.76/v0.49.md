# MParser v0.49 Scope

MParser v0.49 turns the existing scalar typed-loop executor into a predecoded
register kernel. The milestone is driven by the original nested `1000 x 1000`
MATLAB script: reduce dispatch overhead substantially, preserve exact runtime
results and fallback behavior, and expose enough metrics to guide native JIT
work honestly.

## Milestone Contract

- Project and CLI version are `0.49.0`.
- Eligible closed scalar `for` loops compile stack bytecode into a portable
  register kernel before iteration begins.
- Variable names resolve to contiguous scalar slots and expression temporaries
  resolve to indexed registers.
- The final expression producer can write directly to a destination slot,
  removing a separate store operation.
- Supported arithmetic, comparisons, logical operations, scalar transpose,
  and ten pure unary math builtins retain the existing typed semantics.
- Entry guards remain double-scalar and failed guards leave VM state unchanged
  before baseline bytecode resumes.
- Empty ranges preserve the incoming workspace, including an existing loop
  variable.
- Profile-off typed execution no longer reconstructs one profile observation
  per loop iteration.
- Typed reports distinguish source bytecode instruction work from executed
  kernel instruction work.
- CTest contains 72 tests, including direct kernel, fallback, empty-range,
  operation-coverage, adaptive-tier, benchmark-metric, and CLI regressions.

## Predecoded Scalar Kernel

The typed-region contract still comes from bytecode profiling, planning, and
typed IR. v0.49 changes only the execution implementation behind that stable
boundary:

```text
bytecode region
  -> validate entry guards
  -> bind names to scalar slots
  -> lower stack expressions to indexed registers
  -> bind operations and pure calls to enum opcodes
  -> execute the compact kernel for every range value
  -> commit written slots
```

This removes repeated string comparisons, map lookups, dynamic stack traffic,
`RuntimeValue` construction, and bytecode decoding from the loop body. Kernel
preparation also recognizes a store whose source is the most recently produced
register and retargets that producer directly to the variable slot.

The kernel currently supports unary `+`, unary `-`, logical `~`, arithmetic
`+`, `-`, `*`, `.*`, `/`, `./`, `^`, and `.^`, all scalar comparisons,
logical `&`, `&&`, `|`, and `||`, and scalar postfix transpose. Statically
bound one-argument calls to `abs`, `acos`, `asin`, `atan`, `cos`, `exp`, `log`,
`sin`, `sqrt`, and `tan` are bound during kernel preparation.

Logical-producing operations retain the logical numeric class. Arithmetic and
math operations produce doubles, matching the previous typed executor. General
calls, indexing, mutation, nested control flow, and unsupported instructions
remain outside this kernel.

## Guard And Commit Boundary

The loop range must be a double scalar or numeric array, and every external
region input must be a double scalar. Kernel preparation and all entry checks
happen before the VM frame is modified. On rejection, the executor returns a
reason and the bytecode VM resumes at the original loop with its range still on
the stack.

Successful execution commits only slots written by a non-empty loop. An empty
range therefore does not create or overwrite the loop variable and does not
change body outputs. This behavior is covered by a direct executor regression.

## Profiling And Metrics

The previous typed path rebuilt loop-entry and backedge observations even when
`BytecodeVmProfilingMode::Disabled` was selected for steady execution. For a
million iterations that created a million unnecessary scalar runtime values.
v0.49 performs this reconstruction only while full profiling is enabled.

Every typed region now reports both:

- `typedInstructions`: source bytecode instructions represented by the typed
  execution;
- `kernelInstructions`: compact register-kernel instructions actually
  dispatched.

The benchmark statistics aggregate both metrics. This keeps optimization
claims auditable without restoring per-PC profiling overhead.

## Performance Baseline

`samples/timing_loop_demo.m` is the original benchmark:

```matlab
clear;
clc;
tic;
for j = 1:1000
    for i = 1:1000
        k = abs(i) + 9;
        m = sin(i);
        n = k * m;
    end
end
a = toc
```

Observed on the development machine in a Release build:

| Runtime | `a` from `toc` |
| --- | ---: |
| pre-v0.49 typed stack executor | about 1.51 s |
| v0.49 predecoded register kernel | about 0.068-0.079 s |
| MATLAB reference reported by the user | about 0.02 s |

The v0.49 path is roughly 19-22 times faster than the immediately preceding
typed executor, while remaining about 3.4-4.0 times slower than the reported
MATLAB result. Timings vary by machine and run. The deterministic final values
match baseline bytecode execution:

```text
i = 1000
j = 1000
k = 1009
m = 0.826879540532003
n = 834.32145639679
```

The inner region executes 1,000 times, covers 1,000,000 iterations, reports
14,000,000 source typed instructions, and dispatches 4,000,000 kernel
instructions with zero fallback. The outer loop is not specialized because its
body contains nested control flow.

`samples/timing_flat_loop_demo.m` provides the same million operations in one
flat loop so kernel behavior can be measured without the outer-loop boundary.
The `--run-typed-bytecode` command performs an initial profile/planning run and
baseline output comparison, so command wall time is longer than the displayed
`toc` value.

## Current Limitations

- This is a portable C++ register interpreter, not native machine-code JIT.
- Nested control flow prevents the enclosing outer loop from forming one typed
  region, although eligible inner loops still execute through the kernel.
- Kernel preparation occurs when a typed region is entered; persistent native
  code and cross-run code caches are future work.
- External typed inputs remain double scalars. Arrays, complex values, integer
  classes, dynamic calls, indexing, and mutation retain baseline fallback.
- Native LLVM ORC lowering and loop-midpoint on-stack replacement are not yet
  implemented.
- Moving-window operations deferred from v0.48 remain pending.

## Next Iteration

- Add an optional native LLVM ORC backend for the same typed-region contract,
  with portable fallback on Windows and ARM Linux.
- Evaluate nested-loop region formation so a complete loop nest can cross one
  optimized boundary instead of entering the inner region repeatedly.
- Preserve the same guards, transactional commit, output-equivalence checks,
  and source-versus-kernel metrics across native execution.
- Continue runtime coverage with moving-window operations and broader dynamic
  array semantics after the native execution boundary is stable.
