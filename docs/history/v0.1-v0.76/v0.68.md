# MParser v0.68 Scope

MParser v0.68 makes explicit MATLAB handle-object destruction executable as a
complete bytecode-runtime lifecycle. It connects destructor declarations,
inherited event metadata, alias validity, listener ownership, dynamic-property
cleanup, access control, diagnostics, samples, and cross-platform regression
coverage instead of treating `delete` as an isolated builtin.

## Major Capability

- Every resolved handle class inherits the public-listen/private-notify
  `handle.ObjectBeingDestroyed` event.
- `delete(object)` and `object.delete()` share one lifecycle implementation.
- All aliases become invalid before destruction callbacks run, and `isvalid`
  therefore returns false inside the event callback and every destructor.
- Lifecycle code may continue reading and writing the object while it is being
  destroyed; ordinary member access after the lifecycle is rejected.
- The most-derived valid destructor runs first, followed by superclass
  destructors in `classdef` declaration order. A diamond ancestor runs once.
- One failing listener or destructor records its diagnostic without preventing
  later callbacks, remaining destructors, or final cleanup.
- Repeated deletion of an invalid object is a no-op.
- A source-coupled listener is invalidated with its source. An explicitly
  retained uncoupled `listener(...)` remains valid, but its source is invalid.
- Dynamic-property descriptors and their property listeners are invalidated
  and their owner storage is removed.
- `events`, `methods`, `ismethod`, `metaclass`, and `?handle` expose the
  inherited destruction event and handle methods.

## Destructor Contract

A method is a class destructor only when all of these conditions hold:

- its name is `delete`
- it has an executable body
- it is not `Static`, `Abstract`, or `Sealed`
- it accepts exactly one ordinary object parameter
- it has no outputs, `varargin`, or `varargout`
- it has no input or output `arguments` block

A `delete` method that does not match this contract remains an ordinary method.
For example, `delete(object, code)` does not invalidate the object.

An access restriction on the most-derived destructor controls whether callers
may explicitly delete that class. A private destructor can still be reached by
an authorized method of its declaring class. Private destructors declared only
by superclasses do not prevent deleting a public subclass, but they still run
as part of its lifecycle.

## Lifecycle Order

For a valid scalar handle object, explicit deletion performs these steps:

1. Return immediately if the shared object state is already invalid.
2. Mark the shared state invalid for every alias.
3. Notify retained `ObjectBeingDestroyed` listeners with the source and an
   `event.EventData` whose `EventName` and `Source` identify the lifecycle.
4. Invoke every valid destructor, from the most-derived class through the
   resolved superclass graph in declaration order.
5. Remove dynamic-property values and descriptors.
6. Invalidate source-coupled and dynamic-property listeners.
7. Publish any deferred lifecycle diagnostics.

The event cannot be explicitly emitted through `notify`; its inherited
`NotifyAccess=private` policy reserves notification for the runtime lifecycle.

## Example

Run the checked-in production sample with:

```powershell
build\mparser.exe --run samples\handle_lifecycle_demo.m
```

Expected result:

```text
summary = 161
```

The sample checks event-before-destructor order, invalid state inside all
lifecycle callbacks, derived/base destructor execution, aliases, idempotence,
source-coupled and uncoupled listeners, dynamic-property cleanup, method-form
deletion, and metadata discovery.

## Validation

The dedicated `handle_lifecycle_smoke` executable covers:

- free- and method-form deletion
- most-derived, multiple-inheritance, and superclass destructor ordering
- public, private, and inherited-private destructor access
- invalid-object property and unbound instance-method rejection
- callback diagnostic isolation
- ordinary non-destructor methods named `delete`
- workspace replay of invalid aliases and listener/property descriptors
- inherited event and method metadata

The CLI test `handle_lifecycle_bytecode_cli_smoke` executes the complete sample.
Both tests are part of the Linux AArch64 portable QEMU selection in addition to
the complete Windows x64 and Linux x64 suites.

Configure and validate a native-JIT build:

```powershell
cmake -S . -B build -DMPARSER_ENABLE_NATIVE_JIT=ON
cmake --build build --parallel
ctest --test-dir build --output-on-failure
```

Then repeat with `MPARSER_ENABLE_NATIVE_JIT=OFF` to validate the portable-only
runtime. Handle lifecycle state contains no machine pointers or architecture-
specific representation and is independent of the SLJIT backend.

The Windows x64 Release validation for this milestone passed `117/117` tests
with native JIT enabled and `111/111` tests with it disabled. Cross-platform
GitHub Actions remains the release-side validation for Windows x64, Linux x64,
and Linux AArch64.

## Current Boundary

- Destruction is explicit. Variables leaving a function or workspace, `clear`,
  runtime shutdown, and unreachable cycles do not yet trigger destructors.
- Scalar handle objects are supported; object arrays and element-wise deletion
  are not yet represented.
- Partially constructed objects do not yet run rollback destructors when a
  constructor reports a diagnostic.
- Recursive destruction of handle-valued properties and cycle-aware weak
  ownership are not implemented.
- The reference HIR interpreter does not execute class objects or lifecycle
  behavior; production `--run` and baseline `--run-bytecode` use the bytecode
  runtime.
