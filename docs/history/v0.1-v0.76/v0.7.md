# MParser v0.7 Scope

MParser v0.7 turns bytecode profiling from execution counters into early JIT
guard input. The VM now records runtime value kind and shape observations for
loop variables, call/index sites, and assignment sites.

## Added Since v0.6

- Structured value observations:
  `kind`, `rows`, `columns`, `observationCount`, and `stable`.
- Loop profile observations for `for` loop variables.
- Call-site observations for function and builtin arguments and outputs.
- Index-site receiver observations, plus index argument and output
  observations.
- Assignment-site profiles for name assignment and indexed assignment.
- Assignment profiles record whether the store happened inside an active loop
  and, when available, the loop header PC.
- CLI `--profile-bytecode` output now prints observed value shapes such as
  `number(1x1) x12`, `matrix(3x3) x1`, or `mixed`.
- Bytecode VM smoke tests assert stable loop-variable, call-site, and
  assignment-site observations.
- Project version and CLI version bumped to `0.7.0`.

## Why This Matters

The v0.5 profiler could identify hot regions. v0.7 starts answering whether a
hot region is safe to specialize:

- Is a loop variable always a scalar number?
- Does a hot function call always receive and return scalar numbers?
- Does an indexed assignment keep the target array shape stable?
- Does an index expression consistently read from a matrix, vector, or scalar?

These observations are not JIT compilation yet. They are the metadata a JIT
needs before it can emit guarded typed code and safely deopt when runtime
behavior changes.

## Bytecode VM Supported Subset

The v0.7 VM can execute the v0.6 numeric/string/control-flow subset and report
profile observations for:

- `for` loop variables.
- Local function calls.
- Builtin calls.
- Numeric indexing expressions.
- Name assignments.
- Indexed assignments into existing numeric arrays.

Observation stability is conservative. If one profile position sees different
runtime kinds or shapes, it is marked `mixed` and should not be used as a
stable specialization guard.

## VM Gaps

The VM still intentionally reports diagnostics for features that need richer IR
or runtime metadata:

- Automatic array growth during indexed assignment.
- Non-scalar right-hand-side indexed assignment shape matching.
- Dynamic function handles and unresolved function dispatch.
- Classes, object dispatch, member assignment, cells, brace indexing, structs,
  tables, sparse arrays, and complex values.
- Actual JIT compilation, optimized IR generation, guard checks, and
  deoptimization.

## Validation

Validated on Windows with MSVC Build Tools:

```powershell
cmake -S . -B build
cmake --build build
ctest --test-dir build --output-on-failure
build\mparser.exe --version
build\mparser.exe --profile-bytecode samples\bytecode_profile_demo.m
build\mparser.exe --profile-bytecode samples\bytecode_indexing_demo.m
build\mparser.exe --run-bytecode samples\switch_demo.m
build\mparser.exe --run-bytecode samples\try_catch_demo.m
```

Expected version output:

```text
MParser 0.7.0
```

Expected profile signal from `bytecode_profile_demo.m`:

```text
variableValue=number(1x1) x12
args=[number(1x1) x12], outputs=[number(1x1) x12]
target=y, executions=12, value=number(1x1) x12, inLoop=yes
```

Expected profile signal from `bytecode_indexing_demo.m`:

```text
receiver=matrix(3x3) x1
outputs=[matrix(3x1) x1]
target=A, executions=1, value=matrix(3x3) x1
```

## Next Iterations

The next high-value work is to consume these observations:

- Add a small optimization-planning pass that selects hot, stable bytecode
  regions.
- Emit explicit guard records from stable profile observations.
- Factor shared runtime numeric and shape helpers so the HIR interpreter,
  bytecode VM, and future optimizing IR agree on MATLAB subset semantics.
- Extend profile observations to `while` loop induction patterns and more
  builtin-specific output shapes.
