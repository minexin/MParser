# MParser v0.70 Scope

MParser v0.70 converts the first v1.0 language/runtime audit into an
executable contract and closes one high-frequency gap found by that audit:
MATLAB-style exception objects shared by the HIR interpreter and bytecode VM.
The milestone covers implementation, cross-tier tests, a production sample,
documentation, and platform CI. It does not claim that every v1.0 Must-have is
already complete.

## Compatibility Contract

`compatibility-matrix.json` is the machine-readable snapshot of the supported
v1.0 target subset. Its 28 feature records describe status and behavior at the
parser, semantic, HIR, bytecode, production, typed, and native tiers. Supported
or partial claims link to registered CTest evidence and source files instead of
relying on prose alone.

The same document contains 16 explicit gaps. Every gap has a priority,
milestone target, framework-impact classification, requirement, and exit
evidence. This keeps the v1.0 route bounded:

- Must-have work closes required language/runtime, extension, embedding, and
  release contracts.
- Should-have work improves optimization or engineering depth without
  blocking correct baseline execution.
- Post-v1.0 work includes unbounded long-tail functions and MATLAB ecosystem
  compatibility.

`validate_compatibility_matrix.cmake` rejects malformed tier states, duplicate
IDs, missing source files, unsupported claims without evidence, evidence names
that are not registered with CTest, and unclassified gap records. The matrix
therefore acts as both documentation and a release test.

## Exception Runtime

`catch name` now binds a scalar `MException` runtime object in both baseline
engines. Its read-only properties are:

- `identifier`: the explicit message identifier, or
  `MParser:RuntimeError` for ordinary runtime diagnostics.
- `message`: the formatted diagnostic text.
- `stack`: a scalar structure containing `file`, `name`, and `line` for the
  current throw site.
- `cause`: an empty 0-by-1 Cell in the current subset.

The shared `runtime_exception` module implements:

- `MException(identifier, message, values...)`.
- `error(message, values...)` and
  `error(identifier, message, values...)`.
- scalar error structures with `message` and optional `identifier` fields.
- `throw(exception)`, which records the current throw site.
- `rethrow(exception)`, which preserves an existing thrown stack.
- ASCII-stable colon-separated identifier validation and limited scalar
  `%s`, `%d`, `%i`, `%f`, `%g`, `%e`, `%c`, and `%%` formatting.

Uncaught exceptions convert back into a `Diagnostic` without losing their
identifier or source span. Invalid constructors, identifiers, formatting, and
throw operands use `MParser:InvalidException`. `class(exception)` returns
`MException`, and `isa(exception, "MException")` returns logical true.

Typed/native execution keeps its conservative contract: exception regions are
not optimized and legal code falls back to the bytecode VM. Optimization
coverage is never required for language correctness.

## Evidence Integrity

Most historical smoke executables use standard C++ `assert`. Optimized builds
previously inherited `NDEBUG`, which could turn those checks into no-ops while
CTest still reported process success. CMake now applies `/UNDEBUG` on MSVC or
`-UNDEBUG` on GCC/Clang to every `_tests` smoke target. Enabling those checks
also exposed and corrected three stale expectations in optimization planning,
compiled-module invocation, and superclass-construction tests.

`exception_runtime_smoke` executes the same source through HIR and bytecode and
checks object kind, properties, formatting, class queries, source file,
function name, line number, cause shape, rethrow preservation, uncaught
diagnostic identity, and identifier validation. Separate CLI tests cover
`--run-hir`, `--run-bytecode`, and the production `--run` interface.

## Example

Run the production sample with:

```powershell
build\mparser.exe --run samples\exception_runtime_demo.m
```

Expected result:

```text
summary = 111111111
```

The summary verifies explicit identifiers and formatting, `class` and `isa`,
stack/cause shape, explicit throw, stack-preserving rethrow, and automatic
runtime identifiers. The same file runs under `--run-hir` and
`--run-bytecode`.

## Validation

Configure and validate a native-JIT build:

```powershell
cmake -S . -B build -DMPARSER_ENABLE_NATIVE_JIT=ON
cmake --build build --parallel
ctest --test-dir build --output-on-failure
```

Repeat with `MPARSER_ENABLE_NATIVE_JIT=OFF` for the portable-only build. The
Windows x64 Release validation passed `126/126` tests with native JIT enabled
and `120/120` tests with it disabled. Both configurations execute assertions in
optimized smoke targets.

Linux AArch64 QEMU CI runs focused exception, compatibility-matrix, structure,
and production-interface checks in native-JIT and portable-only builds. Full
Windows x64 and Linux x64 jobs continue to run the complete suite; all three
jobs are required at the pushed-commit release gate.

## Current Boundary

- `stack` publicly exposes one scalar frame. Full N-by-1 stack structure
  arrays, complete nested call stacks, and stack mutation APIs are v0.73 work.
- `cause` is present but empty. `addCause`, cause chaining, and cause traversal
  are v0.73 work.
- Message formatting deliberately covers common scalar replacements, not the
  complete MATLAB `sprintf` grammar or array formatting behavior.
- `Correction`, `getReport`, `lastwarn`, warning-state semantics, cleanup
  objects, and complete error-structure compatibility are not implemented.
- HIR class execution remains smaller than bytecode class execution; this
  exception milestone does not change that declared tier boundary.

## Next Ordered Gaps

The compatibility matrix makes the next framework-sensitive work explicit:

1. v0.71: structure arrays and comma-separated field-result semantics.
2. v0.72: general nested lvalue copy-back for arrays, Cells, structures, and
   value objects.
3. v0.73: complete exception stacks, causes, and propagation contracts.
4. v0.74-v0.79: dynamic calls/handles, distinct text representation, object
   arrays/reflection boundaries, and the `RuntimeValue` contract freeze.
5. v0.80: unified builtin registry and representative function migration.

The complete Must-have, Should-have, and Post-v1.0 definitions remain in
[roadmap-v1.0.md](../../roadmap-v1.0.md).
