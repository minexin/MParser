# v1 Release Process

This document defines the local CMake/CPack release build type and its trust
boundary. It is the target of the `buildType` and `builder.id` URIs emitted by
MParser's SLSA Provenance v1 statement.

## CMake CPack Release v1

Build type URI:

```text
https://github.com/minexin/MParser/blob/main/docs/release-process.md#cmake-cpack-release-v1
```

The build takes these external parameters:

| Parameter | Meaning |
| --- | --- |
| `repository` | Canonical source repository |
| `revision` | Exact Git commit used as the source-base dependency |
| `configuration` | CMake configuration used for installed binaries |
| `nativeJit` | Whether the bundled SLJIT backend is compiled |
| `releasePackaging` | Always `true` for this build type |
| `sourceDateEpoch` | Archive metadata normalization epoch |
| `projectVersion` | CMake project/package version |

The statement also records the selected generator, compiler identity/version,
target system, and target processor as internal parameters. Its resolved
dependencies bind the base Git commit plus SHA-256 values for CMake build
configuration and the public CLI/API/protocol/compatibility contracts.

From a clean checkout at `revision`, initialize the platform compiler
environment, then run:

```text
cmake -S . -B build/release-package -G Ninja -DCMAKE_BUILD_TYPE=Release -DMPARSER_ENABLE_NATIVE_JIT=ON -DMPARSER_ENABLE_RELEASE_PACKAGING=ON
cmake --build build/release-package --parallel
cmake --build build/release-package --target mparser_release_package
```

On Windows, run those commands after `vcvars64.bat`. The target invokes CPack
with the configured `SOURCE_DATE_EPOCH`, creates the platform/architecture
archive, validates its unsigned provenance statement, and writes:

```text
<archive>
<archive>.sha256
<archive>.provenance.json
SHA256SUMS
```

`SHA256SUMS` binds both the archive and provenance statement. The CPack
sidecar binds the archive independently. The provenance is not placed inside
the archive because its subject digest would otherwise be self-referential.

The publication target rejects a dirty Git worktree before invoking CPack.
The executable
`release_archive_smoke` may generate a statement with
`mparser_sourceTreeClean: false` solely to exercise the structure during
development; such an artifact is not publishable. The same gate alters an
archive payload and the statement authentication field independently and
requires both mutations to be rejected by the semantic validator.

## Local CMake Builder v1

Builder ID:

```text
https://github.com/minexin/MParser/blob/main/docs/release-process.md#local-cmake-builder-v1
```

This builder means a developer-controlled local machine running the checked-in
CMake/CPack scripts. Its trust boundary includes the machine, operating
system, compiler installation, source checkout, invoking user, and all
processes able to alter them. There is no isolated or independently trusted
control plane.

All provenance fields are generated by tenant-controlled project scripts.
Only the archive and local source/toolchain state visible to those scripts are
measured. Dependency completeness is best effort and does not enumerate every
operating-system library or transitive toolchain component.

The emitted document is an unsigned
[in-toto Statement v1](https://github.com/in-toto/attestation/blob/main/spec/v1/statement.md)
using the
[SLSA Provenance v1 predicate](https://slsa.dev/spec/v1.2/build-provenance).
It intentionally records `mparser_authentication: "unsigned"`. MParser makes
no SLSA level claim for this local builder, and the statement proves neither
publisher identity nor resistance to local tampering.

### MParser Extension Fields

`mparser_authentication` describes only the raw JSON statement emitted by the
local builder. Its value is always `unsigned`; it is not a signer identity and
does not override or describe a later DSSE, Sigstore, or hosted attestation
envelope.

`mparser_sourceTreeClean` reports whether
`git status --porcelain --untracked-files=normal` was empty when the statement
was generated. The publication target requires `true`; development smoke
artifacts may record `false` and are not publishable.

Ignoring either extension field must not confer trust. Publication policy
independently requires a clean release commit, matching artifact and input
digests, and an accepted signer-builder pair or equivalent hosted identity.

## Verification And Publication

Before publication:

1. Require a clean source checkout at the intended release commit and tag.
2. Run native, no-JIT, sanitizer, installed-consumer, and release-archive
   gates applicable to the platform. In a packaging build,
   `ctest -L release --output-on-failure` runs the documentation,
   candidate-readiness, negative readiness-guard, and archive gates together.
3. Regenerate the package with `mparser_release_package`.
4. Verify both lines in `SHA256SUMS`.
5. Verify the provenance subject digest, source revision, contract digests,
   builder/build type, platform, compiler, and build parameters.
6. Attach publisher authentication using the selected release signing or
   hosted provenance mechanism.

The candidate-readiness gate requires the remaining Must-have set to be
exactly provenance authentication, cross-platform reliability evidence,
cross-platform performance evidence, and cross-platform package/documentation
confirmation. Every one must have `framework_impact: none`. It also confines
the only open Should-have to specialist sanitizer evaluation and records
guarded JIT breadth as an additive Should-have explicitly deferred to v1.x.
The measured [v1.0 JIT scope decision](v1.0-jit-scope-decision.md) and its
fixed-report validator preserve that boundary. Negative fixtures prove that
Must-have/Should-have impact, deferred-JIT reactivation, and blocker-set drift
are rejected. Any additional or reclassified gap fails the release label.

A signed DSSE/Sigstore or hosted-platform attestation may wrap or supersede
the local unsigned statement for publication. Its authenticated builder
identity must describe the actual hosted trust boundary; it must not reuse the
local builder ID. Final cross-platform authentication and release publication
remain part of the shared validation window.
