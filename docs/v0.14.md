# MParser v0.14 Scope

MParser v0.14 makes typed-region performance measurable as a first-class
runtime path. The benchmark runner now executes the HIR interpreter, baseline
bytecode VM, and typed-region bytecode VM under one policy, while treating
exact three-way output equivalence as a correctness requirement.

## Added Since v0.13

- A three-path runtime benchmark covering the HIR interpreter, baseline
  bytecode VM, and typed-region bytecode VM.
- One unmeasured baseline profiling pass that builds the typed IR module before
  warmup and measurement begin.
- Common warmup counts for all three paths.
- Three-way execution-order rotation to reduce systematic first/last-run bias.
- Timing distributions for every path: total, mean, median, minimum, and
  maximum duration.
- Mean baseline and typed VM dispatcher instruction counts per run.
- Mean typed-region attempts, executions, fallbacks, and executed typed
  instructions per run.
- Exact HIR-to-baseline and baseline-to-typed variable comparisons.
- Typed IR region count in the CLI report.
- Relative baseline-VM/interpreter and typed-VM/baseline-VM speed ratios.
- A dedicated closed scalar loop benchmark sample.
- Smoke coverage for both an eligible scalar loop and an ineligible call-heavy
  loop.
- Project version and CLI version bumped to `0.14.0`.

## Why This Matters

Typed execution is no longer validated only by a functional one-shot command.
It can now be compared repeatedly against both semantic and VM reference paths:

```text
parse + lower once
  -> unmeasured baseline profile
  -> optimization plan + typed IR
  -> warm up all paths
  -> rotate and time:
       HIR interpreter
       baseline bytecode VM
       typed-region bytecode VM
  -> require exact three-way outputs
  -> report timing and executed work
```

The work counters distinguish two important effects. VM dispatcher
instructions show how much general bytecode dispatch remains, while typed
instructions show the scalar operations completed inside the region executor.
This makes a speed result inspectable instead of relying on wall-clock time
alone.

## Typed Loop Benchmark

```powershell
build\mparser.exe --benchmark-runtime --benchmark-warmup=3 `
  --benchmark-iterations=20 samples\typed_benchmark_demo.m
```

Expected signals include:

```text
typed IR regions: 2
bytecode VM: ... instructionsPerRun=14006.000
typed bytecode VM: ... instructionsPerRun=6.000
typedAttempts=1.000, typedExecutions=1.000, typedFallbacks=0.000
typedInstructions=12000.000
outputs: match (all runtime outputs match)
```

The exact timing and speed ratio depend on the machine and build
configuration. The counters and output-equivalence result are the stable
behavioral checks.

## Conservative Benchmark

```powershell
build\mparser.exe --benchmark-runtime --benchmark-warmup=3 `
  --benchmark-iterations=20 samples\runtime_benchmark_demo.m
```

This sample contains local calls in its loops. Those regions remain ineligible,
so the typed VM follows the baseline bytecode path and reports no typed-region
attempt. The three outputs must still match.

## Current Limitations

- The typed module is created by a deliberate profiling pass before timing;
  adaptive promotion within one VM lifetime is not implemented yet.
- Typed execution still collects the surrounding VM profile, so its timing is
  not yet a profile-off steady-state number.
- Only eligible closed scalar `for` loops execute through the typed executor.
- Calls, indexing, arrays, mutation, nested control flow, and unsupported
  operations remain ineligible or fall back.
- The typed executor is portable C++, not native machine code.
- The benchmark is an in-process microbenchmark, not a statistical replacement
  for representative MATLAB workload suites.

## Remaining Before v1.0

- Add profile-off execution after specialization.
- Promote hot loops adaptively within a single VM lifetime.
- Lower typed scalar operations to LLVM ORC JIT on Windows and ARM Linux.
- Add deoptimization metadata for native frames and resume PCs.
- Extend optimized regions to conditionals, calls, indexing, and arrays.
- Add broader conformance and performance suites with MATLAB-compatible
  expected results.
- Expand runtime coverage for objects, cells, structs, complex values, sparse
  arrays, dynamic dispatch, and broader builtin behavior.


Expected version output:

```text

```

## Next Iteration

The next milestone should isolate steady-state execution cost:

- Add an explicit VM profiling policy.
- Disable profile collection after a typed module has been created.
- Benchmark profiled baseline, profile-off baseline, and profile-off typed
  execution without weakening output-equivalence checks.
- Keep instrumentation available on demand for diagnostics and tiering.
