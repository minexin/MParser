# MParser v0.15 Scope

MParser v0.15 separates profile collection from steady-state bytecode
execution. A full profile can still drive optimization planning, but baseline
and typed VM runs can now skip detailed instrumentation after the typed module
has been created.

## Added Since v0.14

- Public `BytecodeVmOptions` with `Full` and `Disabled` profiling modes.
- A `collected` marker on `BytecodeVmProfile` so callers can distinguish an
  intentionally disabled profile from an empty workload.
- Profile-off overloads for baseline and typed-module VM execution.
- No per-PC execution vector allocation when profiling is disabled.
- No function, loop, call/index-site, assignment, kind, or shape observation
  updates in profile-off mode.
- Lightweight total dispatcher counts remain available in both modes.
- Typed-region attempts, executions, fallbacks, iterations, and instruction
  counts remain available in profile-off mode.
- Ordinary `--run-bytecode` execution now defaults to profile-off mode.
- Analysis, planning, typed-IR, and guard-check commands still collect a full
  profile.
- `--run-typed-bytecode` uses a full baseline planning pass followed by a
  profile-off typed execution pass.
- A four-path runtime benchmark: HIR interpreter, profiled bytecode VM,
  profile-off bytecode VM, and profile-off typed bytecode VM.
- Four-way cyclic measurement order and exact output equivalence checks.
- Separate speed ratios for profiling overhead and typed-region execution.
- Direct profile-off VM tests and benchmark policy tests.
- Project version and CLI version bumped to `0.15.0`.

## Execution Policy

The VM now supports two explicit phases:

```text
analysis phase
  full profile -> optimization plan -> typed IR

steady-state phase
  profile-off baseline VM
  or
  profile-off typed VM -> transactional fallback to baseline bytecode
```

Profile-off execution does not alter language semantics. It only suppresses
the data structures used to discover optimization opportunities. Aggregate
dispatcher and typed-region counters remain enabled so benchmark reports can
still explain which execution path ran.

## Four-Path Benchmark

```powershell
build\mparser.exe --benchmark-runtime --benchmark-warmup=3 `
  --benchmark-iterations=20 samples\typed_benchmark_demo.m
```

Expected report shape:

```text
HIR interpreter: ...
profiled bytecode VM: ... instructionsPerRun=14006.000
profile-off bytecode VM: ... instructionsPerRun=14006.000
profile-off typed bytecode VM: ... instructionsPerRun=6.000,
  typedAttempts=1.000, typedExecutions=1.000,
  typedFallbacks=0.000, typedInstructions=12000.000
profile-off speed relative to profiled VM: ...x
typed VM speed relative to profile-off VM: ...x
outputs: match (all runtime outputs match)
```

Timing ratios vary by machine and build configuration. Stable checks are the
equal baseline instruction counts, typed dispatcher reduction, typed execution
counters, and four-way output match.

## CLI Policy

These commands require a full profile and retain it automatically:

```powershell
build\mparser.exe --profile-bytecode samples\bytecode_profile_demo.m
build\mparser.exe --plan-bytecode samples\typed_region_demo.m
build\mparser.exe --typed-ir-bytecode samples\typed_region_demo.m
build\mparser.exe --check-typed-ir-bytecode samples\typed_region_demo.m
```

These execution commands use profile-off steady-state runs where possible:

```powershell
build\mparser.exe --run-bytecode samples\bytecode_control_demo.m
build\mparser.exe --run-typed-bytecode samples\typed_region_demo.m
```

## Current Limitations

- Profile-off mode still increments one aggregate dispatcher counter per VM
  instruction.
- Typed execution summaries remain instrumented for correctness and reporting.
- Promotion is still a two-pass workflow; a long-lived VM does not yet switch
  tiers while a script is running.
- Only eligible closed scalar `for` loops execute through the typed executor.
- The typed executor is portable C++, not native machine code.
- Calls, indexing, arrays, mutation, and nested control flow remain outside the
  executable typed-region subset.

## Remaining Before v1.0

- Add a long-lived VM session with adaptive hot-loop promotion.
- Accumulate profiles across function invocations without rebuilding runtime
  state.
- Install typed regions atomically while execution continues.
- Lower typed scalar operations to LLVM ORC JIT on Windows and ARM Linux.
- Add native deoptimization metadata and bytecode resume state.
- Extend optimized regions to conditionals, calls, indexing, and arrays.
- Expand MATLAB runtime and conformance coverage, especially classes, objects,
  cells, structs, complex values, sparse arrays, and dynamic dispatch.

Expected version output:

```text

```

## Next Iteration

The next milestone should move from two-pass execution to adaptive tiering:

- Keep profile state across repeated VM invocations.
- Promote a loop only after a configurable hot threshold is reached.
- Install a typed region in the same runtime session.
- Record promotion, guard failure, and deoptimization events.
- Compare cold, warming, and steady-state phases with deterministic tests.
