# MParser v0.16 Scope

MParser v0.16 adds the first adaptive execution session. Profiles now survive
across repeated program invocations, cumulative heat can trigger typed-module
installation, and later invocations automatically execute in the profile-off
typed tier.

## Added Since v0.15

- New `AdaptiveBytecodeVmSession` API.
- Configurable cumulative hot-loop threshold.
- Cross-invocation merging for instruction counts, function counts, loop
  activity, call/index sites, assignments, and runtime kind/shape observations.
- Stable observation preservation and conservative `mixed` marking when
  accumulated observations disagree.
- Automatic optimization planning after every successful profiling invocation.
- Atomic typed-module installation only when at least one executable scalar
  loop region exists.
- Profile-off typed execution from the invocation after promotion.
- Persistent typed-module and accumulated-profile inspection APIs.
- Session reset support.
- Per-invocation tier, profile state, dispatch count, cumulative loop heat,
  promotion, installed-region, and typed execution summaries.
- CLI option `--run-adaptive-bytecode`.
- CLI controls `--adaptive-runs=N` and `--adaptive-hot-loop=N`.
- A short-loop sample that requires two invocations to reach the default heat
  threshold.
- Tests for successful promotion, dynamic typed fallback, session reset, and
  static rejection of call-heavy loops.
- Project version and CLI version bumped to `0.16.0`.

## Tiering Model

The session owns the transition instead of requiring the caller to manually
run the profiler, planner, builder, and typed VM:

```text
invocation 1
  profiling VM -> merge profile -> below threshold

invocation 2
  profiling VM -> merge profile -> threshold reached
  -> plan -> build -> install executable typed module

invocation 3+
  profile-off typed VM
  -> typed region succeeds and commits
  or
  -> guard/runtime check fails and unchanged-state bytecode resumes
```

Promotion occurs at an invocation boundary. v0.16 does not replace a loop while
its current activation is on the stack, so this milestone should not be
confused with on-stack replacement.

## Adaptive CLI

```powershell
build\mparser.exe --run-adaptive-bytecode --adaptive-runs=3 `
  --adaptive-hot-loop=10 samples\adaptive_tiering_demo.m
```

Expected transition:

```text
invocation=1, tier=profiling, profile=full, dispatched=48,
  accumulatedLoopIterations=6, hotLoops=0, promoted=no
invocation=2, tier=profiling, profile=full, dispatched=48,
  accumulatedLoopIterations=12, hotLoops=1, promoted=yes,
  installedRegions=2, executableRegions=1
invocation=3, tier=typed, profile=off, dispatched=6,
  accumulatedLoopIterations=12, hotLoops=1,
  typedAttempts=1, typedExecutions=1, typedFallbacks=0
```

The final variables are `i = 6` and `y = 91` on every invocation.

## Dynamic Fallback

```powershell
build\mparser.exe --run-adaptive-bytecode --adaptive-runs=2 `
  --adaptive-hot-loop=10 samples\typed_region_fallback_demo.m
```

The first invocation promotes the structurally eligible loop. The next
invocation enters the typed tier, discovers vector state at the region entry,
and falls back transactionally:

```text
tier=typed, profile=off, typedAttempts=1,
typedExecutions=0, typedFallbacks=1
```

The baseline result remains `y = [338350 338350]`.

## Conservative Installation

A cumulative profile may contain hot candidates without an executable typed
region. For example, a loop containing a local function call is hot but its
region contract rejects calls. The session keeps profiling and does not install
a module merely because descriptive typed IR regions exist.

## Current Limitations

- Tier changes occur only between complete invocations.
- Each invocation starts with fresh VM variables and call frames; persistent
  MATLAB workspaces are not implemented yet.
- Installed modules are immutable for the rest of the session.
- Repeated dynamic fallback does not yet invalidate or retrain a region.
- There is no promotion cooldown, code cache, background compilation, or OSR.
- The executable typed tier is still portable scalar C++, not native code.
- Calls, indexing, arrays, mutation, and nested control flow remain outside the
  executable typed-region subset.

## Remaining Before v1.0

- Add typed-region invalidation and fallback-rate policy.
- Re-enter profiling after repeated guard failures and replace stale modules.
- Preserve workspace state and support parameterized repeated calls.
- Add native LLVM ORC compilation on Windows and ARM Linux.
- Define native frame maps, deoptimization state, and bytecode resume PCs.
- Add loop-midpoint OSR after the invocation-boundary model is stable.
- Extend optimized regions to conditionals, calls, indexing, and arrays.
- Expand MATLAB class/object and runtime compatibility.


## Next Iteration

The next milestone should make adaptive tiering self-correcting:

- Track fallback rates across typed invocations.
- Invalidate a typed module after a configurable failure threshold.
- Resume profiling after invalidation.
- Retrain and reinstall a replacement module when observations stabilize.
- Expose promotion and invalidation history through deterministic events.
