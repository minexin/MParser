# MParser v0.19 Scope

MParser v0.19 turns function files into reusable bytecode entry points. Callers
can select a same-file function, pass positional runtime values, receive its
declared outputs in order, and retain adaptive tiering across calls with
changing arguments.

## Added Since v0.18

- `BytecodeVmOptions::entryFunction`.
- `BytecodeVmOptions::arguments` for positional runtime values.
- Named function selection instead of always executing the first declaration.
- Entry argument-count validation against the semantic function signature.
- Parameter binding in the outer entry frame.
- Declared output extraction in source order.
- `BytecodeVmResult::entryFunction`, `outputNames`, and `outputs`.
- Full variable snapshots retained separately for diagnostics and inspection.
- `BytecodeFunctionEntryProfile` with parameter names, output names, invocation
  count, argument observations, and result observations.
- Profile-off named function execution with the same call/result semantics.
- Cross-invocation merge of function entry profiles.
- Adaptive entry-function and initial argument configuration.
- Adaptive argument inspection and replacement APIs.
- Function argument evidence in post-invalidation retraining.
- CLI options `--entry-function=name` and repeatable `--argument=value`.
- Scalar, string, and row-vector arguments through the common runtime literal
  parser.
- CLI declared-output report.
- Tests for selecting a non-first function, dual outputs, profile-on/profile-off
  execution, bad arity, missing functions, argument-driven invalidation, and
  successful argument-driven re-promotion.
- Project version and CLI version bumped to `0.19.0`.

## Function Entry Contract

```text
program + selected function + positional arguments
  -> find bytecode/HIR function signature
  -> validate argument count
  -> bind parameters in declaration order
  -> initialize declared outputs
  -> execute selected function body
  -> return:
       complete entry-frame variables
       declared output names
       declared output values in source order
```

Unselected same-file functions remain available for local calls but are not run
as the top-level entry.

## Named Dual-Output Call

```powershell
build\mparser.exe --run-bytecode --entry-function=kernel `
  --argument=2 --argument=4 samples\function_entry_demo.m
```

Expected declared outputs:

```text
Function outputs (kernel):
  s = 20
  p = 8
```

The variables report additionally includes parameters and loop locals for
debugging. Consumers should use `BytecodeVmResult::outputs` when they need the
function's public result contract.

## Function Entry Profile

```powershell
build\mparser.exe --profile-bytecode `
  --entry-function=adaptive_function_demo --argument=3 `
  samples\adaptive_function_demo.m
```

Expected profile signal:

```text
function entries:
  adaptive_function_demo: invocations=1,
    args=[number(1x1) x1], outputs=[number(1x1) x1]
```

## Adaptive Function Calls

```powershell
build\mparser.exe --run-adaptive-bytecode --adaptive-runs=3 `
  --adaptive-hot-loop=10 --entry-function=adaptive_function_demo `
  --argument=3 samples\adaptive_function_demo.m
```

The first two calls accumulate six loop iterations each and promote. The third
call executes the scalar loop in the profile-off typed tier and returns `y=63`.

The API additionally supports `AdaptiveBytecodeVmSession::setArguments()`. The
smoke suite changes `seed` from scalar to vector, triggers two fallbacks and an
invalidation, then restores a scalar argument. Fresh function-entry profiles
prove that `seed` is scalar, the region is promoted again, and the final typed
call succeeds.

## Current Limitations

- Arguments are positional only; defaults, name-value arguments, `varargin`,
  and `nargin` are not implemented.
- All declared outputs are returned; requested output-count semantics are not
  exposed for the top-level entry yet.
- Entry functions must exist in the already lowered same-file program.
- Methods, constructors, package functions, path lookup, and function handles
  are not entry targets yet.
- Function entry executes synchronously and copies runtime argument values.
- The benchmark runner does not yet accept parameterized entry options.
- The typed executor is portable scalar C++, not native machine code.

## Remaining Before v1.0

- Introduce a reusable compiled-program/module object.
- Add requested output counts, `nargout`, `nargin`, and `varargin` behavior.
- Add package/path lookup and method/constructor entry resolution.
- Add per-function adaptive code caches and independent region replacement.
- Add native LLVM ORC compilation on Windows and ARM Linux.
- Define native calling conventions, frame maps, deoptimization values, and
  resume PCs.
- Extend typed regions to calls, indexing, arrays, matrices, and conditionals.
- Expand MATLAB classes, objects, containers, and builtin coverage.

## Next Iteration

The next milestone should make parse/lower artifacts reusable and explicit:

- Add a compiled module that owns semantic HIR and bytecode.
- Validate entry names and signatures once at module creation.
- Create independent invocation objects with arguments and workspaces.
- Keep adaptive profile/code state attached to the compiled module.
- Benchmark compile-once, invoke-many workloads.
