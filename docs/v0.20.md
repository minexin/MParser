# MParser v0.20 Scope

MParser v0.20 introduces a reusable compiled-module boundary. An embedding can
now run the complete frontend once, retain semantic HIR and bytecode, inspect
callable signatures, validate a named entry, and create repeated ordinary or
adaptive VM invocations without reparsing or relowering the source.

## Added Since v0.19

- Public `FunctionSignature` parsing shared by the bytecode VM and module API.
- `CompiledModule::compile()` for the lexer, parser, semantic analyzer, and
  bytecode-lowering pipeline.
- Owned source text, HIR, bytecode, and aggregated phase diagnostics.
- Compilation short-circuiting after parse, semantic, or lowering failures.
- `CompiledFunctionInfo` catalog for invocable top-level functions.
- Function lookup with parameter names, output names, and source spans.
- Class-method exclusion until object dispatch becomes executable.
- Duplicate top-level function diagnostics at the module boundary.
- Named-entry and argument-count preflight through `validateInvocation()`.
- `invoke()` for independent repeated bytecode VM calls over one module.
- `createAdaptiveSession()` for tiering over the same immutable artifacts.
- `--module-info` CLI mode with function catalog and optional entry preflight.
- `samples/compiled_module_demo.m` with two signatures and a hot loop.
- A twelfth CTest target covering catalog construction, compile-once/invoke-many,
  dual outputs, preflight failures, adaptive promotion, invalid compilation,
  and class catalog boundaries.
- Project and CLI version bumped to `0.20.0`.

## Module Contract

```text
source
  -> lex -> parse -> semantic HIR -> bytecode
  -> CompiledModule {
       source, diagnostics, HIR, bytecode, function catalog
     }
  -> validate entry once
  -> ordinary VM invocation 1..N
     or adaptive session invocation 1..N
```

`CompiledModule` is move-only because it owns the HIR. Ordinary `invoke()` calls
are independent. An adaptive session intentionally owns its profile, installed
typed module, invalidation history, and workspace state, while referencing the
compiled module's immutable HIR and bytecode. The `CompiledModule` must outlive
sessions created from it.

## CLI Catalog

```powershell
build\mparser.exe --module-info --entry-function=accumulate_scale `
  --argument=2 --argument=4 samples\compiled_module_demo.m
```

Expected core report:

```text
Compiled module:
  status: valid
  bytecode instructions: 26
  invocable functions: 2
Functions:
  compiled_module_demo() -> [y] @ 1:1
  accumulate_scale(x, n) -> [total, product] @ 5:1
Entry validation:
  function: accumulate_scale
  arguments: 2
  status: valid
```

An unknown function or wrong argument count exits with a diagnostic before the
VM starts.

## Embedding Example

```cpp
auto module = mparser::CompiledModule::compile(source);
if (!module.valid()) {
    // Report module.diagnostics().
}

mparser::BytecodeVmOptions call;
call.entryFunction = "accumulate_scale";
call.arguments = {x, n};
auto first = module.invoke(call);

call.arguments = {nextX, nextN};
auto second = module.invoke(call);

mparser::AdaptiveBytecodeVmOptions adaptive;
adaptive.entryFunction = "accumulate_scale";
adaptive.arguments = {x, n};
auto session = module.createAdaptiveSession(adaptive);
auto warmup = session.run();
```

## Current Limitations

- The catalog exposes top-level same-file functions only. Class methods,
  constructors, nested functions, packages, and path-resolved functions are
  not module entry points.
- Positional fixed-arity parameters remain the only entry argument convention.
- Module compilation is synchronous and in-memory; no serialized bytecode or
  persistent cache format exists yet.
- Adaptive profile and typed-code state belong to each session, not a shared
  per-function cache in the module.
- A module must outlive its adaptive sessions because sessions retain pointers
  to its immutable HIR and bytecode.
- The typed executor remains portable scalar C++, not native machine code.

## Remaining Before v1.0

- Add per-function runtime state and independently replaceable typed-code caches.
- Add requested output counts, `nargout`, `nargin`, and `varargin` behavior.
- Add package/path lookup and method/constructor entry resolution.
- Add a stable serialized bytecode/module cache with compatibility metadata.
- Add native LLVM ORC compilation on Windows and ARM Linux.
- Define native calling conventions, frame maps, deoptimization values, and
  resume PCs.
- Extend typed regions to calls, indexing, arrays, matrices, and conditionals.
- Expand MATLAB classes, objects, containers, and builtin coverage.

## Next Iteration

The next milestone should make adaptive optimization granular per function:

- Introduce a module runtime that owns independent function execution states.
- Attach profiles, promotion state, and installed typed regions to function IDs.
- Preserve unaffected specializations when one function invalidates.
- Expose cache and tier state through the module API and CLI.
- Test alternating hot functions with independent promotion and invalidation.
