# MParser v0.25 Scope

MParser v0.25 gives the v0.24 class runtime an explicit ownership model. It
distinguishes MATLAB-style value objects from classes declared with the
built-in `handle` superclass marker, and it completes the zero-output call path
needed by mutating methods that are invoked as statements.

## Added Since v0.24

- Class superclass lists are retained in semantic HIR and shown by `--hir`.
- Classes declared as `classdef Name < handle` allocate shared property
  storage; copied runtime values retain the same storage identity.
- Mutating a direct property through one handle alias is immediately visible
  through every other alias.
- Ordinary classes retain value-copy behavior: assigning an object copies its
  current property map, and later direct property writes are isolated.
- Standalone `CallOrIndex` statements lower with `resultCount = 0`.
- Local functions, constructors, methods, builtins, and indexing accept a
  zero-result request without pushing a placeholder onto the VM stack.
- Outputless method frames receive `nargout == 0` through the existing function
  call contract.
- Runtime formatting, equality support, and benchmark comparison understand
  shared object fields.
- `samples/handle_semantics_demo.m` and a seventeenth CTest target cover HIR
  superclass retention, lowering, alias mutation, value-copy isolation, and
  zero-output method introspection.
- Project and CLI version bumped to `0.25.0`.

## Example

```powershell
build\mparser.exe --run-bytecode samples\handle_semantics_demo.m
```

Expected values:

```text
alias = <MutableBox>
original = <MutableBox>
shared_value = 9
statement_nargout = 0
```

## Current Limitations

- `< handle` is currently an ownership marker only. General superclass method
  lookup, constructor chaining, multiple inheritance, and `superclass@method`
  dispatch are not implemented.
- Handle lifecycle behavior (`delete`, `isvalid`, destruction callbacks, weak
  references, and cycle collection) is not implemented.
- Property writes require a direct variable receiver such as `obj.Value = 1`;
  nested receivers and indexed object arrays remain unsupported.
- Ordinary value-class methods do not implicitly write a mutated receiver back
  to the caller. Return the object and assign it explicitly when mutation must
  persist through a method call.
- Access control, property defaults and validation, events, enumerations,
  dependent properties, and overloaded operators remain future work.
- Class execution remains a bytecode-VM feature; the reference HIR interpreter
  does not execute objects.
- Native machine-code JIT and non-scalar object layout remain future work.


## Next Iteration

- Add general superclass resolution, inherited property layout, and method
  lookup with deterministic precedence.
- Add constructor chaining and explicit superclass method dispatch.
- Add access-control checks and property defaults before executable validation.
- Add handle lifecycle and an object-storage strategy that can reclaim cycles.
- Add multidimensional Cells and comma-separated-list expansion.
- Introduce native LLVM ORC compilation on Windows and ARM Linux.
