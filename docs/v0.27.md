# MParser v0.27 Scope

MParser v0.27 makes superclass initialization executable. It introduces a
dedicated representation for MATLAB's `@Superclass` call forms, validates
constructor ordering in the semantic layer, and carries one most-derived
object through every constructor in a same-file hierarchy.

## Added Since v0.26

- `SuperclassCallExpr`, `SuperclassCall`, and `CallSuperclass` preserve
  superclass-qualified syntax through the syntax tree, semantic HIR, and
  bytecode instead of treating it as a neutral call/index operation.
- Both `obj@Base(args)` and `obj = obj@Base(args)` initialize a direct base and
  update the active constructor object.
- Explicit constructor calls retain source order and pass evaluated arguments
  to the selected direct superclass.
- Direct superclasses not called explicitly receive implicit zero-argument
  construction in declaration order.
- A class with no constructor forwards its arguments to its first executable
  direct superclass and calls remaining direct bases without arguments.
- One construction context owns the most-derived object, tracks active and
  initialized classes, and prevents a shared diamond ancestor from running
  more than once.
- Value-class constructor results are written back through each active frame;
  handle-derived objects preserve one shared property store throughout the
  constructor chain.
- `method@Base(obj, args)` invokes the exact method declared by `Base`, while
  ordinary calls made inside that implementation continue to dispatch through
  the runtime class of `obj`.
- Semantic diagnostics reject constructor calls to indirect bases, duplicate
  calls, conditional calls, calls after another object reference, object use in
  superclass arguments, missing constructor outputs, and malformed qualified
  base-method calls.
- Semantic diagnostics now flow into lowered bytecode diagnostics, so invalid
  construction cannot silently enter VM execution.
- `samples/superclass_construction_demo.m` and a nineteenth CTest target cover
  frontend retention, both explicit forms, implicit construction, default
  forwarding, value and handle objects, diamond initialization, qualified
  dispatch, and failure diagnostics.
- Project and CLI version bumped to `0.27.0`.

## Example

```powershell
build\mparser.exe --run-bytecode samples\superclass_construction_demo.m
```

Expected values include:

```text
base_id = 4
base_revision = 2
derived_pages = 3
forwarded_id = 7
implicit_tag = 5
qualified_score = 46
tagged_payload = 9
```

`qualified_score` demonstrates both dispatch rules. `Report.score` explicitly
selects `RecordBase.score`; the base implementation then calls
`obj.adjustment()`, which dynamically dispatches back to `Report.adjustment`.

## Construction Contract

- The VM allocates a scalar most-derived object before entering any constructor.
- An explicit constructor target must be a direct, same-file, executable
  superclass and can be called only once by that constructor.
- Explicit calls must be unconditional and precede every other reference to the
  constructor output object.
- Superclass constructor arguments cannot reference the object being built.
- Every uncalled direct superclass is initialized with zero arguments before
  the derived constructor body executes.
- A default derived constructor passes its received arguments to the first
  non-`handle` direct superclass and initializes later bases with no arguments.
- A common superclass reached through multiple direct bases is initialized
  once per most-derived object.
- A qualified base-method call must name the currently executing method and an
  actual ancestor that declares that method.

These rules follow the public MATLAB superclass-construction and base-method
call forms described by MathWorks:

- <https://www.mathworks.com/help/matlab/matlab_oop/subclass-constructors.html>
- <https://www.mathworks.com/help/matlab/matlab_oop/calling-superclass-methods-on-subclass-objects.html>

## Current Limitations

- Runtime class lookup remains limited to classes in the same compiled source;
  package folders, class folders, imports, and MATLAB path discovery are not
  connected to the class registry.
- The built-in `handle` root contributes ownership semantics but has no
  executable constructor or lifecycle methods. Other built-in superclass
  constructors are unsupported.
- Implicit direct-base construction is performed eagerly before the derived
  constructor body rather than lazily at the first object reference.
- Property declarations still do not preserve executable default expressions,
  validation blocks, dimensions, types, or full attribute metadata.
- `Access`, `Abstract`, `Sealed`, and `HandleCompatible` constraints are not
  enforced, and access-specific duplicate property rules remain conservative.
- Constructor cleanup after a partially initialized handle object fails is not
  implemented because `delete` and `isvalid` are not executable yet.
- Class execution remains a bytecode-VM feature; the reference HIR interpreter
  reports class and superclass calls as unsupported.
- Object arrays, events, enumerations, dependent properties, overloaded
  operators, native machine-code JIT, and non-scalar object layout remain
  future work.

```powershell
cmake -S . -B build -G Ninja
cmake --build build --clean-first
ctest --test-dir build --output-on-failure

build\mparser.exe --hir samples\superclass_construction_demo.m

```

Expected version output:

```text
MParser 0.27.0
```

## Next Iteration

- Retain and execute property default expressions before constructor bodies.
- Preserve property validation, dimensions, type constraints, and class/member
  attributes in runtime descriptors.
- Enforce `Abstract`, `Sealed`, access, and handle-compatibility rules.
- Add package/path class discovery and reusable class module entries.
- Expand object behavior toward arrays, operator overloads, events, and handle
  lifecycle.
- Introduce native LLVM ORC compilation on Windows and ARM Linux.
