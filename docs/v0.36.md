# MParser v0.36 Scope

MParser v0.36 makes MATLAB namespace functions and structured imports
executable. It extends the v0.35 `+namespace` class graph without merging
function identity, class identity, and static member lookup into one heuristic.

## Major Capability

- A first function in `+pkg/name.m` is exported as `pkg.name`.
- Nested namespace functions such as `pkg.inner.bias` resolve from
  `+pkg/+inner/bias.m`.
- Later functions in a function file remain source-local and receive internal
  identities such as `pkg.name>helper`.
- Local functions in namespace class and script files receive owner-qualified
  internal identities, preventing two files from sharing an accidental helper.
- Internal helper identities are callable by their owning source but are not
  exposed by the `CompiledModule` public function catalog.
- `import` and each import item have dedicated syntax nodes and compile-time HIR
  nodes; they emit no runtime bytecode.
- One statement can import multiple whitespace-separated targets.
- Explicit imports support namespace functions, classes, and static methods.
- Wildcard imports support namespace functions, classes, nested namespaces, and
  static methods when a referenced short name resolves uniquely.
- Imports apply to the complete containing script or function scope, including
  statements textually before the `import` statement.
- Script imports do not leak into local functions, and function imports do not
  leak into sibling functions.
- Variables, parameters, and outputs win over imports. Explicit imports win
  over source-local functions; source-local functions win over wildcard
  imports; builtins are the final fallback.
- Conflicting explicit aliases, ambiguous wildcard matches, missing targets,
  and imported non-static methods produce compile diagnostics.
- A fully qualified namespace function wins over treating the same dotted name
  as a class/static-method chain.
- Namespace function lookup follows entry-root and repeated `--class-path`
  ordering; reversing roots reverses the selected same-named function.
- Pure namespace function calls execute in both the reference HIR interpreter
  and bytecode VM. Imported classes and static methods execute in the bytecode
  VM.
- Project and CLI version are `0.36.0`; CTest contains 32 tests.

## Identity Model

The physical namespace and primary function file determine the public identity:

```text
<root>/+mathops/scale.m
       function value = scale(input)
                         |
                         v
public identity = mathops.scale
```

A later helper in the same file is isolated from helpers in other files:

```text
mathops.scale>localDouble
mathops.triple>localDouble
```

The `>` form is an internal compiler identity, not MATLAB source syntax. Calls
inside each source retain the short spelling `localDouble(...)`, while semantic
binding selects the owner-specific symbol.

## Import Model

The parser preserves import structure rather than treating it as an ordinary
statement:

```matlab
value = offset(5);
import mathops.offset mathops.Tool mathops.Tool.tag
import mathops.*
```

Imports are collected before lowering the containing scope, so `offset` is
available to the preceding statement. Explicit aliases use the final name
segment. Wildcards are searched only when an unqualified reference is not
resolved by a stronger binding.

The current precedence is:

```text
variable / parameter / output
  -> explicit import
  -> same-source local function
  -> other lexical symbol
  -> wildcard import
  -> builtin
```

Static methods participate only when their declaration has an enabled `Static`
attribute. An instance method cannot be imported as a free function.

## MATLAB Alignment

MATLAB namespace folders may contain classes, functions, and inner namespaces.
The parent of the top-level `+namespace` folder belongs on the path. MATLAB
imports have function or script scope and are processed before execution;
explicit imports have stronger precedence than wildcard imports. MParser v0.36
implements that statically knowable subset:

- <https://www.mathworks.com/help/matlab/matlab_oop/namespaces.html>
- <https://www.mathworks.com/help/matlab/ref/import.html>
- <https://www.mathworks.com/help/matlab/matlab_prog/function-precedence-order.html>
- <https://www.mathworks.com/help/matlab/matlab_oop/importing-classes.html>

## Example

Run the complete demo with:

```powershell
build\mparser.exe --run-bytecode `
  --class-path=samples\namespace_functions `
  samples\namespace_functions\app\run_demo.m
```

Expected values:

```text
class_value = 7
explicit_value = 15
nested_value = 102
qualified_value = 9
static_value = 42
wildcard_static_value = 43
wildcard_value = 9
```

Inspect the loaded source graph and public function catalog with:

```powershell
build\mparser.exe --module-info `
  --class-path=samples\namespace_functions `
  samples\namespace_functions\app\run_demo.m
```

The module contains six sources and four public namespace functions:
`mathops.scale`, `mathops.offset`, `mathops.triple`, and
`mathops.inner.bias`. The two `localDouble` implementations remain internal.

Run only the function subset through the reference HIR interpreter with:

```powershell
build\mparser.exe --run `
  --class-path=samples\namespace_functions `
  samples\namespace_functions\app\run_function_demo.m
```

## Diagnostics And Regression Coverage

- Multiple import items and `.*` retain structured syntax.
- Qualified and imported functions execute through the filesystem source graph.
- Explicit import precedence and nested function scope isolation are tested.
- Two wildcard namespaces exporting the same short name are ambiguous.
- Missing targets and imported instance methods are rejected.
- Two files with the same helper spelling retain independent identities.
- Reversing namespace roots verifies deterministic path precedence.
- Qualified namespace classes and static methods remain covered in the same
  demo, while all v0.35 class tests remain in the full suite.

## Current Limitations

- Ordinary cross-file function discovery outside `+namespace` folders is not
  implemented. Namespace functions must be qualified or imported.
- `private` folders, `@class` method folders, methods in separate files, and
  enumeration members are not loaded.
- Wildcard imports are resolved lazily from referenced names. An unused invalid
  wildcard prefix does not currently produce a diagnostic or trigger a folder
  scan.
- Source loading conservatively collects imports across a file to discover
  dependencies; semantic visibility is still scoped per script or function, so
  extra candidate files may be parsed without leaking bindings.
- Assignment targets are declared as statements lower. A variable assigned
  later in a scope is not yet predeclared early enough to shadow an import at a
  preceding use as MATLAB's full function-wide variable analysis would.
- The loader parses source during dependency inspection and again during module
  compilation. Persistent metadata, file hashes, invalidation, and compiled
  module caches remain future work.
- A namespace folder itself should not be supplied as `--class-path`; supply its
  parent root.
- The reference interpreter executes pure namespace functions but not class
  objects. Use `--run-bytecode` for imported constructors and static methods.
- Native machine-code JIT remains future work. Current specialization uses
  portable typed regions with bytecode fallback.
