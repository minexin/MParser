# MParser v0.37 Scope

MParser v0.37 makes ordinary external `.m` function files and caller-scoped
`private` functions executable. It extends the namespace graph from v0.36 with
stable per-caller bindings instead of treating one filename as one global
function identity.

## Major Capability

- A simple call such as `work(x)` can discover `work.m` beside the entry file
  or in a repeated `--path` root.
- The entry file directory wins over search-path roots, and the first matching
  search-path root wins among path candidates.
- A function or script can call a function in the immediate `private` folder
  of its parent directory.
- Private functions are visible only to callers in that parent directory.
- Two libraries can each own `private/adjust.m`; caller-specific binding edges
  keep both implementations independent in one compiled module.
- A local function in the caller still wins over its private helper.
- Explicit imports, source-local functions, and wildcard imports retain their
  stronger semantic precedence over ordinary external bindings.
- Dependency-loaded path functions receive internal identities such as
  `$path0>work`; private functions receive identities such as
  `$private1>adjust`.
- Internal path/private identities are executable but omitted from the public
  `CompiledModule` entry catalog.
- Entry-source top-level functions retain the existing public module-entry
  behavior for embedding compatibility.
- `SourceUnit` records the primary internal identity and every caller's
  alias-to-target binding. `--module-info` prints this graph.
- External functions are recursively inspected, so their own ordinary,
  private, namespace, and class dependencies can enter the same source graph.
- Both the reference HIR interpreter and bytecode VM execute the supported
  pure-function subset.
- `--path=DIR` is the general repeated source-path option;
  `--class-path=DIR` remains a compatibility alias.
- Project and CLI version are `0.37.0`; CTest contains 35 tests.

## Lookup And Identity Model

For the currently supported simple parenthesized call form, final semantic
resolution uses this deterministic order:

```text
variable / parameter / output
  -> explicit import
  -> same-source local function
  -> other lexical symbol
  -> wildcard import
  -> caller's eligible private/<name>.m
  -> entry directory/<name>.m
  -> each --path root/<name>.m in order
  -> builtin
```

The loader may conservatively add an external candidate before semantic
analysis knows whether a variable or stronger import shadows it. Filesystem
search selects one external binding edge first; semantic name resolution then
decides whether that edge is reached at all.

Physical files do not become globally callable by short name. Instead, each
caller records the selected edge:

```text
first_library/run_first.m  bind adjust -> $private0>adjust
second_library/run_second.m bind adjust -> $private1>adjust
app/run_demo.m              bind adjust -> $path2>adjust
```

The `$path` and `$private` spellings are compiler identities, not MATLAB source
syntax. They survive semantic HIR and bytecode lowering so runtime lookup does
not repeat filesystem search or accidentally change precedence.

## MATLAB Alignment

MATLAB gives a caller access to functions in the immediate `private` subfolder
of its parent, gives private functions precedence over ordinary path functions,
and searches the current folder before the rest of the search path. MParser
v0.37 implements the statically discoverable `.m` source subset of those rules:

- <https://www.mathworks.com/help/matlab/matlab_prog/private-functions.html>
- <https://www.mathworks.com/help/matlab/matlab_prog/function-precedence-order.html>
- <https://www.mathworks.com/help/matlab/matlab_env/files-and-folders-that-matlab-accesses.html>
- <https://www.mathworks.com/help/matlab/search-path.html>

In the deterministic CLI model, "current directory" means the entry source
file's parent directory rather than the process working directory.

## Example

Run current-directory, ordered path, and private function lookup through the
bytecode VM:

```powershell
build\mparser.exe --run-bytecode `
  --path=samples\function_paths\first_library `
  --path=samples\function_paths\second_library `
  --path=samples\function_paths\global_library `
  samples\function_paths\app\run_demo.m
```

Expected values:

```text
current_value = 2
first_value = 11
local_value = 31
outside_value = 101
second_value = 21
```

The same graph executes through the HIR interpreter:

```powershell
build\mparser.exe --run `
  --path=samples\function_paths\first_library `
  --path=samples\function_paths\second_library `
  --path=samples\function_paths\global_library `
  samples\function_paths\app\run_demo.m
```

Inspect internal identities and caller edges with `--module-info` in place of
the runtime mode.

## Diagnostics And Regression Coverage

- Entry-directory lookup beats a same-named function on the search path.
- The first repeated path wins, and reversing the roots reverses the result.
- Two private helpers with the same filename execute independently.
- A same-source local function wins over a private helper.
- A caller outside the private parent falls back to the global path function.
- A wildcard namespace import wins over an ordinary path binding.
- Dependency-loaded internal identities do not leak into the public module
  function catalog.
- Existing entry files with multiple public top-level functions retain their
  module catalog and named-entry behavior.
- Namespace function, package class, and `--class-path` compatibility tests
  remain in the full suite.

## Current Limitations

- Ordinary discovery currently starts from simple parenthesized
  `CallOrIndexExpr` names. Command-form calls and function-handle references do
  not yet add source dependencies.
- Only valid primary `.m` function files whose first function declaration
  matches the requested filename are accepted.
- MATLAB's richer `.mlx`, `.p`, MEX, and built-in precedence is not yet modeled.
- `@class` method folders, methods in separate files, and enumeration members
  are not loaded.
- The source graph is conservative. A candidate may be parsed even when later
  semantic analysis proves that a variable, local function, or import wins.
- The loader parses source during dependency inspection and again during module
  compilation. Persistent metadata, file hashes, invalidation, and compiled
  module caches remain future work.
- The reference interpreter executes pure external functions but not class
  objects. Use `--run-bytecode` for constructors and object dispatch.
- Native machine-code JIT remains future work. Current specialization uses
  portable typed regions with bytecode fallback.
