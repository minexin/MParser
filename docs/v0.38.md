# MParser v0.38 Scope

MParser v0.38 makes modern `classdef` classes organized across MATLAB
`@ClassName` folders executable. Separate method files are normalized back into
the existing class syntax tree, so access control, inheritance, dispatch, and
bytecode execution do not depend on a second class runtime.

## Major Capability

- A class definition can be discovered at `@Counter/Counter.m` when the parent
  folder is on `--path`.
- Class folders can be nested inside namespaces, including forms such as
  `+pkg/+inner/@Counter/Counter.m`.
- Every valid sibling `.m` function file is collected in deterministic filename
  order and tagged with the canonical declaring class.
- `SourceUnit::classMethodOwner` preserves ownership without exposing method
  files as global functions.
- `--module-info` prints `method-of=<qualified-class>` for each method source.
- A separate implementation replaces a matching classdef method prototype only
  when its input/output signature agrees.
- Method-block attributes such as `Static`, `Access`, `Abstract`, and `Sealed`
  are retained when the prototype is replaced.
- A method file without a classdef prototype becomes a public, non-static
  method with default attributes.
- Instance, static, and private separate methods execute through the bytecode
  VM and use the existing class access checks.
- Local functions later in a method file receive owner-qualified internal
  identities and remain callable only from their source.
- Qualified/internal function labels retain semantic parameter bindings, while
  static method parameters no longer receive an instance-receiver type hint.
- Separate methods participate in inheritance, overrides, and virtual dispatch.
- Repeated search roots retain first-root class precedence.
- Constructors remain inline in the classdef file, as MATLAB requires.
- Signature mismatches, duplicate inline/separate implementations, malformed
  primary functions, separate constructors, and missing class owners produce
  compile diagnostics tied to the method file.
- Project and CLI version are `0.38.0`; CTest contains 38 tests.

## Source Graph Model

For a namespace class, one physical folder becomes several source units:

```text
<root>/+folderpkg/@Counter/Counter.m  owner: folderpkg.Counter definition
<root>/+folderpkg/@Counter/scale.m    owner: folderpkg.Counter method
<root>/+folderpkg/@Counter/twice.m    owner: folderpkg.Counter method
```

The loader first resolves the class by normal path order. Once a class-folder
definition is selected, it scans only that selected folder, ignores nested
directories, excludes the class definition file, and sorts sibling `.m` files
before assigning source IDs. Competing class folders on later roots never enter
the module.

Method source ownership is explicit metadata. It is not encoded as a public
function name and does not add a `CompiledModule` entry. This keeps class method
dispatch separate from the ordinary/path/private function bindings introduced
in v0.37.

## Syntax Merge Model

The primary function from each method source is attached to the canonical class
before semantic analysis:

```matlab
classdef Counter
    methods (Static)
        result = twice(value)
    end
end
```

```matlab
% @Counter/twice.m
function result = twice(value)
    result = value * 2;
end
```

The prototype supplies the method attributes, while the implementation supplies
the executable body and source span. Both signatures must have the same named
outputs, parameters, `varargin`, and `varargout` shape. If no prototype exists,
the merger creates or reuses an attribute-free methods block.

A later local function in `scale.m` receives an identity such as:

```text
folderpkg.Counter.scale>localMultiply
```

The `>` spelling is compiler metadata, not MATLAB source syntax. It prevents
same-named helpers in different method files from colliding.

## MATLAB Alignment

MATLAB class folders begin with `@`, contain the same-named classdef file, and
may contain methods in separate function files. The class folder's parent is
placed on the path. Declarations are optional for ordinary methods but required
when method attributes must be specified. Constructors and dot-named property
access methods must remain in the classdef file. MParser v0.38 implements the
`.m` source subset of these rules:

- <https://www.mathworks.com/help/matlab/matlab_oop/methods-in-separate-files.html>
- <https://www.mathworks.com/help/matlab/matlab_oop/organizing-classes-in-folders.html>
- <https://www.mathworks.com/help/matlab/ref/classdef.html>

## Example

Run the namespace class-folder demo with:

```powershell
build\mparser.exe --run-bytecode `
  --path=samples\class_folders\lib `
  samples\class_folders\app\run_demo.m
```

Expected values:

```text
offset_value = 12
revealed = 107
scaled = 21
static_value = 12
```

The demo includes a private separate method, a static separate method, an
undeclared default-public method, and a method-local helper function.

Inspect the seven-file graph with:

```powershell
build\mparser.exe --module-info `
  --path=samples\class_folders\lib `
  samples\class_folders\app\run_demo.m
```

Five method sources report `method-of=folderpkg.Counter` and remain absent from
the public function catalog.

## Diagnostics And Regression Coverage

- Namespace and non-namespace class folders are discovered through ordered
  search roots.
- Reversing two roots reverses the selected same-named class implementation.
- Instance, static, private, unlisted, and method-local helper execution is
  validated in one graph.
- Calling a private separate method externally is denied.
- Separate overrides preserve direct and inherited virtual dispatch.
- Prototype/implementation signature mismatches are rejected.
- A method file whose primary function differs from its filename is rejected.
- An inline body plus a same-named separate body is rejected as a duplicate.
- Existing direct-file classes, namespace classes, ordinary/private functions,
  namespace functions, and `--class-path` compatibility remain in the full
  suite.

## Current Limitations

- Only top-level `.m` function files with valid simple MATLAB names are scanned.
  `.mlx`, `.p`, and MEX method files are not loaded.
- Constructor and dot-named property accessor implementations must remain in
  the classdef file. This is also the MATLAB rule.
- Signature validation currently requires the same output and parameter names,
  not only equivalent arity.
- Functions in an `@Class/private` folder can be discovered through the v0.37
  private-function path, but class-privileged private-member access from those
  helper functions is not yet modeled.
- The reference HIR interpreter does not execute class objects. Class-folder
  demos use `--run-bytecode`.
- The loader still parses files during dependency inspection and again during
  compilation. Persistent metadata, fingerprints, and compiled module caches
  remain future work.
- Native machine-code JIT remains future work. Current specialization uses
  portable typed regions with bytecode fallback.
