# MParser v0.41 Scope

MParser v0.41 makes first-class function handles and MATLAB class events
executable across the frontend, bytecode VM, multi-file source graph, and CLI.
The milestone connects syntax that was previously only preserved to concrete
callback execution, access checks, event data, and listener lifetime.

## Major Capability

- `events` declarations split top-level comma-separated names, accept `...`
  continuation, and copy block attributes to every event.
- Event declarations have distinct `Event` syntax/HIR nodes, symbols, and
  bindings instead of being represented as generic class-member text.
- Event/member collision checks are independent of class-block source order.
- Event tables inherit through the resolved class hierarchy and diagnose
  redeclaration, ambiguous multiple inheritance, missing bases, and cycles.
- Only handle classes may declare events.
- `ListenAccess`, `NotifyAccess`, and `Hidden` use the existing public,
  protected, private, and selective-class access-policy machinery.
- `events(obj)` and `events('Class')` return inherited, non-hidden events with
  public `ListenAccess` in declaration order.
- Anonymous function handles retain parameter names, a bytecode body range,
  lexical class access, and a value snapshot of their defining frame.
- Named handles resolve builtins, local/path/package functions, static methods,
  and bound object methods. Private method handles can be created only from an
  authorized lexical class context.
- Function handles are directly callable with `handle(arguments)` and are
  recognized by `class`, `isa`, and runtime equality.
- Named callback handles add ordinary and package function files to the source
  dependency graph.
- `addlistener(source,event,callback)` creates a source-coupled listener.
- `listener(source,event,callback)` creates an uncoupled listener whose result
  must remain referenced.
- `notify(source,event)` invokes matching callbacks synchronously with source
  and default `event.EventData` arguments.
- `notify(source,event,data)` accepts user classes derived from
  `event.EventData`; MParser assigns their `Source` and `EventName` fields.
- Listener `Callback`, `Enabled`, and `Recursive` properties are readable and
  writable. Recursive delivery is suppressed by default and enabled per
  listener.
- `delete(listener)` disables future delivery, and `isvalid(listener)` reports
  listener validity.
- Handle-object equality now compares shared object identity. This also avoids
  recursive comparison through source/listener reference cycles.
- Project and CLI version are `0.41.0`; CTest contains 51 tests.

## Function-Handle Model

The bytecode instruction that creates an anonymous handle skips over its body
during ordinary execution and stores the body as a callable region:

```text
MakeFunctionHandle(parameters, body=[entry,end), lexicalClass)
  -> captured frame snapshot
  -> opaque VM-local function_handle value
```

Calling the value creates an isolated frame from the captured snapshot, binds
the supplied parameters, and executes only that body range. Named handles keep
a resolved callable descriptor instead of reparsing their textual spelling.
Bound method handles also retain the receiver object, so handle receivers keep
their shared identity while value receivers retain their copied value.

Example:

```matlab
factor = 3;
transform = @(value) value * factor;
factor = 10;
result = transform(4);  % result = 12

callback = @signals.onPulse;
```

## Event And Listener Model

Every resolved class owns an ordered event table containing the declaring
class, access policies, and hidden flag. Listener runtime state is separate:

```text
event.listener
  -> source identity + event name
  -> callback function_handle
  -> Enabled + Recursive + validity
  -> coupled or uncoupled lifetime
```

`addlistener` stores a listener reference on the source object. The callback
therefore remains active even when the call result is discarded. `listener`
keeps only weak runtime registration; if its returned handle is not retained,
the registration expires. Explicit deletion marks either form invalid.

`notify` first snapshots matching listener IDs. It then checks validity,
`Enabled`, and recursive state before making a normal function-handle call with
exactly two arguments. The default data object contains `Source` and
`EventName`; custom data preserves its user properties and receives those same
built-in fields.

## Example

Run the package callback demo with:

```powershell
build\mparser.exe --run-bytecode `
  --class-path=samples\event_listeners\lib `
  samples\event_listeners\app\run_demo.m
```

The script creates anonymous and package-function callbacks, demonstrates
closure capture, disables and deletes listeners, invokes a private callback
closure, and queries visible events.

Expected highlights:

```text
callbacks_after_first = 2
callbacks_while_disabled = 3
callbacks_after_delete = 4
callbacks_after_private = 15
closure_value = 12
event_names = {"ObjectBeingDestroyed", "Tick"}
listener_valid = 1
summary = 40
```

Inspect source loading and event identities with:

```powershell
build\mparser.exe --module-info `
  --class-path=samples\event_listeners\lib `
  samples\event_listeners\app\run_demo.m

build\mparser.exe --hir `
  --class-path=samples\event_listeners\lib `
  samples\event_listeners\app\run_demo.m
```

## Regression Coverage

- Same-line, continued, attributed, hidden, and inherited event declarations.
- Event syntax, symbol, binding, HIR, bytecode, module-info, and CLI output.
- Handle-only declarations and same-class name conflicts in either block order.
- Public and private listen/notify access from allowed and denied contexts.
- Anonymous capture-by-value and lexical private access.
- Builtin, local, package, static-method, bound-method, and private-method
  handles.
- Function-handle `class`, `isa`, invocation, and object-bound behavior.
- Default event data plus custom `event.EventData` properties, `Source`, and
  `EventName`.
- Callback replacement state, enable/disable, deletion, validity, and handle
  identity.
- Default recursion suppression and explicit recursive delivery.
- Retained and discarded coupled/uncoupled listener lifetimes.
- Package callback discovery through a named function handle.

## Current Limitations

- Function handles and events execute only in the bytecode VM. The reference
  HIR interpreter still reports these runtime operations as unsupported.
- Handles are VM-local values. They cannot be serialized, transferred between
  runs, or retained across separate `BytecodeVm::run` calls.
- `str2func`, `func2str`, `functions`, `feval`, nested functions, workspace
  mutation from closures, and dynamically resolved textual handles are not yet
  implemented.
- Event sources and listeners are scalar. Object arrays, cell arrays of mixed
  sources, listener arrays, and vectorized notification are not represented.
- Only function-form `addlistener`, `listener`, and `notify` are implemented;
  `event.listener(...)` constructor spelling and object method-form calls are
  not yet lowered as built-in handle methods.
- Listener `Source` and `EventName` are readable but not yet reassignable.
- Property events (`PreSet`, `PostSet`, `PreGet`, and `PostGet`),
  `event.proplistener`, `event.hasListener`, and observable-property metadata
  remain future work.
- The v0.41 boundary did not include the implicit `ObjectBeingDestroyed` event
  or general handle-object deletion. Current v0.68 execution now provides both,
  so the checked-in sample also lists the inherited destruction event.
- Custom event-data objects execute but `ConstructOnLoad`, save/load, and
  serialization contracts are not implemented.
- Callback execution is synchronous and stops on the first runtime diagnostic.
  Callback ordering is deterministic internally but is not a compatibility
  guarantee.
- Native machine-code JIT remains future work. Existing optimization still
  uses profiled bytecode, typed regions, guards, fallback, and retraining.

## Next Iteration

- Add N-dimensional numeric and Cell array metadata, indexing, construction,
  and shape-preserving assignment as the next major runtime capability.
- Reuse that array representation for object and listener arrays instead of
  adding event-specific collection types.
- Keep event callbacks on the ordinary bytecode/function-call path so future
  native lowering preserves one semantic implementation and deoptimization
  boundary.
