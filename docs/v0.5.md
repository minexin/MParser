# MParser v0.5 Scope

MParser v0.5 adds bytecode VM profiling as the first concrete JIT-enabling
runtime feature. The VM now records which functions, loops, instructions, and
call/index sites actually run, then marks hot loops with a fixed threshold.
This gives later optimizing IR and JIT work a stable input instead of guessing
from syntax alone.

## Added Since v0.4

- `BytecodeVmProfile` in the VM result, with instruction, function, loop, and
  call/index-site profiles.
- Per-PC instruction execution counts.
- Per-function call counts and executed-instruction counts, including same-file
  local functions.
- For-loop profile counters: entries, iterations, backedges, completions,
  breaks, continues, and hot-loop marking.
- Generic backward-jump loop backedge counting for lowered loop shapes such as
  `while`.
- `CallOrIndex` site profiling for local function, builtin, and indexing
  dispatch points.
- CLI option `--profile-bytecode` that executes bytecode and prints a profile
  summary after variables.
- `samples/bytecode_profile_demo.m` as the v0.5 profiling demo.
- Project version and CLI version bumped to `0.5.0`.

## Bytecode VM Supported Subset

The v0.5 VM can execute the v0.4 numeric/string subset and additionally report
execution profile data for:

- Top-level script execution as `<script>`.
- Entry functions and same-file local functions.
- Hot `for` loops and lowered backward-jump loops.
- Stable call/index sites, including repeated local function calls inside loops.

This does not compile code yet. The value of v0.5 is that hot regions are now
observable and testable, which is the required input for guarded specialization.

## VM Gaps

The VM still intentionally reports diagnostics for features that need richer IR
or runtime metadata:

- `switch` and `try` control execution.
- Automatic array growth during indexed assignment.
- Non-scalar right-hand-side indexed assignment shape matching.
- Dynamic function handles and unresolved function dispatch.
- Classes, object dispatch, member assignment, cells, brace indexing, structs,
  tables, sparse arrays, and complex values.
- Actual JIT compilation, type/shape guards, optimized IR generation, and
  deoptimization.

These remain covered, where implemented, by the HIR interpreter.

## Validation

Validated on Windows with MSVC Build Tools:

```powershell
cmake -S . -B build
cmake --build build
ctest --test-dir build --output-on-failure
build\mparser.exe --version
build\mparser.exe --profile-bytecode samples\bytecode_profile_demo.m
build\mparser.exe --run-bytecode samples\bytecode_indexing_demo.m
build\mparser.exe --run-bytecode samples\bytecode_call_demo.m
build\mparser.exe --run-bytecode samples\bytecode_control_demo.m
```

Expected version output:

```text
MParser 0.5.0
```

The v0.5 profiling demo should execute through the bytecode VM and report one
hot loop:

```powershell
build\mparser.exe --profile-bytecode samples\bytecode_profile_demo.m
```

Expected high-level output:

```text
Variables:
  i = 12
  j = 3
  y = 668
Bytecode profile:
  instructions executed: 181
  hot loop threshold: 10
  functions:
    bytecode_profile_demo: calls=1
    kernel: calls=12
  loops:
    variable=i ... iterations=12 ... hot=yes
    variable=j ... iterations=3 ... hot=no
  call/index sites:
    kind=function, target=kernel ... executions=12
```

## Next Iterations

The next high-value work is to turn profile data into optimization decisions:

- Add typed numeric runtime helpers shared by the HIR interpreter and bytecode
  VM so optimized regions use one value model.
- Add type and shape observations to call/index and loop profiles.
- Build a small optimizing IR for straight-line numeric regions inside hot
  loops.
- Add guard failures and a deoptimization path back to the bytecode VM.
- Extend bytecode control execution to `switch` and `try` so more scripts can
  reach the profiling/JIT pipeline.
