# MParser v0.50 Scope

MParser v0.50 extends the portable typed scalar kernel across complete,
well-nested `for` loop trees. The outer region now owns nested range planning,
iteration, scalar operations, metrics, and transactional commit instead of
entering a separate inner region once per outer iteration.

## Milestone Contract

- Project and CLI version are `0.50.0`.
- Region analysis validates structured nested `ForBegin`/`ForNext` pairs and
  records nested-loop count and maximum depth.
- The typed IR marks an enclosing loop tree with `specialize-loop-nest`.
- Kernel preparation lowers nested headers and latches to structured loop
  operations while retaining register-based scalar expressions.
- Two- and three-term colon ranges use one runtime planner in the HIR
  interpreter, bytecode VM, and typed executor.
- Positive and negative steps, scalar ranges, and empty ranges have identical
  behavior across those runtimes; a zero step is rejected.
- Empty inner loops do not create or overwrite body variables, and an existing
  loop variable is preserved when no iteration executes.
- A leaf-loop span executes without one recursive dispatcher call per inner
  iteration.
- Typed reports distinguish outer iterations, nested iterations, represented
  source instructions, and dispatched kernel instructions.
- CTest contains 74 tests, including direct two-level, three-level, empty-loop,
  range-semantics, typed-IR, region-contract, and CLI regressions.

## Structured Loop Region

The existing bytecode-region contract remains the optimization boundary:

```text
profiled bytecode candidate
  -> validate one closed structured loop tree
  -> emit typed guards and specialize-loop-nest
  -> bind scalar slots and expression registers
  -> lower nested ranges and loop boundaries
  -> execute structured kernel spans
  -> commit only dynamically written slots
```

Nested loops are accepted only when every header has its expected latch and
all boundaries are contained by the enclosing region. General branches,
`break`, `continue`, mutation, dynamic calls, and unsupported operations still
reject the complete region before execution. This keeps the contract suitable
for later native lowering without weakening fallback correctness.

The compiler snapshots definite initialization at each nested header. Since a
range may be empty, names first written only inside the body are not considered
initialized after the loop. Runtime commit independently tracks which slots
were actually written, preserving existing variables across zero-trip loops.

## Shared Colon Semantics

MATLAB's left-associated `start:step:stop` syntax previously reached bytecode
as nested binary operations. v0.50 recognizes the complete colon tree and
emits one range instruction with two or three operands. `runtime_range` then
plans and materializes the same range for all execution tiers.

Examples covered by regression tests include:

```matlab
1:2:5    % 1, 3, 5
5:-2:1   % 5, 3, 1
5:1      % empty
```

## Execution Metrics

`samples/nested_typed_loop_demo.m` covers a two-level stepped loop, a
descending loop, and an empty loop. It produces `summary = 711`. The first
region enters once, executes 12 outer iterations and 36 nested iterations,
represents 312 source instructions, and dispatches 84 kernel instructions.

The original `samples/timing_loop_demo.m` now crosses one optimized outer
boundary:

```text
attempts=1, executions=1, fallbacks=0
iterations=1000, nestedIterations=1000000
typedInstructions=15004000, kernelInstructions=4001000
```

The inner candidate remains visible for diagnostics but has zero attempts
because the enclosing region owns its execution.

## Performance Observation

The development machine is an Intel Core i5-1135G7 with 4 cores and 8 logical
processors. Five consecutive runs of the final Release binary reported these
script `toc` values:

| Run | v0.50 `a` |
| --- | ---: |
| 1 | 0.0837009 s |
| 2 | 0.0949460 s |
| 3 | 0.0813982 s |
| 4 | 0.0827688 s |
| 5 | 0.0806068 s |
| median | 0.0827688 s |

A run immediately after build and test activity reached `0.104902` seconds,
showing how strongly this short measurement responds to mobile-CPU frequency
and system load. A single comparable v0.49 run was about `0.0786201` seconds;
that one sample is not a statistically sound basis for claiming either a
v0.50 speedup or regression. The raw final samples and median are retained
rather than selecting the best result.

The user reported about `0.02` seconds for MATLAB on an Intel Core i7-12700.
That result establishes a useful target scale, but it is not a strict runtime
ratio because the CPU and runtime environment differ. The concrete v0.50 gain
is one structured optimization boundary for the complete nest, not a proven
wall-time improvement. Closing the remaining gap requires native machine-code
lowering; this milestone still dispatches a portable C++ register kernel.

## Current Limitations

- The typed kernel is portable C++, not native machine code.
- Nested `if`, `while`, `switch`, `try`, `break`, `continue`, indexing,
  mutation, and general calls retain the baseline fallback boundary.
- Typed external inputs remain double scalars; arrays, complex values, integer
  classes, and dynamic dispatch are not specialized by this executor.
- Kernel preparation occurs on region entry and there is no persistent native
  code cache or loop-midpoint on-stack replacement.
- LLVM was not present in the current Windows toolchain, so no unverified
  compile-time LLVM switch is included in this milestone.

## Next Iteration

- Add an optional LLVM ORC backend for this structured typed-region contract,
  with the portable kernel retained on Windows and ARM Linux when LLVM is not
  configured.
- Preserve guards, zero-trip semantics, transactional commit, metrics, and
  bytecode fallback across native execution.
- Add native code caching and an executable capability probe before considering
  loop-midpoint on-stack replacement.
- Continue broader MATLAB runtime coverage after the native backend boundary is
  repeatable on both target platforms.
