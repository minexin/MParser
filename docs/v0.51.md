# MParser v0.51 Scope

MParser v0.51 adds the first executable native-code backend for the structured
scalar loop kernel introduced in v0.49-v0.50. Eligible `for` loop trees can now
run as machine code generated by SLJIT, with the existing portable kernel and
bytecode VM retained as correctness fallbacks.

## Milestone Contract

- Project and CLI version are `0.51.0`.
- Native JIT support is enabled by default and remains optional at build time.
- The repository vendors SLJIT at pinned revision
  `3907e69005ba6e30b225000f24aaef3632f88347`, accepts an existing checkout
  override, and records the Simplified BSD license in
  `THIRD_PARTY_NOTICES.md`.
- One backend-neutral `ScalarKernel` contract is shared by the portable and
  native executors.
- `--typed-backend=auto|portable|native` is propagated through direct typed,
  adaptive, module-runtime, and benchmark execution.
- The native backend handles complete supported nested loop trees, direct
  scalar operations, comparisons, logical results, and the existing pure math
  builtins.
- Generated code is cached process-wide by complete kernel identity and freed
  through SLJIT when the cache is destroyed.
- Native execution preserves guard checks, zero-trip behavior, colon-range
  diagnostics, transactional commit, output comparison, and bytecode resume.
- Reports expose selected backend, compile/cache counts, generated code size,
  platform name, and native fallback reason.
- Debug and Release CTest contain 76 tests. A separate native-disabled build
  verifies that `auto` continues through the portable kernel without SLJIT.

## Runtime Shape

```text
profiled bytecode candidate
  -> typed guards and closed-region validation
  -> backend-neutral structured scalar kernel
  -> auto
       -> SLJIT machine code -> process cache -> transactional commit
       -> portable register kernel when native entry is unavailable
  -> unchanged bytecode resume when the requested tier cannot execute
```

`auto` is the normal policy. It attempts the native backend and records why it
selected the portable path when native generation is unavailable or rejects a
kernel. `portable` bypasses SLJIT for deterministic same-binary comparisons.
`native` requires successful native entry; a compile or runtime failure leaves
the workspace unchanged so the VM can execute the original bytecode region.

The native call receives a compact context containing scalar slots, temporary
registers, written-slot flags, outer range values, and per-loop iteration
counters. The generated function owns loop control and scalar expression
execution. Only slots marked written after a successful return are copied back
to the VM workspace.

## Native Instruction Coverage

SLJIT instructions directly implement slot/register copy, unary plus/minus,
addition, subtraction, multiplication, division, absolute value, nested range
control, comparisons, and logical operations. Power and the pure unary
`acos`, `asin`, `atan`, `cos`, `exp`, `log`, `sin`, `sqrt`, and `tan` operations
use ABI-correct calls from generated code to the platform math runtime.

The cache key contains slot/register layout, every operation, operand storage,
literal values, destination, loop IDs, jump targets, and range form. A mutex
protects lookup and insertion; concurrent duplicate compilations converge on
one cached entry. Each execution still owns independent mutable slots and
registers, so cached code is reusable across adaptive invocations.

## Performance Observation

`samples/native_jit_benchmark.m` retains all eight `toc` samples in one
adaptive session. It uses the original nested `1000 x 1000` loop and receives
`runCount=0` as an initial persistent workspace value. The first invocation
profiles bytecode, the second enters the installed tier, and later invocations
reuse the same generated code.

On the Intel Core i5-1135G7 development machine, the final Release build
reported:

| Execution | Samples | Result |
| --- | ---: | ---: |
| Full-profile bytecode | 1 | `21.9175517 s` |
| Native tier, initial compile | 1 | `0.0303072 s` |
| Native tier, cache hits | 6 | median `0.0329642 s` |
| Native cache-hit range | 6 | `0.0227196-0.0479037 s` |
| Portable typed tier | 7 | median `0.1108442 s` |
| Portable typed range | 7 | `0.0654137-0.1218238 s` |

The cache-hit native median is about `3.36x` faster than the portable median
in this same-process comparison. Both backends produce
`finalValue = 834.32145639679`. A smaller structured-loop sample reports a
`406` byte native kernel and identifies the current backend as
`x86 64bit (little endian + unaligned)`.

The user-reported MATLAB result of about `0.02` seconds was measured on an
Intel Core i7-12700. It remains a useful target scale, but it is not a valid
cross-machine speed ratio. The v0.51 result does establish that the current
eligible loop now runs in the same tens-of-milliseconds order of magnitude.

## Build and Validation

The default build compiles the vendored SLJIT source without network access:

```powershell
cmake -S . -B build-release -G Ninja -DCMAKE_BUILD_TYPE=Release
cmake --build build-release -j 4
ctest --test-dir build-release --output-on-failure
build-release\mparser.exe --version
```

Use an existing checkout or omit the native backend with:

```powershell
cmake -S . -B build-local `
  -DMPARSER_SLJIT_SOURCE_DIR=C:\path\to\sljit
cmake -S . -B build-nojit -DMPARSER_ENABLE_NATIVE_JIT=OFF
```

Run the native/cache and same-machine comparison samples with:

```powershell
build-release\mparser.exe --run-adaptive-bytecode `
  --typed-backend=native --adaptive-runs=3 --adaptive-hot-loop=10 `
  samples\nested_typed_loop_demo.m

build-release\mparser.exe --run-adaptive-bytecode `
  --typed-backend=native --adaptive-runs=8 --adaptive-hot-loop=1 `
  --adaptive-persist-workspace --adaptive-workspace=runCount=0 `
  samples\native_jit_benchmark.m
```

Expected version:

```text
MParser 0.51.0
```

## Platform Status

The source uses only portable C++20 plus SLJIT's public C API. The vendored SLJIT
backend supports the required Windows x86-64 and Linux AArch64 machine-code
targets, and MParser does not contain x86 instruction encoding. Windows x86-64
has passed native execution, cache, fallback, Debug, Release, and native-off
tests in this milestone. Linux AArch64 still requires execution in the target
CI or hardware environment before it can be claimed as validated rather than
source-compatible.

## Current Limitations

- Native regions still specialize scalar double inputs. Arrays, complex
  values, integer classes, objects, Cells, and sparse values remain outside
  this executor.
- Branches, indexing, mutation, dynamic calls, `break`, `continue`, and
  exception regions retain the conservative bytecode boundary.
- Math builtins currently use calls into the platform math runtime instead of
  target-specific vector instructions.
- The code cache is process-local and currently has no size limit, eviction,
  serialization, or invalidation by compiler version.
- Promotion happens between adaptive invocations; loop-midpoint on-stack
  replacement is not implemented.
- Linux AArch64 execution is not available on the current Windows development
  machine and has not yet been measured.

## Next Iteration

- Add Linux AArch64 CI or hardware validation for native execution and fallback.
- Add bounded cache accounting and lifecycle policy before persistent caching.
- Broaden typed kernel values toward arrays and vectorizable elementwise loops.
- Keep the native backend interface suitable for an optional LLVM ORC backend
  when richer optimization passes justify that larger dependency.
