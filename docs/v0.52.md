# MParser v0.52 Scope

MParser v0.52 extends the typed scalar loop tier across structured
`if`/`elseif`/`else` statements. The region analyzer, portable kernel, and
SLJIT native backend now share one closed forward-branch contract, while
unsupported control flow continues through unchanged bytecode fallback.

## Milestone Contract

- Project and CLI version are `0.52.0`.
- The repository continues to vendor SLJIT revision
  `3907e69005ba6e30b225000f24aaef3632f88347`, its source, and its Simplified
  BSD license. Default configuration performs no dependency download.
- Closed scalar `for` loop trees may contain structured forward
  `if`/`elseif`/`else` branches at any supported loop depth.
- Region analysis rejects backward jumps, cross-loop-depth jumps,
  `break`, `continue`, `return`, and exception control flow.
- A path-sensitive definition analysis identifies values assigned on every
  incoming path and preserves possibly uninitialized values as guarded region
  inputs.
- The backend-neutral scalar kernel has explicit `Jump` and `JumpIfFalse`
  operations with patched, region-local instruction targets.
- The portable executor and SLJIT native emitter implement identical branch
  truth and target validation.
- Native branch kernels report path-accurate source and kernel instruction
  counts instead of estimating all arms from loop iteration totals.
- Generated branch kernels retain structural process-wide caching,
  transactional workspace commit, and bytecode fallback.
- Native-enabled Debug and Release CTest contain 78 tests, including portable
  result validation and native branch-cache CLI coverage.
- Cross-platform CI executes the full native-enabled suite on Windows x64 and
  Linux x64, then cross-compiles Linux AArch64 and runs focused native and
  portable runtime checks through QEMU.

## Region Analysis

The bytecode lowerer already represents MATLAB conditionals with
`JumpIfFalse` and forward `Jump` instructions. v0.52 admits those instructions
only when all of the following hold:

1. The target is after the source instruction.
2. The target stays inside the selected outer loop region.
3. Source and target have the same structured loop depth.
4. The branch enters and leaves with an empty statement stack boundary.

This accepts ordinary nested conditionals without accepting general control
flow. A `while` backedge, loop control statement, return, or jump across a
`for` boundary remains in the baseline VM.

The input analysis is a forward control-flow pass. Each program point stores
the intersection of definitions reaching it. A load absent from that
intersection becomes a region input. Consequently, a temporary assigned in
every `if`/`elseif`/`else` arm does not require an entry value, while a variable
assigned by an `if` without `else` remains an input when the following code can
observe its previous value.

## Kernel Execution

Kernel preparation records the scalar-kernel instruction index corresponding
to each bytecode PC, emits branch placeholders, and patches them after the
complete region is lowered. Targets must remain forward and inside the active
kernel span.

The portable executor updates its instruction cursor directly. The native
emitter creates SLJIT labels for kernel instruction boundaries, queues jumps
whose labels have not yet been emitted, and refuses to install code when any
target remains unresolved. Branches at the end of a nested or outer loop body
bind to the loop-span end label before loop control resumes.

Branch paths execute different instruction counts. Native branch kernels
therefore increment compact per-instruction counters in the execution context.
The resulting source-bytecode and scalar-kernel totals match the portable
executor for the same runtime values.

## Sample

Run the structured nested-loop sample with either backend:

```powershell
build\mparser.exe --run-typed-bytecode --typed-backend=portable `
  samples\branched_typed_loop_demo.m

build\mparser.exe --run-typed-bytecode --typed-backend=native `
  samples\branched_typed_loop_demo.m
```

Both executions produce:

```text
score = 23100
high = 182
middle = 238
summary = 23520
```

On the current Windows x86-64 Debug build, the sample reports 20 outer
iterations, 420 nested iterations, 9,781 source instructions, and 3,785 kernel
instructions for both backends. The native kernel is 1,262 bytes on this
toolchain; generated size is platform and build dependent.

## Build and Validation

The default build uses only the repository copy of SLJIT:

```powershell
cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Debug
cmake --build build -j 4
ctest --test-dir build --output-on-failure
build\mparser.exe --version
```

The native backend can still be omitted without removing portable typed
execution:

```powershell
cmake -S . -B build-nojit -G Ninja `
  -DMPARSER_ENABLE_NATIVE_JIT=OFF
cmake --build build-nojit -j 4
ctest --test-dir build-nojit --output-on-failure
```

Expected version:

```text
MParser 0.52.0
```

## Platform Status

The implementation uses portable C++20 and SLJIT public APIs. The bundled
source contains Windows x86-64 and Linux AArch64 backends and requires no
network access during configuration. Windows x86-64 has passed portable,
native, cache, fallback, Debug, native-disabled, and AddressSanitizer coverage
for this milestone.

The checked-in CI workflow adds three independent gates:

1. Windows x64 with MSVC builds SLJIT and executes the complete suite.
2. Linux x64 with GCC builds SLJIT and executes the complete suite.
3. A GNU Linux AArch64 cross-build compiles all native-JIT targets, executes the
   typed native-branch smoke under QEMU, and separately executes portable
   region tests and the branch sample from a native-disabled build.

The reusable toolchain file is
`cmake/toolchains/linux-aarch64.cmake`. QEMU validates AArch64 instruction and
ABI behavior in emulation; timing and final runtime qualification still require
real ARM64 Linux hardware.

The corresponding manual cross-build is:

```bash
cmake -S . -B build-arm64 -G Ninja \
  -DCMAKE_BUILD_TYPE=Release \
  -DCMAKE_TOOLCHAIN_FILE=cmake/toolchains/linux-aarch64.cmake \
  -DMPARSER_ENABLE_NATIVE_JIT=ON
cmake --build build-arm64 --parallel
```

## Current Limitations

- Typed regions still specialize scalar numeric entry values. Arrays, complex
  values, integer payloads, objects, Cells, and sparse values remain outside
  this executor.
- Only closed forward branches are accepted. `while`, `break`, `continue`,
  `return`, short-circuit control-flow regions, and exceptions remain in the
  bytecode VM.
- Indexing, mutation, dynamic calls, and user-function calls are not native
  scalar-kernel operations.
- Exact branch counters add instrumentation to native branch kernels. A later
  metrics policy may make that instrumentation optional for production runs.
- The process-local native code cache remains unbounded and is not serialized.
- Promotion still happens between adaptive invocations rather than by
  loop-midpoint on-stack replacement.
- Linux AArch64 native execution has not been measured on physical hardware in
  this Windows workspace.

## Next Iteration

- Add bounded native cache accounting and an explicit lifecycle policy.
- Run performance and long-duration native-JIT validation on physical Linux
  AArch64 hardware.
- Broaden typed values toward arrays and vectorizable elementwise loops.
- Keep richer backends behind the same scalar-kernel, guard, and fallback
  boundary.
