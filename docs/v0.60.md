# MParser v0.60 Scope

MParser v0.60 makes MATLAB name-value input arguments executable across the
frontend, reference interpreter, bytecode VM, reusable compiled modules, and
adaptive module runtime. It supports both modern `Name=value` call syntax and
legacy `"Name", value` pairs without changing the stable `arguments`-block or
`FunctionSignature` model introduced in v0.59.

## Milestone Contract

- Project and CLI version are `0.60.0`.
- Modern `Name=value` operands have dedicated syntax and HIR nodes and lower to
  `MakeNameValueArgument` bytecode instead of being confused with assignment.
- Exact field names and unambiguous prefixes are accepted. Unknown and
  ambiguous names fail before the function body runs.
- Name-value pairs may appear in any order. Repeating the same name is allowed;
  the last supplied value wins.
- Legacy string/value tails and modern wrappers share one runtime normalizer.
  A positional value cannot follow the first name-value argument.
- Optional text positionals are reinterpreted as the start of a name-value tail
  when the text resolves to a declared field and the preceding positional
  prefix is valid.
- Every name-value root is bound as a Struct. Supplied fields and defaults use
  the existing class conversion, dimension adaptation, and validator pipeline.
  A declaration without a default remains absent when omitted, so `isfield`
  can distinguish it.
- Fixed, repeating, `varargin`, and name-value inputs compose in one signature.
  `nargin` reports only the number of positional values supplied by the caller.
- Local/path/package functions, constructors, instance/static methods, named
  bytecode entries, `CompiledModule`, adaptive sessions, and
  `AdaptiveModuleRuntime` use the same binding contract.
- CLI named entries accept `--argument=Name=value`; module-runtime calls accept
  the same argument form after an entry-name colon.

## Semantic Rules

The semantic pass requires name-value fields to be globally unique across all
name-value structures in one function and rejects a field that collides with a
positional or repeating parameter. Defaults and validator arguments cannot
reference any name-value structure, preserving order-independent validation.
The existing ordering rule remains positional, then repeating, then
name-value.

Matching currently follows identifier case. This is an implementation boundary
of v0.60 rather than a claim about every MATLAB release or compatibility mode.

## Example

```matlab
[value, seen] = configure(2, Scale=4, Offset=3);

function [y, seen] = configure(x, options)
arguments
    x (1,1) double
    options.Scale (1,1) double {mustBePositive} = 3
    options.Offset (1,1) double = 1
end
y = x * options.Scale + options.Offset;
seen = nargin;
end
```

Run the checked-in modern/legacy/repeating demo with:

```powershell
build\mparser.exe --run samples\name_value_arguments_demo.m
build\mparser.exe --run-bytecode samples\name_value_arguments_demo.m
```

The demo reports `summary = 65`. A named entry can be invoked with:

```powershell
build\mparser.exe --run-bytecode --entry-function=configure `
  --argument=2 --argument=Scale=4 --outputs=2 `
  samples\name_value_arguments_demo.m
```

## Build Reliability

`CMakePresets.json` adds a Windows MSVC/Ninja preset, and
`cmake/configure-windows-msvc.cmd` switches the configure console to UTF-8
before using it. This preserves the localized `/showIncludes` dependency
prefix instead of storing mojibake in `rules.ninja`. Run the wrapper from a VS
Developer Shell. After any public runtime-header layout change, an older build
tree created without this setting should be rebuilt once with
`cmake --build <dir> --clean-first` before tests are trusted.

## Validation

`name_value_argument_smoke` uses explicit Release-build failures and covers
syntax/HIR/bytecode identity, modern and legacy calls, defaults, partial names,
ambiguous and unknown names, duplicate last-wins behavior, optional text
reinterpretation, repeating groups, multiple structures, omitted fields,
field mutation, validation failures, positional-only `nargin`, static methods,
compiled-module preflight, and adaptive invocation. Three CLI tests cover both
baseline runtimes and named-entry `--argument=Name=value` parsing.

The local release gate is the complete CTest suite. Windows x64, Linux x64,
and Linux AArch64/QEMU GitHub jobs remain the remote release gate.

## Remaining Boundary

Output `arguments` blocks remain parsed, lowered, and semantically checked but
are not yet validated after function execution. That is the primary input/output
contract gap for the next milestone.
