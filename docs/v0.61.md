# MParser v0.61 Scope

MParser v0.61 makes MATLAB output `arguments` blocks executable across the HIR
interpreter, bytecode VM, compiled modules, adaptive runtime, and bytecode class
calls. Fixed and repeating outputs now use one shared post-execution contract
instead of remaining frontend-only metadata.

## Milestone Contract

- Project and CLI version are `0.61.0`.
- `FunctionSignature` retains an optional named repeating output separately
  from the fixed output prefix. A final named output and `varargout` therefore
  use the same variable-result calling convention.
- Assigned fixed outputs are class-converted, shape-adapted, and validated
  after the function body. Converted values are written back before callers or
  entry-result snapshots observe them.
- Missing, unassigned outputs are skipped by output validation, matching the
  MATLAB rule that validation applies when an output has a value at return.
- A repeating output is initialized as a one-dimensional Cell. Each assigned
  element is validated independently and then expands into one output slot.
- A function may combine a fixed output prefix with one final repeating output.
  Expanded requested output counts pass compiled-module preflight and remain
  visible through `nargout`.
- Validation failures identify the callable, declaration, and repeating
  occurrence, for example `repeat.values{2}`.
- Local/path/package functions, named entries, reusable modules, adaptive
  sessions, constructors, instance methods, and static methods use the same
  output contract.
- Public named-entry output slots are stable: a repeating declaration named
  `values` produces `values1`, `values2`, and so on; existing `varargout1`
  naming remains unchanged.

## Semantic Rules

An output declaration cannot define a default or use name-value field syntax.
A repeating output block contains exactly one declaration, appears after fixed
output blocks, and names the final output in the function signature.
`varargout` remains valid only as the sole declaration in a repeating output
block. An output validator cannot reference an earlier output.

The runtime validates every assigned fixed output and every assigned element of
the repeating output Cell, even when the caller requests only a shorter result
prefix. This keeps the function's declared return contract independent of the
particular assignment form used by its caller.

## Example

```matlab
[head,first,second] = partition(5);

function [head,tail] = partition(seed)
arguments (Output)
    head (1,1) double
end
arguments (Output,Repeating)
    tail (1,1) double {mustBePositive}
end
head = seed;
tail{1} = seed + 1;
tail{2} = seed + 2;
end
```

Run the checked-in fixed and repeating output demo with:

```powershell
build\mparser.exe --run samples\output_arguments_demo.m
build\mparser.exe --run-bytecode samples\output_arguments_demo.m
build\mparser.exe --run-bytecode --entry-function=repeatedOutputs `
  --argument=4 --outputs=2 samples\output_arguments_demo.m
```

The full script reports `summary = 34`; the named entry reports
`values1 = 4` and `values2 = 5`.

## Validation

`output_argument_smoke` uses explicit Release-build failures and covers fixed
class/shape conversion, fixed validator rejection, named repeating output
metadata and expansion, occurrence diagnostics, Cell storage enforcement,
fixed-plus-repeating composition, validated `varargout`, compiled-module
preflight and invocation, adaptive invocation, constructors, static methods,
class constraints, and semantic ordering/reference restrictions. The older
repeating-argument test now verifies successful output execution. Three CLI
tests cover both baseline runtimes and named-entry output expansion.

The complete CTest suite is the local release gate. Windows x64, Linux x64, and
Linux AArch64/QEMU GitHub jobs remain the remote release gate.

## Remaining Boundary

User-defined validation functions are still limited by the executable
validator subset. Property-derived name-value declarations such as
`options.?ClassName`, richer output object/array values, and a fully unified
call-frame object remain candidates for the next compatibility iterations.
