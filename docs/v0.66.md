# MParser v0.66 Scope

MParser v0.66 makes observable class properties executable in the bytecode VM.
It adds MATLAB-style property event listeners for declared and per-instance
dynamic properties while retaining the portable C++20 runtime contract on
Windows x64, Linux x64, and Linux AArch64.

## Milestone Contract

- Project and CLI version are `0.66.0`.
- A declared property emits get events only when `GetObservable` is true and
  set events only when `SetObservable` is true.
- A live `matlab.metadata.DynamicProperty` uses its mutable `GetObservable`
  and `SetObservable` attributes in the same way.
- Supported event names are `PreGet`, `PostGet`, `PreSet`, and `PostSet`.
- `PreGet` runs before a getter and `PostGet` after its result is available.
  `PreSet` runs before a setter and `PostSet` after the mutation commits.
- Validation and `AbortSet` equality checks happen before `PreSet`. An equal
  assignment suppressed by `AbortSet` emits neither set event.
- Property callbacks receive the matching metadata Property descriptor first
  and an `event.PropertyEvent` second.
- `event.PropertyEvent` exposes read-only `AffectedObject`, `Source`, and
  `EventName` fields and derives from `event.EventData`.

## Listener Creation

The runtime supports the three MATLAB listener styles:

```matlab
lh1 = addlistener(obj, "Value", "PostSet", callback);
lh2 = listener(obj, "Value", "PostSet", callback);
lh3 = event.proplistener(obj, propMetadata, "PostSet", callback);
```

`obj.addlistener(...)` and `obj.listener(...)` are equivalent method forms.
`addlistener` is coupled to its source, so an unassigned listener remains live
after the caller discards its output. The `listener` and
`event.proplistener` constructors are uncoupled and therefore require the
returned handle to remain reachable. General source destruction and automatic
listener teardown remain outside this milestone, so explicit `delete` is the
defined way to end a coupled listener during a VM run.

`event.proplistener` derives from `event.listener` and adds the read-only
`Object` property. Its `Source` is the canonical metadata property descriptor,
while `Object` is a 1-by-1 Cell containing the affected source object. Existing
`Enabled`, `Recursive`, `Callback`, `EventName`, `delete`, and `isvalid`
behavior is shared with ordinary listeners.

## Delivery And Identity

Listener matching uses both source-object identity and property identity.
Handle aliases therefore observe the same events, while separate instances do
not. An inherited declared property resolves to the descriptor as seen from
the concrete source class and retains its original `DefiningClass`.

Dynamic listener matching uses the descriptor's run-local ID. Deleting the
descriptor removes its property, invalidates descriptor aliases, and also
invalidates listeners bound to it. A descriptor supplied to
`event.proplistener` must belong to the source object.

Callbacks are synchronous. With `Recursive` false, reentrant delivery of the
same listener is suppressed; with `Recursive` true, the callback may observe
its own nested property access. Listener invocation order is deterministic
inside the current VM but is not a public ordering contract between different
listeners.

## Runtime Representation

Property listener records reuse the ordinary VM event-listener registry and
callback engine. A record adds a declared-property storage key or dynamic
descriptor ID plus a property-listener discriminator. Ordinary `notify`
delivery excludes these records, while property access selects only matching
property records.

The event descriptor and `event.PropertyEvent` are constructed at delivery
time. Records store no native pointers, generated code, operating-system
handles, or SLJIT state. The implementation therefore follows the same data
model in native-JIT and `MPARSER_ENABLE_NATIVE_JIT=OFF` builds.

## Example

Run the checked-in demo with:

```powershell
build\mparser.exe --run-bytecode samples\property_events_demo.m
```

The demo covers declared getter/setter ordering, method-form creation,
metadata and event-data identity, dynamic property events and deletion, and
the explicit `event.proplistener` constructor. The final value is
`summary = 738`.

## Validation

`property_listener_smoke` covers:

- exact declared `PreGet`/`PostGet` and `PreSet`/`PostSet` ordering
- getter/setter callbacks and `AbortSet` event suppression
- metadata descriptors and `event.PropertyEvent` callback fields
- direct, method-form, and `event.proplistener` construction
- source-coupled and uncoupled listener lifetime
- enabled, recursive, delete, validity, and reflection behavior
- normal event delivery through method-form `notify`
- dynamic property events and listener invalidation on descriptor deletion
- inherited descriptor identity, handle aliases, and instance isolation
- diagnostics for nonobservable properties, invalid event names, missing
  properties, wrong owners, and value-class sources

`property_listener_bytecode_cli_smoke` executes the complete sample. Both are
included in the focused portable Linux AArch64 QEMU CI selection as well as the
normal Windows x64 and Linux x64 suites.

For a local Windows release check:

```powershell
cmake --build build --config Release --clean-first --parallel
ctest --test-dir build -C Release --output-on-failure
build\mparser.exe --version
build\mparser.exe --run-bytecode samples\property_events_demo.m
```

## Remaining Boundary

- Property listener execution is authoritative in the bytecode VM. The HIR
  reference interpreter still does not execute class objects or metadata.
- Sources and property selectors are currently scalar. Object arrays and
  Cells of source or property metadata are not expanded into listener sets.
- Property listener records are VM-local and are not reconstructed from a
  serialized or independently created workspace.
- General handle destruction, `ObjectBeingDestroyed`, class destructor
  methods, and automatic source teardown remain outside this milestone.
- Built-in listener fields are not themselves observable properties.
- Callback diagnostics stop synchronous delivery. A `PostSet` diagnostic can
  occur after the underlying assignment has already committed.
