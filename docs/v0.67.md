# MParser v0.67 Scope

MParser v0.67 establishes a stable production script-execution interface.
Applications, terminals, and editor Run buttons can use `mparser --run` while
the VM chooses and safely falls back between native, portable typed, and
baseline bytecode execution.

## Milestone Contract

- Project and CLI version are `0.67.1`.
- `mparser --run file.m` is the canonical one-shot execution command.
- Production execution uses the full bytecode VM semantics and runs the script
  once. It does not perform a profiling baseline followed by a second run.
- Statically eligible loops are lowered to typed IR before execution.
- `--jit=auto` is the default and prefers native SLJIT code when available.
- `--jit=off`, `--jit=portable`, and `--jit=native` select an explicit policy.
- Typed guards, transactional workspace commit, and lower-tier fallback remain
  authoritative, so backend selection does not change script semantics.
- The reference HIR interpreter is now explicitly selected with `--run-hir`.
- Invalid options and conflicting execution modes fail with a nonzero status
  and a specific diagnostic. `--help` documents the supported interface.

v0.67.1 also separates the native benchmark samples by execution contract.
`native_jit_benchmark.m` is a self-contained one-shot production script;
`adaptive_native_jit_benchmark.m` retains the eight-invocation persistent
workspace experiment and requires explicit adaptive-session options.

## Production Execution

The default command is intentionally small:

```powershell
build\mparser.exe --run samples\production_run_demo.m
```

It performs these stages:

1. Load the entry source and recursively resolve its source graph.
2. Parse, analyze, and lower the complete module to bytecode.
3. Discover statically eligible structured loop regions and build typed IR.
4. Execute the bytecode VM once, entering typed regions only when their guards
   hold and committing their results transactionally.
5. Print the resulting workspace and return success only when compilation and
   runtime diagnostics are empty.

No static typed region is required for a script to run. Unsupported loops,
failed guards, unavailable native code, and recoverable typed execution all
continue through the existing portable or bytecode fallback contract.

## JIT Policy

| Option | Contract |
| --- | --- |
| `--jit=auto` | Prefer native SLJIT, with guarded lower-tier fallback |
| `--jit=off` | Execute only the baseline bytecode VM |
| `--jit=portable` | Use eligible portable C++ typed kernels |
| `--jit=native` | Request eligible native SLJIT kernels |

The `native` policy is a backend preference rather than permission to bypass
correctness checks. Builds configured with `MPARSER_ENABLE_NATIVE_JIT=OFF`
still retain the parser, semantic analyzer, bytecode VM, and portable typed
executor. Production scripts remain runnable on Windows x64, Linux x64, and
Linux AArch64 from the same source tree.

## Diagnostic Interfaces

The production facade is separate from development and validation modes:

| Mode | Execution behavior |
| --- | --- |
| `--run` | One production execution with selected JIT policy |
| `--run-bytecode` | One baseline VM execution with JIT disabled |
| `--run-hir` | One execution through the smaller reference interpreter |
| `--run-jit` | Static typed/JIT execution plus internal region reporting |
| `--run-typed-bytecode` | Profile, rerun typed code, and compare outputs |
| `--run-adaptive-bytecode` | Repeated hotness/tiering session |

The old pre-v0.67 spelling `--run` selected the HIR interpreter. Current
automation that specifically needs that reference tier must use `--run-hir`.
Historical milestone documents retain their original commands as records of
those releases. A hidden `--run-interpreter` alias remains temporarily for
manual compatibility, but it is not the public interface.

## CLI Contract

`--help` and `-h` print the execution, JIT, and inspection modes. Unknown
options, multiple execution modes, and use of `--jit` outside production
`--run` are rejected. A standalone `--` ends option parsing so a source path
that begins with a hyphen can still be passed unambiguously.

The process returns zero for successful execution, one for compilation or
runtime diagnostics, and two when invocation is incomplete. Argument contract
violations are reported as errors and return one.

## Editor Integration

The editor-facing contract is simply an executable plus `--run` and the active
file path. With VS Code CMake Tools, a task may use the selected launch target
without embedding a Windows or Linux executable suffix:

```json
{
  "label": "MParser: Run current file",
  "type": "process",
  "command": "${command:cmake.launchTargetPath}",
  "args": ["--run", "${file}"],
  "options": { "cwd": "${workspaceFolder}" },
  "problemMatcher": []
}
```

## Example

`samples/production_run_demo.m` combines a nested scalar loop with a handle
class and observable property callback. The typed loop computes `702`; the
property event verifies descriptor, event-name, and affected-object identity,
producing `summary = 705`. This demonstrates that an optimized region and full
class/event VM semantics participate in the same one-shot run.

```powershell
build\mparser.exe --run --jit=native --native-cache-stats `
  samples\production_run_demo.m
```

On a native-JIT build, the sample reports at least one native compilation. The
same sample reports `summary = 705` under `auto`, `portable`, and `off`.

The million-iteration benchmark is directly runnable and reports both elapsed
time and `finalValue = 834.32145639679`:

```powershell
build\mparser.exe --run --jit=native samples\native_jit_benchmark.m
```

Use the separate adaptive sample when measuring promotion and cache hits across
eight invocations:

```powershell
build\mparser.exe --run-adaptive-bytecode `
  --typed-backend=native --adaptive-runs=8 --adaptive-hot-loop=1 `
  --adaptive-persist-workspace --adaptive-workspace=runCount=0 `
  samples\adaptive_native_jit_benchmark.m
```

## Validation

The v0.67 regression set adds:

- help-text and canonical-command coverage
- default, portable, native, and JIT-disabled production executions
- a zero-native-compilation assertion for `--jit=off`
- a positive native-compilation assertion for `--jit=native`
- unknown-option, conflicting-mode, JIT-scope, and `--` separator contracts
- explicit migration of reference-interpreter CLI tests to `--run-hir`
- focused Linux AArch64 QEMU coverage for native and portable builds
- direct native and portable execution of the self-contained JIT benchmark

For a local Windows release check:

```powershell
cmake --build build --config Release --clean-first --parallel
ctest --test-dir build -C Release --output-on-failure
build\mparser.exe --version
build\mparser.exe --help
build\mparser.exe --run samples\production_run_demo.m
build\mparser.exe --run --jit=off samples\production_run_demo.m
build\mparser.exe --run-hir samples\local_function_demo.m
```

## Remaining Boundary

- Static production planning currently specializes the same structured scalar
  and dense-double linear-array loops supported by the typed region executor.
- Production `--run` is a process-level CLI facade, not yet a stable C++ or C
  embedding API.
- Adaptive hotness state and native code cache entries remain process-local.
- Command-line output is human-readable; a versioned machine-readable result
  protocol remains future work.
- Native performance must be measured on physical target hardware; QEMU CI is
  a correctness and portability check only.
