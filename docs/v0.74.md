# MParser v0.74 Scope

MParser v0.74 closes compatibility gap `G-CALL-001` by giving dynamic calls
and function handles one runtime contract across the HIR interpreter,
bytecode VM, adaptive execution, and `CompiledModule`. It replaces VM-local
handle identifiers with first-class callable descriptors, adds MATLAB-like
handle conversion and introspection builtins, and defines source-loading and
shadowing behavior for text targets.

This milestone does not make handles serializable, parse anonymous functions
from text, or add HIR class-method execution. Those boundaries remain explicit
so later embedding work does not accidentally expose process-local code
addresses as a stable ABI.

## Callable Descriptor Contract

`RuntimeValueKind::FunctionHandle` now owns a shared
`RuntimeFunctionHandle`. A descriptor records:

- an immutable runtime identity;
- anonymous, function, builtin, or method kind;
- independent, HIR, or bytecode backend ownership;
- its normalized display name and source location;
- the target function or method identity;
- anonymous parameters and a value snapshot of captured variables;
- the HIR body or bytecode range needed by its owning engine;
- an optional `RuntimeCallableContext` for module-bound code.

Copying a `RuntimeValue` keeps the same descriptor identity, while creating
another handle expression produces a new identity. Runtime-internal comparison
and benchmark helpers use that identity; this milestone does not add a new
MATLAB source-level handle comparison operator. Anonymous workspaces use
capture-by-value semantics: later writes to the defining frame do not change
the closure snapshot.

`CompiledModule` owns one callable context for its lifetime and passes it to
every VM invocation. A source-backed handle returned from one call can be
passed back to later calls on the same module. A different module rejects it
before using its executable body. Context-free builtin handles are portable
between modules. Adaptive sessions use the same context rule.

## Dynamic Calls And Introspection

Both baseline engines now support:

- direct invocation of named, anonymous, and builtin handles;
- `feval(handle, ...)` and `feval(name, ...)`, including zero or multiple
  requested outputs;
- `str2func(name)` for public compiled functions and builtins;
- `func2str(handle)` with complete normalized anonymous source text;
- `functions(handle)` metadata with `function`, `type`, `file`, and an
  anonymous `workspace` Cell;
- a neutral `target(args)` operation that evaluates `target` once, calls it
  when it is a handle, and otherwise indexes it.

The parser now accepts keyword spellings after member access, so fields such
as `details.function` remain valid even though `function` is a declaration
keyword in other positions.

Bytecode execution retains its existing static and bound method-handle support.
The HIR interpreter deliberately diagnoses method-handle execution because its
class-object runtime remains outside that engine's target subset. Typed and
native regions reject dynamic handle operations and fall back to the bytecode
VM without rejecting legal scripts.

## Source Graph And Shadowing

Literal `feval('name', ...)` and `str2func('name')` calls are static source
dependencies. The source loader records valid dotted names and can therefore
load ordinary path and package functions before semantic analysis. A computed
string can call a target already present in the compiled graph, but it does not
perform runtime filesystem loading.

Text resolution uses this order:

1. a loaded public ordinary or package function;
2. a loaded public static method in the bytecode runtime;
3. a known builtin.

This lets an ordinary path function shadow a builtin consistently. A variable
of the same name still wins for neutral `name(args)` indexing, while lexical
`@name` can explicitly obtain the callable target. Private functions can be
captured with `@name` only from an authorized owner; text conversion does not
grant private path visibility.

## Example

Run the dynamic call sample through every baseline interface:

```powershell
build\mparser.exe --run-hir samples\dynamic_call_demo.m
build\mparser.exe --run-bytecode samples\dynamic_call_demo.m
build\mparser.exe --run samples\dynamic_call_demo.m
```

Each mode reports:

```text
summary = 106
```

The sample covers capture-by-value, direct and `feval` invocation, multiple
outputs, text conversion, dynamic call/index resolution, builtin shadowing,
`func2str`, and `functions` workspace metadata.

## Validation

`function_handle_runtime_smoke` differentially runs one script through HIR and
bytecode. It checks anonymous and named calls, handle and text `feval`, output
arity, call/index ambiguity, variable-versus-builtin shadowing, normalized
text, metadata, and unsupported anonymous text diagnostics. It also returns
closure, named, and builtin handles from a `CompiledModule`, reuses them across
ordinary and adaptive invocations, checks descriptor copy/creation identity,
and verifies the foreign-module boundary. A standalone zero-output `feval`
protects the statement-call arity path.

`function_path_smoke` adds literal dynamic dependencies for an ordinary path
function that shadows `sin`, a package function, and private text-access
rejection. `parser_smoke` protects keyword member access. Three CLI tests run
the sample through the HIR, bytecode, and production interfaces.

Use the native and portable-only release gates:

```powershell
cmake -S . -B build -DMPARSER_ENABLE_NATIVE_JIT=ON
cmake --build build --config Release --parallel
ctest --test-dir build -C Release --output-on-failure

cmake -S . -B build-nojit -DMPARSER_ENABLE_NATIVE_JIT=OFF
cmake --build build-nojit --config Release --parallel
ctest --test-dir build-nojit -C Release --output-on-failure
```

Windows x64 and Linux x64 run the complete registry. Linux AArch64 QEMU runs
the focused function-handle, source-graph, and production sample evidence in
both native-JIT and portable-only configurations.

The local Windows x64 Release gates passed `142/142` tests with native JIT
enabled and `136/136` tests in a clean portable-only build. The dynamic call
sample completed through HIR, bytecode, and production execution with
`summary = 106` in both configurations.

## Current Boundary

- HIR supports named, anonymous, and builtin handles, but not class method
  handles or class-object dispatch.
- `str2func` does not parse anonymous function text.
- Computed text targets do not trigger runtime source discovery.
- Text lookup does not expose private path functions.
- Module-bound handles are reusable only while their owning in-process module
  and compiled graph remain alive; there is no disk, wire, or C ABI format.
- Typed/native regions fall back for dynamic handles and calls.
