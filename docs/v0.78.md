# MParser v0.78 Scope

MParser v0.78 closes compatibility gap `G-WORKSPACE-001` by adding explicit
MATLAB-like `global` and `persistent` declarations and one shared runtime-state
contract across the reference HIR interpreter, bytecode VM, production
fallback, adaptive execution, and embedding API.

This milestone does not claim complete MATLAB workspace or `clear` command
compatibility. It establishes the declaration, ownership, lifetime, assignment,
fallback, and reset rules needed before the remaining v0.79 runtime freeze.

## Declaration Contract

The parser accepts whitespace- or comma-separated identifiers:

```matlab
global shared_value, loop_last
persistent count values
```

Declarations are explicit syntax and HIR nodes rather than calls to builtins.
Semantic analysis predeclares them only in their containing script or function
scope and does not inherit declarations across nested function or class
boundaries.

The supported subset has these rules:

- `global` is valid in scripts and functions and binds equal names to the same
  `RuntimeSessionState` global slot.
- `persistent` is valid only in a function and is keyed by compiled callable
  identity, canonical function identity, and variable name. Class-method
  function keys are class-qualified.
- A workspace declaration must appear before the first reference to that name.
- A name cannot combine global, persistent, parameter, output, or incompatible
  local roles in one scope.
- A missing identifier, illegal separator, top-level `persistent`, conflicting
  declaration, or reference before declaration produces a semantic diagnostic.
- A first global or persistent declaration creates an empty 0-by-0 double
  matrix, so the ordinary `isempty` initialization idiom works.

## Shared State

`RuntimeSessionState` stores globals and per-function persistent values. The HIR
interpreter and VM use the same lookup and write routes for:

- direct scalar/name assignment;
- parenthesis and brace indexing;
- member and nested transactional lvalues;
- loop-target writes, including a global variable assigned only by `for`.

State can be inspected through deterministic global and persistent snapshots.
Individual declare, find, store, clear, reset, and snapshot operations are
mutex-protected. A complete script invocation or read-modify-write sequence is
not atomic; an embedding application must serialize concurrent invocation when
it deliberately shares one state.

Different compiled modules may share one state to exchange globals. Their
same-named functions retain separate persistent slots because compiled callable
identity is part of the key. HIR and VM execution share persistent values only
when the caller supplies both the same state and the same callable context.

## Embedding Lifetime

`CompiledModule::createSession()` creates an isolated
`CompiledModuleSession` by default. It owns:

- the immutable source, semantic, bytecode, function-catalog, and diagnostic
  artifacts;
- the module callable identity used by source-backed function handles;
- one mutable `RuntimeSessionState`.

The session may repeatedly invoke the module, inspect global and persistent
values, clear one global, clear every persistent value owned by one function,
clear all globals, or reset all runtime state. A caller may inject a
`RuntimeSessionState` to share globals between selected sessions without
colliding their module-scoped persistent values.

Sessions, adaptive sessions, and module-bound function handles retain the
immutable compiled artifacts. They remain usable after the original
`CompiledModule` object is destroyed and release the artifacts when the last
owner is gone.

Bare `CompiledModule::invoke()` remains independent unless
`BytecodeVmOptions::sessionState` is supplied. `InterpreterOptions` and
`AdaptiveBytecodeVmOptions` expose the same injection point.

## Clear And Reset Boundary

A no-argument script `clear` clears the current execution frame association but
does not erase the session's globals or persistent values. Adaptive-session
`reset()` resets tiering profiles and adaptive workspaces while preserving
`RuntimeSessionState`.

Explicit embedding operations have unambiguous state effects:

| Operation | Effect |
| --- | --- |
| `clearGlobal(name)` | Remove one global slot |
| `clearFunction(function)` | Remove all persistent slots for one function |
| `clearGlobals()` | Remove every global slot |
| `CompiledModuleSession::reset()` | Remove all global and persistent slots |
| `RuntimeSessionState::reset()` | Remove all global and persistent slots |

MATLAB command forms such as `clear name`, `clear global name`, and
`clear functionName` are not yet parsed or executed. They remain an explicit
compatibility-matrix boundary rather than being approximated silently.

## Optimization Boundary

Typed-region discovery rejects global and persistent declarations, loads,
stores, indexed mutations, and session-bound loop targets. Portable and native
specializations never capture mutable session addresses. Legal code continues
in the bytecode VM through guarded fallback without changing workspace
semantics.

The fallback rule is intentional: wider shared-state optimization may be added
later, but optimization coverage cannot make valid target-subset code fail.

## Example

Run the checked sample through all three public execution modes:

```powershell
build\mparser.exe --run-hir samples\workspace_session_demo.m
build\mparser.exe --run-bytecode samples\workspace_session_demo.m
build\mparser.exe --run samples\workspace_session_demo.m
```

Each command reports:

```text
summary = 14389
```

The sample covers a script global, a store-only global `for` target, shared
global access from two local functions, persistent scalar initialization,
persistent indexed array mutation, and repeated calls in one runtime state.

## Validation

`runtime_session_smoke` differentially exercises HIR and VM state sharing,
isolated and explicitly shared module sessions, repeated persistent calls,
global visibility, every supported assignment route, targeted clear operations,
full reset, adaptive reuse, same-named persistent functions in two compiled
modules sharing one state, module destruction before session execution, and
function-handle lifetime anchoring.

Parser, semantic, bytecode, VM, region-selection, and three CLI sample tests
cover the complete source-to-runtime path. The ARM64 workflow runs the focused
runtime test and all sample modes in both native-SLJIT and portable-only QEMU
configurations.

The Windows x64 Release validation passed all 157 native-SLJIT tests and all
151 portable-only tests. Both production executables completed
`workspace_session_demo.m` with `summary = 14389`, and the native CLI reported
`MParser 0.78.0`.

## Explicit Boundaries

- Workspace declarations must precede references in the supported subset.
- Script-level persistent variables are rejected; persistent storage belongs to
  functions.
- MATLAB's complete base/function/nested/global workspace interaction model is
  not implied.
- Command-form selective `clear` syntax is not implemented.
- One shared state does not make an entire invocation atomic or safe for
  concurrent read-modify-write without external serialization.
- Adaptive reset and session-state reset are deliberately separate operations.
- CLI execution is one process-local run; compile-once/invoke-many persistence
  is exposed through `CompiledModuleSession`.
- Shared bindings are not typed/native optimized and execute through VM
  fallback.
- Cross-process persistence, serialization, and a frozen external state ABI
  remain future embedding work.

## Next Ordered Gaps

1. v0.79: freeze the remaining `RuntimeValue`, shape, indexing, object,
   exception, call-frame, output-arity, diagnostic, ownership, and fallback
   contracts.
2. v0.80: land the unified builtin registry, descriptor, call/result/error

   migration.
3. v0.90: stabilize embedding APIs and the versioned machine protocol, then
   freeze v1.0 candidates.
