# MParser v0.8 Scope

MParser v0.8 adds the first profile-consuming optimization layer. The VM still
executes bytecode interpretively, but the new planner can turn runtime profile
data into concrete optimization candidates and guard records.

## Added Since v0.7

- New `BytecodeOptimizationPlanner` module.
- New public optimization data structures:
  `BytecodeOptimizationPlan`, `BytecodeOptimizationCandidate`, and
  `BytecodeOptimizationGuard`.
- CLI option `--plan-bytecode`.
- Hot-loop candidates for loops with stable loop-variable observations.
- Hot function/builtin/index site candidates with stable receiver, argument,
  and result observations.
- Assignment candidates for hot stores and stores inside hot loops with stable
  value observations.
- Guard records carrying source, role, runtime kind, shape, and observation
  count.
- Dedicated `optimization_plan_smoke` CTest coverage.
- Project version and CLI version bumped to `0.8.0`.

## Why This Matters

v0.7 records whether runtime values are stable. v0.8 starts consuming that data
the way a JIT pipeline needs to consume it:

- Hot code is selected from measured execution counts.
- Cold regions are ignored even if they have stable values.
- Candidate guards are explicit and structured, not inferred from printed text.
- Each candidate has a PC, target, execution count, reason, and guard list.

This is the step between profiling and typed IR. It gives later compiler passes
a small, testable contract instead of requiring them to inspect raw VM profile
tables directly.

## CLI Example

```powershell
build\mparser.exe --plan-bytecode samples\bytecode_profile_demo.m
```

Expected plan signal:

```text
Bytecode optimization plan:
  hot loop threshold: 10
  candidates: 4
    pc=7, kind=hot-loop, target=i, executions=12
      guard source=loop, role=variable, kind=number, shape=1x1
    pc=11, kind=function-site, target=kernel, executions=12
      guard source=call-site, role=arg0, kind=number, shape=1x1
      guard source=call-site, role=result0, kind=number, shape=1x1
```

The short `j` loop in the same sample is intentionally not selected because it
does not meet the hot-loop threshold.

## VM And Planner Gaps

The planner does not compile or rewrite bytecode yet. It also does not compute
loop body ranges, dominance, aliasing, object dispatch, or deoptimization
points. It only identifies high-confidence candidates from existing profile
data.

The VM still intentionally reports diagnostics for classes, object dispatch,
automatic array growth, cell/function handle execution, non-scalar
right-hand-side indexed assignment shape matching, structs, sparse arrays, and
complex values.

## Validation

Validated on Windows with MSVC Build Tools:

```powershell
cmake -S . -B build
cmake --build build
ctest --test-dir build --output-on-failure
build\mparser.exe --version
build\mparser.exe --plan-bytecode samples\bytecode_profile_demo.m
build\mparser.exe --profile-bytecode samples\bytecode_profile_demo.m
```

Expected version output:

```text
MParser 0.8.0
```

## Next Iterations

The next high-value work is to introduce a small typed optimization IR:

- Convert v0.8 candidates and guards into typed IR regions.
- Start with scalar numeric loop and scalar function-call patterns.
- Keep deoptimization as an explicit runtime fallback contract.
- Preserve bytecode execution as the correctness baseline.
