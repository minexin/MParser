# MParser v0.80 Scope

MParser v0.80 closes compatibility gap `G-BUILTIN-001` by replacing
distributed builtin recognition and representative runtime dispatch with one
frozen, module-owned `BuiltinRegistry`. This milestone stabilizes the source
contracts needed to add functions over time; it does not claim a complete
MATLAB function library or a frozen binary ABI.

## Unified Catalog

`BuiltinDescriptor` is the single catalog record for a builtin name and its
aliases. It declares:

- accepted input and output arity;
- value and shape constraints;
- shared, context, intrinsic, or explicitly unsupported implementation;
- purity, determinism, thread-safety, and side effects;
- available and required runtime context permissions;
- the stable error identifier and a short summary;
- optional eligibility for an existing typed/JIT lowering;
- the shared C++ handler used by both baseline engines.

The default catalog contains every builtin name previously recognized by
semantic analysis. It is frozen before publication. A caller that needs
source-level C++ extensions starts with
`createBuiltinRegistryWithDefaults()`, registers additional descriptors,
freezes the result, and passes it through `CompiledModuleCompileOptions`.
The compiled module retains that registry for its full lifetime.

Registration rejects empty names, invalid arities, missing handlers,
duplicate names or aliases, and mutation after freeze. Invocation validates
arity, declared argument constraints, required context, exact requested output
count, storable output ownership, and the recursive `RuntimeValue` contract.
Host C++ exceptions become `MParser:BuiltinHostException` diagnostics rather
than escaping through the runtime.

## Engine Integration

Semantic resolution, builtin handles, dynamic text resolution, HIR execution,
bytecode execution, typed-region discovery, optimization planning, portable
typed execution, native SLJIT execution, adaptive planning, and runtime
benchmark planning all consume the registry retained by the semantic result.
The old math, reduction, scan, array-transform, and warning dispatch branches
were removed from both baseline engines after migration.

The original `CompiledModule::compile` and optimization-planner overloads
remain available and select `defaultBuiltinRegistry()`. Registry-aware
overloads are additive, preserving existing source callers while the public
C++ ABI remains pre-freeze.

## Representative Migration

The registry now owns representative families rather than merely recognizing
their names:

- scalar and array-preserving math: `abs`, `acos`, `asin`, `atan`, `cos`,
  `exp`, `log`, `sin`, `sqrt`, and `tan`;
- reductions and multi-output operations: `sum`, `prod`, `mean`, `min`,
  `max`, `all`, `any`, and `find`;
- scans: `cumsum`, `cumprod`, `cummin`, `cummax`, and `diff`;
- array transforms: `reshape`, `permute`, `ipermute`, `squeeze`, `repmat`,
  `cat`, `horzcat`, and `vertcat`;
- context builtins: `warning` and `lastwarn`.

Engine-only operations remain explicit `Intrinsic` descriptors. Recognized
functions that are not implemented remain explicit `Unsupported`
descriptors. Neither category silently acquires a generic host handler.

Pure unary math descriptors expose existing typed lowering identifiers.
Custom names may opt into one only when their behavior is exactly identical to
that lowering. The same custom descriptor is tested through HIR, bytecode,
portable typed execution, and native SLJIT when the backend is available.
Unsupported optimized calls still fall back to the VM.

## Extension Paths

v0.80 defines three levels:

1. Ordinary `.m` functions use the source graph and require no registry
   changes. Normal MATLAB-like local/path/package/private shadowing applies.
2. Built-in C++ functions use `BuiltinRegistry`, `BuiltinDescriptor`,
   `BuiltinCall`, and `BuiltinResult`.
3. A narrow external C/C++ adapter and stable ABI are future v0.90 work. A
   source-level v0.80 handler must not be presented as a stable plugin ABI.

The complete authoring rules and a minimal registration example are in
[extending-builtins.md](extending-builtins.md).

## Validation

`builtin_registry_smoke` covers:

- the frozen 118-name default catalog and representative metadata;
- custom names and aliases;
- duplicate and post-freeze registration rejection;
- arity, missing-context, malformed-output, ownership, and exception
  boundaries;
- local-function shadowing and builtin function handles;
- HIR/bytecode parity using the reusable conformance helper;
- portable typed execution and native SLJIT execution when available.

All three public execution routes run
`samples/builtin_registry_demo.m` and require `summary = 510446`:

```powershell
build\mparser.exe --run-hir samples\builtin_registry_demo.m
build\mparser.exe --run-bytecode samples\builtin_registry_demo.m
build\mparser.exe --run samples\builtin_registry_demo.m
```

The native Windows and portable-only builds run their complete CTest suites.
Linux x64 and AArch64 native/portable jobs exercise the registry test and all
three sample routes in CI.

## Deliberate Limits

- v0.80 is a source-contract milestone, not a stable C++ ABI or C ABI.
- The descriptor constraints are intentionally small and will grow only when
  a representative function requires a reusable rule.
- Arbitrary custom native code generation is not exposed. The typed lowering
  enum selects audited kernels already supported by both portable and SLJIT
  backends.
- Dynamic invoker context is represented but is not yet supplied by the
  engines; composite host callbacks remain a later contract.
- Intrinsic migration continues when a shared handler can preserve semantics;
  engine operations are not forced through an unsuitable generic interface.
- Long-tail MATLAB and toolbox function growth belongs to v1.x. v1.0 still
  requires the documented target language subset and stable extension rules.

The next release work advances the v0.90 embedding gate: versioned result
protocols, public value/lifetime boundaries, compile-once invocation APIs,
resource limits, and installed cross-platform consumers.
