# MParser v0.81

MParser v0.81 starts the v0.90 embedding gate with one engine-neutral module
execution contract. It separates host-facing request, result, diagnostic, and
execution-summary semantics from `BytecodeVmOptions` and
`BytecodeVmResult`. The new contract is a source-level API candidate; this
milestone does not freeze C++ object layout or provide the future C ABI and
machine-readable CLI protocol.

## Module Execution Contract

`module_execution.h` defines:

- `ModuleInvocationRequest`;
- `ModuleInvocationResult`;
- `ModuleExecutionBackend` and `ModuleExecutionTier`;
- `ModuleInvocationStatus`;
- phase- and severity-aware `ModuleDiagnostic`;
- `ModuleExecutionSummary`.

`CompiledModule::execute()` and `CompiledModuleSession::execute()` consume the
same request and return the same result. A caller can therefore switch between
stateless and persistent execution without changing its value, diagnostic, or
backend handling.

The request owns:

- an optional entry-function name;
- positional and name-value `RuntimeValue` arguments;
- an optional requested output count;
- an initial workspace;
- an execution backend preference;
- a profiling opt-in.

An empty entry name executes the module as a script. Script requests reject
arguments and nonzero function-output counts rather than silently ignoring
them. Initial workspace names must be nonempty and unique, values must satisfy
the recursive `RuntimeValue` contract, and transient values cannot cross the
workspace boundary. Function arguments are contract-validated before signature
normalization.

## Guarded Production Backends

The backend preference has four values:

| Backend | Contract |
| --- | --- |
| `Automatic` | Prefer the available optimized tier and preserve VM fallback |
| `Bytecode` | Execute only the ordinary bytecode VM |
| `Portable` | Attempt portable typed regions and fall back to the VM |
| `Native` | Attempt native SLJIT regions and fall back to the VM |

`Automatic` is the default. Backend selection is a preference, not permission
to reject legal target-subset code. Unsupported regions continue in the VM.

`CompiledModule` now builds the registry-aware static typed-region module once
after bytecode lowering and retains it with the compiled artifacts. Repeated
`execute()` calls reuse that typed IR and the existing process-local native
kernel cache. This removes repeated planner construction from the public
compile-once/invoke-many path.

`ModuleExecutionSummary` reports the requested backend, effective bytecode,
portable, native, or mixed tier, profiling state, instruction count, typed
region attempts/executions/fallbacks, and native compilation/cache-hit counts.
The summary describes observed execution; it does not promise that every
region used the requested optimized backend.

## Stable Result Classification

`ModuleInvocationStatus` distinguishes:

- `Succeeded`;
- `CompilationFailed`;
- `RequestRejected`;
- `RuntimeFailed`.

Warnings remain diagnostics on a successful result. An uncaught language error
produces `RuntimeFailed`. Invalid modules and rejected requests never enter the
VM.

Diagnostics are projected into an owned host-facing structure with:

- compilation, validation, or execution phase;
- error or warning severity;
- stable identifier and message fields;
- source name plus begin/end offsets, lines, and columns when available;
- copied stack frames and recursive causes.

Diagnostics without an engine identifier receive a phase-specific fallback
identifier. Entry lookup, argument/output count, malformed value, duplicate
workspace, transient workspace, script-argument, and backend validation errors
have explicit identifiers.

Escaping `std::exception` and nonstandard host exceptions become
`MParser:HostExecutionException`. `std::bad_alloc` is deliberately rethrown
until the v0.90 allocation-failure and resource-budget contract can guarantee a
safe preallocated reporting path.

## Persistent Sessions

`CompiledModuleSession::execute()` injects the session's
`RuntimeSessionState` into the same execution path. Globals, persistent
variables, module identity, reset, and targeted clear behavior therefore remain
identical to the v0.78 contract while the host observes the v0.81 result model.

Compound invocation on one intentionally shared state is still caller
serialized. Resource budgets and cooperative cancellation are separate v0.90
work and will attach to `ModuleInvocationRequest` without changing the result
classification above.

## Source Compatibility

The existing APIs remain available:

- `CompiledModule::invoke(BytecodeVmOptions)`;
- `CompiledModuleSession::invoke(BytecodeVmOptions)`;
- adaptive session and adaptive module runtime APIs.

They continue to expose engine-specific profiles for low-level tools and
existing callers. New embedding code should start with `execute()`. Public
C++ binary layout, external value handles, the narrow C ABI, result
serialization, and protocol version negotiation remain pre-freeze.

## Runnable Host Example

Build and run the C++ embedding example:

```powershell
cmake --build build --target mparser_embedding_execution_demo
build\mparser_embedding_execution_demo.exe
```

It compiles one in-memory module, invokes a loop through the default guarded
production backend, reuses a persistent session, and prints:

```text
status = succeeded
requested_backend = automatic
effective_tier = native
summary = 5075
```

The effective tier is platform dependent. A portable-only build prints
`portable`; legal execution can also report `bytecode` when no optimized region
is eligible.

## Validation

`module_execution_smoke` covers:

- bytecode, portable typed, native SLJIT when available, and automatic modes;
- compile-once cached typed-region execution and execution summaries;
- multiple outputs and profiling opt-in;
- compilation, validation, warning, and runtime-failure diagnostics;
- source-name/range projection and stable identifiers;
- malformed arguments, duplicate/transient workspace values, invalid backends,
  and script-call rejection;
- initial script workspace transport;
- persistent session reuse and reset.

`embedding_execution_demo_smoke` runs the host example and requires
`summary = 5075`. Both tests are included in the focused Linux AArch64 native
and portable QEMU jobs.

## Remaining v0.90 Work

v0.81 intentionally leaves these release gates open:

1. an external value/array/object ownership boundary suitable for a C ABI;
2. instruction, time, call-depth, allocation, diagnostic, and cancellation
   limits;
3. a versioned machine-readable result protocol;
4. a narrow C ABI with explicit allocation and release functions;
5. CMake install/export packages and external C/C++ consumer tests;
6. public API/ABI compatibility policy and final v1.0 freeze review.
