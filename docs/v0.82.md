# MParser v0.82

MParser v0.82 closes the first production resource-boundary gate for the
engine-neutral embedding API introduced in v0.81. A stateless
`CompiledModule` call and a persistent `CompiledModuleSession` call now share
the same cancellation, budget, terminal-diagnostic, and execution-summary
contract.

This milestone provides cooperative, deterministic boundaries around MParser
execution. It is not a hard real-time scheduler, a process-wide memory
sandbox, or a transactional rollback system.

## Request Controls

`ModuleInvocationRequest` now carries:

- `RuntimeExecutionLimits limits`;
- an optional copyable `RuntimeCancellationToken`.

Every numeric limit uses zero to mean unlimited:

| Limit | Contract |
| --- | --- |
| `maxInstructionCount` | Stop before dispatching an instruction after exactly this many VM instructions have completed |
| `maxWallTime` | Stop at a VM checkpoint after this much steady-clock wall time; negative durations are rejected |
| `maxCallDepth` | Limit active MParser entry/function/anonymous call frames, including the root entry |
| `maxArrayBytes` | Limit the recursive dynamic payload represented by any one live `RuntimeValue` |
| `maxDiagnosticCount` | Retain at most this many language diagnostics before a terminal diagnostic-limit stop |

`RuntimeCancellationToken` owns shared atomic state. The host may copy the
token into a request, execute on one thread, and request cancellation from
another thread. Cancellation is one-shot and cooperative.

The wall-time clock starts after compilation and request validation, just
before VM execution. It excludes module compilation and host-side result
projection. `elapsedNanoseconds` reports the same VM-side timing boundary.

## Stable Stop Contract

`RuntimeExecutionStopReason` distinguishes:

- `Cancelled`;
- `InstructionLimit`;
- `WallTimeLimit`;
- `CallDepthLimit`;
- `ArrayByteLimit`;
- `DiagnosticLimit`.

The stable names are `cancelled`, `instruction-limit`, `wall-time-limit`,
`call-depth-limit`, `array-byte-limit`, and `diagnostic-limit`.

A stop produces `ModuleInvocationStatus::RuntimeFailed`, records the stop
reason in `ModuleExecutionSummary`, and appends one terminal error with a
stable identifier:

| Stop | Identifier |
| --- | --- |
| Cancellation | `MParser:ExecutionCancelled` |
| Instruction budget | `MParser:InstructionLimitExceeded` |
| Wall-time budget | `MParser:WallTimeLimitExceeded` |
| Call depth | `MParser:CallDepthLimitExceeded` |
| Array payload | `MParser:ArrayByteLimitExceeded` |
| Diagnostic volume | `MParser:DiagnosticLimitExceeded` |

These terminal diagnostics bypass MATLAB-language `try`/`catch`. A script
cannot turn a host cancellation or resource stop into ordinary language
success.

The execution summary additionally reports whether controls were active,
whether optimized execution was suppressed, instruction count, maximum call
depth, maximum observed per-value payload, maximum observed diagnostic count,
and elapsed steady-clock nanoseconds.

## Array-Payload Boundary

`runtimeValueArrayBytes()` counts recursive dynamic payload bytes for numeric,
character, string, Cell, structure, object, and function-handle capture
values. Shared handle fields and function-handle graphs are cycle-safe and
count shared storage once within one value traversal. Overflow is represented
as an unbounded value and fails any finite limit.

Host arguments and initial workspace values are checked before VM entry.
During execution, the VM observes live frame values, operand values, loop
vectors, index and lvalue transactions, switch selectors, pending exception
values, entry arguments, and outputs after controlled instructions.

This is deliberately a per-`RuntimeValue` payload boundary. It does not count
allocator metadata, native code, parser/compiler storage, or the aggregate
process heap. An engine operation can allocate a value before the next
checkpoint observes it. Builtins that may perform large allocations must
preflight their requested size against the supplied execution control rather
than treating post-operation observation as an allocation sandbox.

## Diagnostic Boundary

The diagnostic budget includes warnings and errors produced during execution.
When the next diagnostic exceeds the configured count, MParser retains the
configured number and appends one terminal diagnostic-limit error outside that
count. This guarantees that the host can always distinguish truncation from a
normal runtime failure.

## JIT And Fallback

Instruction limits, wall-time limits, and cancellation require checkpoints
between VM instructions. Current portable and native typed kernels do not yet
contain safe polling points, so a request containing any of those controls
suppresses typed-region execution and uses the bytecode VM. The summary sets
`optimizedExecutionSuppressed` and reports policy fallback for automatic,
portable, or native requests.

Call-depth, array-byte, and diagnostic controls do not require instruction
polls inside the current typed kernels. They preserve eligible portable or
native execution and retain normal guarded VM fallback.

This is the v1.0 safety rule: an optimization tier may decline controlled
execution, but legal target-subset code must still run correctly in the VM.
Future kernels may regain strict-control eligibility only after their polling
and unwind behavior is proven.

## Builtin Cooperation

`BuiltinCallContext` exposes the current `RuntimeExecutionControl`.
Context builtins must declare
`BuiltinContextPermission::ExecutionControl` before consuming it. A builtin
may call `checkpoint()`, inspect the configured limits, and use
`observeArrayBytes()` before a large host allocation.

The VM cannot forcibly interrupt a noncooperative builtin blocked inside host
code or a system call. Extension authors should checkpoint bounded chunks of
long-running work and return promptly after a failed checkpoint.

Expected host validation failures still use `BuiltinResult::failure`.
Ordinary C++ exceptions remain contained as builtin or module host
diagnostics. `std::bad_alloc` deliberately propagates to the embedder because
converting it safely requires a preallocated reporting reserve that is not yet
part of the public contract.

## Session Semantics

Every invocation receives a fresh execution control and snapshot. A stopped
`CompiledModuleSession` remains structurally reusable for later requests.

Execution is not transactional. Workspace, global, persistent, object, or
external side effects completed before a stop are not rolled back. A host that
requires atomic application state should execute against an isolated session
or stage its own commit outside MParser.

One intentionally shared session still requires caller serialization. The
cancellation token is thread-safe; the session workspace itself is not made
concurrently mutable by this milestone.

## Runnable Host Example

Build and run:

```powershell
cmake --build build --target mparser_embedding_resource_control_demo
build\mparser_embedding_resource_control_demo.exe
```

The example compiles one typed-eligible function plus an infinite loop,
terminates the loop at exactly 64 VM instructions, demonstrates optimized-tier
suppression, cancels a second request, and proves that the session remains
usable:

```text
instruction_status = runtime-failed
instruction_stop = instruction-limit
instruction_count = 64
optimized_suppressed = true
cancellation_stop = cancelled
recovered = 42
summary = instruction-limit,cancelled,42
```

## Validation

`module_resource_control_smoke` covers:

- recursive and cycle-safe runtime-value byte accounting;
- exact instruction termination and uncatchable stops;
- pre-cancellation and live cross-thread cancellation;
- steady-clock deadline termination;
- exact recursive call-depth termination;
- host-input rejection and live array-payload termination;
- diagnostic retention and terminal truncation reporting;
- optimized execution under non-checkpoint controls;
- strict-control JIT suppression and VM fallback;
- invalid-limit rejection;
- session reuse after a stop;
- builtin execution-control permission and visibility;
- deliberate `std::bad_alloc` propagation;
- stable stop-reason names.

`embedding_resource_control_demo_smoke` runs the host example and requires the
deterministic summary above. Both tests are part of the focused Linux AArch64
native and portable QEMU jobs.

## Remaining v0.90 Work

v0.82 closes `G-RESOURCE-001` at the source-level embedding boundary. The
remaining v0.90 release-candidate work includes:

1. external value/array/object handles with explicit ownership;
2. a narrow C ABI and versioned machine-readable result protocol;
3. allocation-safe host reporting and release functions;
4. install/export packages and external C/C++ consumer tests;
5. API/ABI/version compatibility policy and platform release evidence;
6. broader stress, fuzz, sanitizer, memory, and performance characterization.

v0.83 completes candidate C value/ownership handles and the first narrow C ABI.
See [v0.83.md](v0.83.md). The final ABI freeze, machine protocol, installed
consumers, and remaining release evidence are still v0.90 work.
