The native Linux ARM64 and cross/QEMU lanes are complementary. The native lane
can characterize target execution and resource behavior. The QEMU lane proves
the independent cross toolchain, native and portable target generation,
installation, package consumption, and fallback behavior; its timing does not
represent ARM performance.

The first native Linux ARM64 reports passed protocol, schema, correctness,
zero-fallback, and native-cache checks, but the hosted kernel exposed no
generic model-name field and the collector emitted `cpu_model=unknown`. Those
reports are deliberately not indexed as final hardware-labelled performance
evidence. Revision `f36a014` added raw ARM MIDR fallback and made an unknown CPU
identity a native-evidence failure. Run `30732814590` then recorded
`implementer=0x41`, architecture `8`, variant `0x0`, part `0xd49`, revision `0`
on its non-emulated aarch64 host; both accepted reports are indexed and
continuously validated.

All first-party CI builds enable warnings-as-errors. A direct audit of all
seven execution-job logs from run `30732814590` found no compiler, linker, or
CMake warning. The only broad `warning` text was Git's standard initial
branch-name hint inside checkout on non-Windows runners; it is not project
build output.

## Performance Evidence

The later run uploaded two validated reports from each native Windows x64,
Linux x64, macOS x64, and macOS ARM64 job. All eight reports were downloaded,
SHA-256 indexed, and checked into
[`baselines/v1.0/actions-30691616946`](baselines/v1.0/actions-30691616946/README.md).
They bind the exact revision, current workload hashes, Release binaries,
hardware labels, compilers, timing/resource boundaries, correctness, zero
fallback, and native-cache transitions.

Every report records `emulated=false`. The macOS ARM64 report identifies its
CPU as `Apple M1 (Virtual)`, so it is native-architecture Apple Silicon hosted
runner evidence, not a bare-metal timing claim. Linux AArch64/QEMU does not
publish a performance report. The source-tree
`cross_platform_performance_evidence_smoke` rejects report-set, manifest,
identity, source, semantic, correctness, fallback, and cache drift without
using a machine-specific timing threshold.

The final native Linux ARM64 job uploaded two additional reports. They are
SHA-256 indexed under
[`baselines/v1.0/actions-30732814590`](baselines/v1.0/actions-30732814590/README.md)
and bind revision `3ec2bc0`, GNU 13.3.0, aarch64, the raw ARM MIDR label,
`emulated=false`, exact workload/binary hashes, zero fallback, matching
results, and native-cache transitions. The independent
`linux_arm64_performance_evidence_smoke` freezes that exact two-report set.

## Release Decisions

These runs confirm:

- the frozen CLI, C ABI 1.1, header-only C++ API 1.0, machine protocol 1.0,
  builtin descriptor contract, and compatibility matrix;
- deterministic frontend/bytecode verification, invoke-many, lifecycle,
  resource, cache, allocation, unload, concurrency, and Linux sanitizer
  reliability evidence;
- installed and archived documentation, C11/C++20 consumers, CLI protocol,
  platform/architecture naming, checksum generation, and deterministic local
  provenance metadata on the advertised release matrix;
- reproducible, hardware-labelled cross-platform performance/resource
  evidence for the v1.0 target set.

Accordingly, `G-RELIABILITY-001`, `G-PERFORMANCE-001`,
`G-DOCUMENTATION-001`, and `G-PROVENANCE-001` are closed. Tag-scoped Actions
run `30743014345` authenticated the five candidate archives and five local
provenance statements; its retained evidence is under
`docs/release-evidence/v0.90.1-authentication`. The engine/package version is
1.0.0 and the public contract is `frozen-v1`; final tag authentication,
evidence retention, and publication are separate hosted operations.

## Remaining Boundaries

The candidate still does not close:

- `G-SANITIZER-001`: Linux TSan and macOS ARM64 sanitizer feasibility remain
  focused evaluations, while local Windows MSVC ASan is evidence rather than
  a recurring lane;
- final `1.0.0` artifacts, tag, repetition of authenticated assembly for that
  final tag, and release-page publication.

The release-candidate readiness test freezes the open Must-have set to empty,
keeps `G-SANITIZER-001` as a bounded Should-have, and keeps broader JIT
coverage deferred to v1.x.
