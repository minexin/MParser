# v1.0 Release Documentation Gate

This gate turns the existing architecture and public-contract records into a
coherent release-facing manual set. It does not create a second semantic
authority: the compatibility matrix, CLI contract, public contract manifest,
protocol schema, public headers, and builtin catalog remain authoritative.

## Published Manual Set

The task-oriented [documentation index](README.md) routes:

- script users to the [User Manual](user-manual.md),
  [CLI Reference](cli-reference.md), and
  [Support Matrix](support-matrix.md);
- builders to [Build And Install](build-and-install.md);
- runtime operators to [JIT And Fallback](jit-and-fallback.md) and
  [Runtime Boundaries](runtime-boundaries.md);
- C and C++ hosts to the embedding and ABI guides;
- builtin authors to the source-extension contract;
- pre-v1 users to [Migrating From v0.x To v1.0](migration-v1.0.md);
- contract reviewers to versioning, freeze, roadmap, reliability, and
  performance evidence.

Every scope guide states that v1.0 is a MATLAB-like subset runtime rather than
complete MATLAB compatibility. The support summary distinguishes parser,
production VM, portable typed, and native states and names explicit
unsupported/Post-v1.0 work.

## Executable Consistency

`release_documentation_smoke`:

1. requires the complete release manual set and rejects empty files or
   unfinished markers;
2. verifies that the documentation index and top-level README route every
   required guide;
3. reads `cli-contract-v1.json` with CMake's JSON parser;
4. requires every frozen production mode/option, diagnostic mode, backend
   selector, utility command, and removed-mode migration in
   `cli-reference.md`;
5. checks the same option names against the built CLI's live `--help`;
6. executes the documented human production command with `--jit=off` and
   verifies `summary = 705`;
7. executes the documented JSON command and parses a successful
   `mparser.result` major-1 document with empty stderr.

The check derives its option list from the frozen contract rather than
maintaining a second hand-written list in the test.

## Installed And Archived SDK

CMake installs the manual set beside the versioned schemas, manifests,
license, notices, and builtin catalog. The source `docs/README.md` is installed
as `documentation-index.md` so it does not overwrite the project overview
`README.md`.

Both relocated installed-consumer tests require all release guides before
building and running independent C11 and multi-translation-unit C++20 hosts.
`release_archive_smoke` requires the same files after unpacking, then runs
those consumers and the installed JSON CLI without source-tree access.

The release archive is generated twice from one fixed compiled payload with
normalized metadata and must have identical hashes. Its `.sha256` sidecar and
`SHA256SUMS` are authoritative because an archive hash cannot be embedded
inside that same archive without changing it.

## Windows Candidate Evidence

The current documentation candidate passed:

- Windows x64 MSVC Release native: 202/202 tests;
- Windows x64 MSVC Release no-JIT: 196/196 tests;
- focused native and no-JIT documentation, compatibility-matrix, installed C,
  and installed C++ gates;
- packaging-tree documentation and reproducible relocated archive gates;
- a regenerated `mparser-0.90.0-windows-x86_64.zip` with matching SHA-256
  sidecar.

The first direct installed-consumer attempt outside a Visual Studio developer
environment could not locate `kernel32.lib`. Re-running under `vcvars64`
passed; this confirms the build-guide requirement to activate the actual MSVC
toolchain rather than treating a plain shell as a compiler verdict.

## Deferred Evidence

Per the current validation schedule, this milestone does not claim a fresh
final-candidate rerun on Linux x64/AArch64 or macOS x64/ARM64. The manuals,
CMake install rules, package required-file checks, and CMake-only
documentation validator are platform-neutral, but final release packages must
repeat the same archive/consumer/CLI evidence in the shared cross-platform
window.

`G-DOCUMENTATION-001` therefore remains in progress until that final package
confirmation, while `DOC-001` records the locally implemented and executable
documentation contract.

## Next Gate

The next v1.0 work is specialist sanitizer evaluation where toolchains are
stable, followed by the final release freeze: version 1.0.0, final matrix and
contract snapshots, release notes, provenance, checksummed packages, and
independent unpacked SDK consumers on every release target.
