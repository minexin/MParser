# MParser v1.0 JIT Scope Decision

Status: accepted for the local v1.0 release candidate.

Decision: **defer broader typed/JIT coverage to v1.x**.

`G-JIT-001` remains a Should-have optimization item, but its release state is
`deferred`, its target is `v1.x`, and its permitted framework impact remains
additive. No v1.0 execution-engine change is authorized by this decision.
Legal target-subset code that is not eligible for a typed region continues to
execute in the verified bytecode VM.

## Evidence Reviewed

The decision uses the three committed protocol-1.0 reports under
`docs/baselines/v1.0/windows-x86_64-msvc-release`. They were collected on one
non-emulated Windows x86-64 MSVC Release host and bind the source workloads,
runtime binaries, build configuration, and implementation revision
`da4b010791590a235dbcbf3be5a8dc853b790963` by SHA-256 or revision identity.

| Workload and backend | Bytecode median | Optimized median | Median speedup |
| --- | ---: | ---: | ---: |
| scalar loop, portable | 2342.359 ms | 11.533 ms | 203.10x |
| scalar loop, native warm | 2342.359 ms | 2.571 ms | 911.12x |
| dense linear array, portable | 90.290 ms | 0.555 ms | 162.83x |
| dense linear array, native warm | 90.290 ms | 0.541 ms | 166.94x |
| no-JIT dense linear array, portable | 98.938 ms | 0.814 ms | 121.52x |

Every measured bytecode, portable, and available native result matched the
same reference value. The optimized phases recorded typed execution with zero
fallbacks. Each native cold phase compiled and inserted one bounded cache
entry; warm measurements reused that entry. The no-JIT report recorded both
native phases as unavailable and left native-cache activity at zero.

The allocation counters explain the bytecode gap without requiring another
typed representation. For the scalar workload, one warm native call issued
about 29,467 times fewer allocation requests and requested about 57,016 times
fewer cumulative bytes than bytecode. For the array workload, the reductions
were about 957x and 823x. These counters measure successful allocation
requests, not live heap or retained memory.

## Interpretation

The existing v1.0 candidate already accelerates its advertised high-value
families: selected scalar and nested numeric loops, structured branches,
statically bound pure unary math builtins, and dense-double direct linear
array reads and writes. Portable execution also preserves those gains when
SLJIT is disabled.

The reports do not prove that arbitrary matrix expressions, straight-line
regions, general builtin calls, or user-function specialization are fast.
They do show that current supported typed families are working, that the
portable fallback is valuable, and that no measured release workload exposes
a missing specialization that must be added before v1.0. Expanding coverage
without such a workload would add guard, lowering, diagnostic, cache, and
cross-platform risk while the v1.0 release is otherwise in contract freeze.

This is a scope decision, not a universal performance threshold and not a
claim of MATLAB-wide performance parity. The fixed-report checks only prevent
the evidence supporting this decision from being silently replaced by weaker
or behaviorally inconsistent data.

## Frozen v1.0 Contract

- The bytecode VM remains the semantic authority.
- Typed eligibility is conservative and guarded at runtime.
- Portable and native execution must produce equivalent values and
  diagnostics for every advertised typed family.
- Guard failure or unsupported lowering leaves the workspace unchanged before
  VM fallback.
- Native JIT remains optional; no-JIT builds retain portable typed execution.
- The native cache remains bounded and process-local for v1.0.

Objects, Cells, Struct values, dynamic operations, arbitrary calls,
unsupported mutation, and unrecognized control flow commonly remain in the
VM. Their legality is determined by the compatibility matrix, not by JIT
coverage.

## v1.x Reactivation Rule

Broader specialization may resume in v1.x only when a representative workload
and profiler or allocation evidence identify a material bottleneck. Each
addition must be additive, preserve guarded fallback, and provide:

1. bytecode, portable, and native result and diagnostic equivalence;
2. guard-failure and transactional rollback tests;
3. cold compilation, warm cache, and invalidation evidence;
4. native/no-JIT regression plus applicable x64 and ARM64 validation;
5. a runnable sample and an updated performance report.

Likely v1.x candidates remain straight-line numeric regions, common
matrix/array kernels, high-value pure builtin lowering, guarded function-call
specialization, and measured `RuntimeValue` or temporary-allocation reduction.
LLVM, OSR, broad speculative object optimization, and persistent native-code
disk caches retain their separate later-work boundaries.

## Executable Gate

`release_candidate_readiness_smoke` includes
`tests/validate_v1_jit_scope.cmake`. It checks the exact deferred matrix state,
document decision, report identity and correctness, zero-fallback execution,
native cold/warm cache behavior, no-JIT unavailability behavior, and the
fixed reports' conservative worst-sample speedup evidence. The negative guard
also rejects an unreviewed v1.0 reactivation or representation-changing JIT
item.

The representative scripts remain directly runnable:

```text
mparser --run --jit=native samples/performance_scalar_loop.m
mparser --run --jit=portable samples/performance_array_workload.m
```
