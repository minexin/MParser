# v1.0 Performance And Resource Baseline

This document defines the repeatable performance and resource evidence used by
the MParser v1.0 release gate. It is characterization, not a promise that one
timing number applies to every host. A report is meaningful only together with
its hardware, operating system, compiler, build type, workload, backend,
iteration settings, and exact measurement boundary.

The collector is the source-tree engineering executable
`mparser_performance_baseline`. It links directly to `mparser_core` so it can
measure parse, compile, execution, allocation, and native-cache boundaries
without changing the frozen public CLI or embedding APIs. It is deliberately
not installed in the user SDK. The report schema, this guide, and the
representative MATLAB-like workloads are installed.

## Protocol

Reports use `mparser.performance-baseline` protocol `1.0` and validate against
[performance-baseline-v1.schema.json](performance-baseline-v1.schema.json).
Major version 1 consumers accept additive fields. Removing a field, changing
its meaning, unit, or type, or weakening a correctness invariant requires a
new protocol major.

`performance_baseline_smoke` generates a real report, validates it with a
Draft-7 implementation, independently recomputes source and binary SHA-256
identities, recomputes timing/allocation statistics from every raw sample,
checks cross-field invariants, and runs negative cases. It never enforces a
machine-specific speed threshold.

## Measured Boundaries

| Phase | Included | Excluded |
| --- | --- | --- |
| `parse` | Lexer construction through `Parser::parse` return using in-memory source | Syntax-tree destruction and source file I/O |
| `compile` | Collector wrapper entry through immutable module return, including the source ownership copy into `CompiledModule::compile` | Module destruction and source file I/O |
| `process_cold_start` | Fresh child launch through exit, including CLI startup, source I/O, compile, one `--run --jit=off` execution, and shutdown | Captured output and parent-process work |
| `bytecode` | One `CompiledModule::execute(Bytecode)` call through result return | Compilation, result validation by the collector, and result destruction |
| `portable` | One forced portable typed execution through result return | Module compilation, collector validation, and result destruction |
| `native_cold` | First forced native execution after explicit native-cache clear/reset | Module compilation and collector validation |
| `native_warm` | Forced native execution after cache population | Module compilation and collector validation |

`process_cold_start` is process-cold and engine-cold, not a claim that the
operating-system filesystem cache is cold. Host wall time comes from
`steady_clock`. Runtime phases also report the engine's own elapsed counter so
the caller boundary and engine boundary remain distinguishable.

Every runtime phase must produce the same finite scalar named by
`--result-variable`. Bytecode is the reference result. Portable and native
results are compared exactly; legal unoptimized code may still execute through
guarded fallback. When native JIT is disabled or unavailable, both native
measurements have status `unavailable` rather than fabricated zero timings.

## Resource Definitions

`allocation_activity` retains per-iteration counts and requested-byte samples
for successful global `operator new` and `operator new[]` requests only while
the measured in-process call is active. Its aggregate fields are checked sums
of those samples. It does not count deallocation, live heap, allocator
metadata, C `malloc` calls made outside C++ allocation, or child-process
allocations. It is an allocation-activity signal, not a leak detector.

`peak_resident_bytes` is the process peak observed up to resource capture. It
is process-wide and is not attributed to one phase. LeakSanitizer and lifecycle
tests remain the ownership authorities.

Each binary artifact records path, size, and SHA-256 for the exact collector,
CLI, and C API shared-library files used by the report. The workload records
its own SHA-256 as well as path, size, and line count. Native cache statistics
are captured after reset, after the cold phase, and after the warm phase. The
eligible quick contract workload must demonstrate a cold
compilation/insertion and a later cache hit.

## Build And Run

Build the Release collector and runtime:

```powershell
cmake -S . -B build/windows-msvc-release `
  -G Ninja -DCMAKE_BUILD_TYPE=Release `
  -DBUILD_TESTING=ON `
  -DMPARSER_ENABLE_NATIVE_JIT=ON
cmake --build build/windows-msvc-release --parallel
```

Generate the scalar-loop report:

```powershell
build\windows-msvc-release\mparser_performance_baseline.exe `
  --cli=build/windows-msvc-release/mparser.exe `
  --library=build/windows-msvc-release/mparser_c.dll `
  --source=samples/performance_scalar_loop.m `
  --output=build/windows-msvc-release/performance-scalar.json `
  --workload-id=scalar-loop-v1 `
  --revision=<git-commit>
```

Replace the source and workload id with
`samples/performance_array_workload.m` and `linear-array-v1` for the
representative dense-array path. The same options work on Linux and macOS with
their executable and shared-library names. `--quick` reduces all iteration
counts for contract testing, not for publication evidence.

Run the automated contract:

```powershell
ctest --test-dir build/windows-msvc-release `
  -R "^performance_baseline_smoke$" --output-on-failure
```

Generate both release-evidence workloads through the portable CMake target:

```powershell
cmake -S . -B build/windows-msvc-release `
  -DMPARSER_PERFORMANCE_EVIDENCE_REVISION=<git-commit>
cmake --build build/windows-msvc-release --config Release `
  --target mparser_performance_evidence
```

The target is present only in native, non-cross-compiled builds with SLJIT
enabled. It writes `native-scalar-loop-v1.json` and
`native-linear-array-v1.json` below
`MPARSER_PERFORMANCE_EVIDENCE_OUTPUT_DIR` (by default
`<build>/performance-evidence`). Before accepting either report it runs the
schema/semantic validator and independently verifies revision, workload, OS,
architecture, a non-unknown CPU identity, `emulated=false`, native-JIT
availability, source hash, and all three binary hashes. On Linux ARM hosts
without a board or model-name field, the collector records the first CPU's raw
implementer/architecture/variant/part/revision identity from `/proc/cpuinfo`
instead of guessing a marketing name. `performance_evidence_contract_smoke`
exercises this two-report orchestration with bounded quick inputs, while
`performance_environment_smoke` freezes x86, ARM board-name, and ARM MIDR
parsing behavior.

Iteration options are bounded at 100,000. Use repeated
`--child-prefix=<argument>` options when a child must run through an emulator.
CTest forwards `CMAKE_CROSSCOMPILING_EMULATOR` both to the collector and to its
fresh CLI child. Such a report sets `environment.emulated=true`.

## Comparison Rules

Before comparing two reports:

1. Require matching workload and binary hashes, result variable, iteration
   settings, architecture, native/emulated state, build type, compiler family
   and major version, JIT configuration, and timing boundary.
2. Record CPU model, logical CPU count, physical memory, OS version, revision,
   and power/thermal policy. Prefer an otherwise idle host.
3. Compare distributions and raw samples, not only one minimum. Median and p95
   are descriptive; neither is a universal release threshold.
4. Separate native cold compilation cost from native warm cache-hit cost.
5. Treat QEMU or other emulation as functional contract evidence only. Native
   hardware is required for performance claims.
6. Re-run suspicious changes several times. A regression decision must exceed
   normal host variance and should be supported by a profiler or allocation
   evidence before changing the optimizer.

No current v1.0 result justifies broad Parser, IR, bytecode, `RuntimeValue`, or
embedding redesign. The completed
[v1.0 JIT scope decision](v1.0-jit-scope-decision.md) therefore retains
`G-JIT-001` as a Should-have but defers broader specialization to v1.x. A
future specialization requires a representative bottleneck plus guarded
bytecode/portable/native equivalence; optimization breadth does not block
correct VM execution or v1.0 publication.

## Evidence Status

The source-tree contract covers the quick eligible scalar path plus the
runnable scalar-loop and dense-array workloads. The first evidence set under
`docs/baselines/v1.0` binds three Windows x86-64 Release reports to
implementation commit `da4b010`: native scalar, native array, and no-JIT array.
The same candidate passed 201/201 native tests, 195/195 no-JIT tests, an SDK
build with testing disabled, and unpacked release-package validation.

Functional release-matrix validation subsequently passed at revision
`f34d8d9` in Actions run `30684969401`. The release workflow then collected
two full reports on each native Windows x64, Linux x64, macOS x64, and macOS
ARM64 job at revision `85685b8`. All six jobs in Actions run
[`30691616946`](https://github.com/minexin/MParser/actions/runs/30691616946)
succeeded, and the eight downloaded reports are indexed with their SHA-256
manifest under `docs/baselines/v1.0/actions-30691616946`.

The accepted set records exact OS, architecture, CPU label, logical CPU count,
memory, compiler, build type, binaries, workloads, timing boundaries,
allocation activity, peak RSS, and native-cache transitions. All reports have
`emulated=false`, matching results, and zero runtime or typed-region fallback.
The macOS ARM64 environment reports `Apple M1 (Virtual)`: it is a
native-architecture Apple Silicon hosted runner and is deliberately not
described as bare metal. Linux AArch64/QEMU remains functional evidence only
and does not produce a performance report.

`cross_platform_performance_evidence_smoke` validates the exact eight-report
set and manifest with the protocol-1.0 schema/semantic validator, then
independently enforces revision, workload hashes, platform/compiler identity,
non-emulation, measured phase boundaries, correctness, zero fallback, and the
cold-to-warm native-cache transition. No timing threshold is used. This closes
`G-PERFORMANCE-001`; future reports characterize regressions or new release
hosts rather than reopening the v1.0 runtime architecture.

`release_candidate_readiness_smoke` additionally checks that all three fixed
reports still share one implementation revision, match their current source
hashes and reference results, execute optimized regions without fallback, and
preserve native cold/warm and no-JIT cache behavior. Its speedup checks apply
only to these immutable reports and are not cross-machine release thresholds.
