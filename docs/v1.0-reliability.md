# v1.0 Reliability Gate

This document records the reliability evidence collected after the v1 public
contract candidate. It is a release gate, not a claim that MParser accepts
arbitrary MATLAB programs or arbitrary serialized bytecode.

Status: **closed for the v1.0 candidate**. The deterministic frontend fuzz,
malformed-bytecode, soak/lifecycle/resource suite, and MSVC AddressSanitizer
no-JIT configuration pass locally on Windows x64. Revision `f34d8d9` also
passes every release lane in Actions run `30684969401`, including Linux Clang
ASan/UBSan/LeakSanitizer, both macOS architectures, and native/portable
AArch64 QEMU evidence.

## Deterministic Frontend Fuzz

`parser_semantic_fuzz` is a bounded regression fuzz harness:

- fixed seed `0x4D505253`;
- 12 curated sources plus 128 generated or mutated cases;
- at most 768 source bytes and six mutations per generated case;
- Lexer token, Parser tree/diagnostic, and Semantic HIR/scope/symbol/diagnostic
  fingerprints compared across two complete executions;
- Semantic runs only for syntax accepted without Parser diagnostics, matching
  the production pipeline;
- failures print the seed, case index, reason, and complete source.

The harness includes functions, control flow, arrays, text, handles,
workspace declarations, and `classdef`. It is deterministic regression
coverage, not a substitute for a continuously evolving coverage-guided fuzz
campaign. Reproduce it with:

```powershell
ctest --test-dir build/windows-msvc-release -R parser_semantic_fuzz -V
```

## Bytecode Verification Boundary

`BytecodeProgram` remains an internal compiler/runtime format and is not a
public file format or ABI. Every untrusted direct VM, region-analysis, or
typed-executor entry validates it before metadata collection, optimization,
or execution. Validation is deterministic and covers:

1. opcode, binding, source-span, arity, result, capture, and subscript
   metadata;
2. module, class, function, initializer, argument-default, and unsupported
   control boundaries, including nested anonymous-body ownership;
3. jump bounds and confinement to the current executable owner;
4. matching `for`, `switch`, and `try` structures plus exact structured
   context state at every reachable branch merge or control-flow cycle;
5. index-context and transactional lvalue-path creation, consumption, and
   merge state;
6. reachable stack underflow, exact stack depth at merges and cycles, and the
   required exit or `Return` depth for every executable range;
7. exact binding of installed typed-region contracts to contracts re-derived
   from the validated bytecode.

Rejected programs report `MParser:Bytecode:InvalidProgram`, emit at most 64
validation diagnostics, execute zero instructions, and do not commit
workspace state. `CompiledModule`, adaptive sessions, and benchmark runners
validate once before using explicitly named trusted internal paths, so
invoke-many and typed-loop hot paths do not rescan the whole program. Adaptive
sessions own immutable bytecode and semantic snapshots rather than trusting
borrowed caller state. Legal outward transfers such as `break` and `continue`
also unwind exited `switch` and `try` contexts before execution resumes.

`bytecode_verifier_smoke` checks valid lowering, deterministic diagnostics,
the diagnostic bound, malformed opcode/count/binding/span/control/index/
lvalue/stack cases, cross-boundary structure/context rejection, stack-changing
cycles and merges, executable-range exit leaks, jumps into anonymous bodies,
structured-context bypasses, legal nested transfers, a systematic mutation
corpus, VM side-effect exclusion, adaptive snapshot immutability and
non-promotion, forged typed contracts, and typed/region `InvalidContract`
fallback.

## Existing Reliability Evidence

The new gates complement, rather than replace, existing tests:

| Boundary | Evidence |
| --- | --- |
| compile once / invoke many | `compiled_module_smoke`, `runtime_contract_smoke` |
| module and session state | `module_execution_smoke`, `runtime_session_smoke` |
| cancellation and resource limits | `module_resource_control_smoke` |
| handle and listener lifetime | `handle_lifecycle_smoke`, `property_listener_smoke`, `event_listener_smoke` |
| allocation and internal failure | `c_api_allocation_failure`, `c_api_named_fault_smoke` |
| C API retain/release pressure | `c_api_lifecycle_stress` |
| shared-library load/unload | `embedding_unload_stress` |
| C++ concurrent calls and sessions | `cpp_api_concurrency_stress` |
| native cache bounds and churn | `native_scalar_jit_cache_smoke`, `native_cache_lifecycle_cli_smoke` |
| machine protocol malformed input | `machine_protocol_schema_smoke`, `machine_protocol_contract_smoke` |

`runtime_soak_smoke` adds one named, quantified long-running regression:

- 5,000 invocations of one immutable `CompiledModule`;
- 2,500 invocations through one `RuntimeSession`, with exact persistent and
  global state checked after every call;
- 512 invocations through one adaptive session, with one promotion, 510 typed
  executions, and no fallback or invalidation.

That is 8,012 checked invocations in one process. None of these tests uses
elapsed-time pass/fail thresholds.

## Windows MSVC AddressSanitizer

The optional `windows-msvc-asan-nojit` preset provides a reproducible local
Windows x64 AddressSanitizer configuration. It uses MSVC 19.44,
`RelWithDebInfo`, `/fsanitize=address`, debug information,
`/INCREMENTAL:NO`, and `MPARSER_ENABLE_NATIVE_JIT=OFF`. The normal `/EHsc`
exception model remains intact.

`MPARSER_ENABLE_MSVC_ASAN` is deliberately narrow:

- it rejects non-MSVC, native-JIT, and release-packaging configurations;
- it locates exactly one architecture-matched
  `clang_rt.asan_dynamic-*.dll` beside the selected compiler;
- it stages that runtime beside local test executables and into temporary
  relocated-SDK consumer test directories;
- `msvc_asan_runtime_smoke` verifies the staged runtime hash and starts the
  instrumented CLI;
- the runtime DLL is never installed, packaged, vendored, or represented as
  an MParser redistributable.

Explicit staging is required for deterministic CTest behavior. Depending only
on the developer-prompt `PATH` allowed the first ASan child process to start
but later children could exit with Windows status `0xc0000135`. Placing the
runtime beside each executable removes that loader ambiguity. Microsoft also
documents that current MSVC `/MD` and `/MT` AddressSanitizer configurations
use the dynamic runtime, so switching CRT linkage would not remove this
dependency. See Microsoft's
[AddressSanitizer runtime reference](https://learn.microsoft.com/en-us/cpp/sanitizers/asan-runtime?view=msvc-170)
and
[build reference](https://learn.microsoft.com/en-us/cpp/sanitizers/asan-building?view=msvc-170).

The clean preset build passed **199/199** tests with no AddressSanitizer
report. That includes the five-test `reliability` label, the 8,012-invocation
soak, lifecycle/allocation/load-unload/concurrency stress, and both relocated
installed-consumer tests. This is local Windows no-JIT evidence, not native
SLJIT sanitizer coverage and not a claim that the configuration is already a
recurring CI lane.

## Runnable Sample

The valid side of the boundary is exercised by
`samples/reliability_boundary_demo.m`, which combines arrays, indexed
mutation, branches, loops, `switch`, `try/catch`, nested lvalues, and an
anonymous closure:

```powershell
build\windows-msvc-release\mparser.exe --run --jit=off `
  samples\reliability_boundary_demo.m
```

The stable result is `summary = 26`.

## Windows Candidate Evidence

The candidate is based on public-contract commit `cfd59b7` and was built with
MSVC 19.44 in Release mode:

- native-JIT build: **200/200** CTest tests passed;
- no-JIT build: **194/194** CTest tests passed;
- `reliability_boundary_demo.m`: `summary = 26` in both applicable full
  suites;
- archive:
  `build/windows-msvc-release-package-v1-contract-clean/packages/mparser-0.90.0-windows-x86_64.zip`;
- authoritative SHA-256 sidecar:
  `mparser-0.90.0-windows-x86_64.zip.sha256` beside the archive (the digest is
  deliberately not embedded in this installed document because doing so
  would make the archive hash self-referential);
- `release_archive_smoke` passed reproducible fixed-payload packaging,
  archive-path validation, relocation, independent C11/C++20 consumers, and
  the unpacked `json-v1` CLI protocol.

These counts include the frontend fuzz, bytecode verifier, 8,012-invocation
soak, and runnable reliability sample introduced by this gate.

## Remaining Specialized Evaluation

This document does not claim Linux TSan, macOS sanitizer feasibility,
recurring Windows MSVC ASan suitability, coverage-guided fuzz saturation, or
security certification. The first three remain bounded Should-have work under
`G-SANITIZER-001`; the latter two are outside the v1.0 reliability claim.
