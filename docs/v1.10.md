# MParser v1.10 Shared Runtime Milestone

v1.10 is the shared-runtime and cross-module execution-graph batch. It makes
the compile-once/invoke-many embedding model useful for applications that
load more than one MATLAB-like source module while keeping ownership and
failure behavior explicit. The product and source-tree version remains the
current 1.3.0 development identity until the next complete release candidate;
this document records the v1.10 functional batch, not a separate published
package.

## Shared Runtime

The C API adds an opaque `mparser_runtime` and the C++ facade adds
`mparser::sdk::Runtime`. A Runtime owns one shared `RuntimeSessionState` and a
registry of compiled module callable contexts. Execute a module through the
Runtime to opt into this graph:

```cpp
auto producer = mparser::sdk::Module::compile(producerSources);
auto consumer = mparser::sdk::Module::compile(consumerSource,
                                               "consumer.m");
auto runtime = mparser::sdk::Runtime::create();

auto produced = runtime.execute(producer, makeRequest("makeValue"));
auto value = produced.output(0);
producer = {};

auto result = runtime.execute(consumer, makeRequest("useValue", {value}));
```

The complete sample is `samples/cpp_shared_runtime_demo.cpp`. The equivalent
C entry points are `mparser_runtime_create`, `mparser_runtime_execute`,
`mparser_runtime_clear_global`, `mparser_runtime_clear_globals`, and
`mparser_runtime_reset`.

Runtime registration is lazy and keyed by the module's callable-context
identity. Registering a module retains its compiled state until the Runtime
is released or reset; `reset` clears shared language state but deliberately
keeps registered modules available for later calls. Releasing the caller's
Module wrapper therefore does not invalidate a closure, object, or diagnostic
that is still owned by a Runtime result/value.

## Ownership And Language Semantics

The following rules are intentional:

- A module-bound value produced through a Runtime carries the Runtime lifetime
  anchor. Cell and Struct composition preserves one compatible Runtime owner;
  mixing values from different Runtime instances is rejected.
- A module-bound value passed to an ordinary stateless Module call, Session,
  or a different Runtime still returns `OWNER_MISMATCH`. No implicit process
  global registry is used.
- Function handles from another registered module are synchronously dispatched
  through the owning module's bytecode/typed policy. The active invocation's
  cancellation, resource limits, session state, and backend selection are
  inherited.
- User-defined objects retain the callable context that defines their class.
  Public methods and properties can be read or written from another module;
  the owner module performs the original access checks, validators, setters,
  and event behavior. Private members remain private.
- Handle-class mutation is visible through aliases. Value-class property
  assignment returns the updated value object to the current call and does
  not mutate the original value object held by the caller.
- Globals, persistent variables, random state, paths, files, and other
  session-owned state are shared by Runtime calls. `clearGlobal` and `reset`
  act on that shared state.

Cross-module object arrays and dynamic object registries remain deliberately
guarded until their indexing and lifecycle contracts receive the same full
owner-side treatment. A scalar object passed through the current boundary is
never silently flattened or converted to bypass that restriction.

## Diagnostics And Output

Owner execution annotates returned diagnostics and output events with the
source name of the module that actually produced them. A consumer-side
failure therefore retains the producer source in its public diagnostic and
output-event provenance. Runtime results retain the Runtime owner when
projecting output values, top-level expressions, workspace variables, Cell
elements, and Struct fields.

The C boundary continues to translate `std::bad_alloc` to
`MPARSER_API_STATUS_ALLOCATION_FAILED`, leaves output handles null on failure,
and never lets a C++ exception cross the shared library. A Runtime remains
usable after an injected pre-publication allocation failure. Language side
effects that completed before a later publication failure retain the existing
non-transactional embedding contract.

## Concurrency

A Runtime serializes attached module executions with one recursive mutex.
This conservative first contract prevents races among shared globals,
persistent values, escaped closures, handle objects, listener state, and
module registration. Retain/copy the Runtime handle independently for each
thread; do not concurrently overwrite or release one host handle variable.
The concurrency regression runs eight workers through a cross-module
persistent callback and checks the exact serialized sequence.

This is a correctness boundary, not a claim of parallel execution. Finer
grained scheduling or parallel array kernels belongs to a later performance
milestone after profiler evidence and an explicit state model.

## Public Contract

The additive Runtime exports advance C ABI generation 2 from revision 1 to
revision 2. The active exact export manifest contains 124 symbols in
`tests/c_api_generation2_revision2_symbols.txt`; the revision-1 117-symbol
manifest and v1.3 header snapshot remain immutable archive evidence. SONAME
and install-name generation remains 2. The header-only C++ facade remains a
source API with no C++ binary ABI promise.

The current product/API numbers remain the development line documented by
`docs/versioning-and-deprecation.md`. A later release candidate must freeze a
new public-contract snapshot containing the Runtime declarations, installed
consumer evidence, and the matching symbol manifest together.

## Evidence

The batch includes these focused checks:

- `shared_runtime_smoke`: closures, ownership rejection, Cell/Struct
  composition, globals/persistent reset, public/private object members,
  handle/value assignment, reentrant callbacks, diagnostic/output provenance,
  and resource limits;
- `shared_runtime_c_api_smoke`: raw C creation, retained values after module
  release, composition, state, and owner rejection;
- `shared_runtime_concurrency_stress`: serialized cross-module persistent
  callback behavior;
- `c_api_allocation_failure`: Runtime construction and execution translation
  plus post-failure reuse;
- `c_api_lifecycle_stress`: concurrent retain/release including Runtime;
- `cpp_shared_runtime_demo_smoke`: the runnable C++ embedding sample;
- `c_api_shared_library_abi`, `embedding_unload_stress`, and installed C11/
  C++20 consumers: export, unload, package, and relocation boundaries.

The Windows MSVC focused set passes locally. Linux GCC strict-warning,
no-JIT, sanitizer, release-package, and applicable native x64/ARM64 CI runs
remain milestone evidence to collect before this batch is treated as a
cross-platform release candidate.

## Next Work

The next substantial v1.x batch can build on this boundary to close debugger
frame/locals inspection and broader function-library families without adding
module-specific ownership shims. Cross-module dynamic object arrays,
parallel Runtime scheduling, and external native builtin adapters remain
separately gated work.
