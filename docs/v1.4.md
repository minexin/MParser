# MParser v1.4 Development Milestone

v1.4 is the active advanced-mathematics and Typed/JIT performance train. It
is intentionally broader than one optimization: the milestone remains open
until the planned numerical, benchmark, optimization, documentation, and
cross-platform slices form a coherent release candidate. The source and SDK
therefore remain versioned as 1.3.0 during these internal batches.

## Batch 1: Versioned Workloads And Local Function Specialization

The first batch establishes `benchmarks/v1.4/manifest.json` as a versioned
seven-workload authority. It covers nested scalar loops, dense linear-array
loops, straight-line scalar code, dense element-wise expressions, reductions,
user-function calls, and dense linear algebra. Every workload produces one
finite checksum that must agree across bytecode, portable Typed, and native
Typed execution.

`mparser.performance-suite` protocol 1.0 binds the manifest, every source,
every underlying baseline report, the build/environment identity, timing
medians, allocation activity, Typed coverage, and native availability by
SHA-256. Its final integrity pass reopens the emitted index, resolves only
root-relative paths, and recomputes every manifest/source/report digest.
`performance_suite_contract_smoke` validates a quick real suite plus four
structural negative cases. It does not impose host-specific timing thresholds
and is omitted from emulator-based cross-compile CTest runs.

The first evidence-selected optimization specializes a deliberately narrow
but useful local-function contract inside an eligible scalar loop. A call is
accepted only when all of the following are proven from validated bytecode:

- direct `Function` binding with exactly one input and one output;
- an exact semantic symbol-id match to one top-level local function, with no
  class or lexical parent;
- no `varargin`, `varargout`, `arguments` block, defaults, or validation;
- straight-line numeric body using initialized parameters/locals/output only;
- numeric literals, supported scalar operators, and registry-declared pure
  one-input Typed builtins only;
- no free workspace reads, indexing, dynamic calls, control transfer,
  global/persistent state, object access, or other side effects.

The body is inlined into the existing `ScalarKernel`. Function parameters,
locals, and outputs become private SSA operands, so they cannot leak into or
overwrite the caller workspace. Portable C++ and SLJIT native execution lower
the same kernel. Runtime type/domain failure discards all staged writes and
restarts the original loop in the bytecode VM.

Nested-function shadowing is rejected by exact declaration/call identity, and
an active call-depth limit suppresses this specialization so logical calls are
still counted by the VM resource guard. Argument-default validation also keeps
its historical isolated workspace: validation-only bindings are removed from
the reused call frame before validated values and lexical captures are rebound.

`samples/scalar_function_jit_demo.m` is runnable with `--jit=off`, portable,
and native modes. Region, Typed IR, executor, malformed-bytecode, CLI, complex
domain failure, unsupported signature/body, and non-double input tests cover
acceptance, rejection, result parity, local ownership, and transactional
fallback.

## Batch 2: N-Dimensional Dense Fusion And Sum Lowering

The second evidence-selected batch adds a guarded Dense Typed executor for a
closed assignment right-hand side. It accepts floating `double`/`single`
scalars and dense arrays, real or complex numeric literals and builtin
constants, unary signs, supported element-wise arithmetic, scalar scaling,
and registry-declared pure unary mathematical functions. The portable kernel
evaluates the complete expression in one N-dimensional pass, uses MATLAB
column-major logical coordinates, supports implicit expansion, preserves the
numeric class and imaginary channel, and materializes only the final result.
Profile-derived candidates retain exact type/complexity/shape guards;
statically discovered production candidates use floating-type and dynamic
shape guards.

Exact-shape real-double expressions can lower through the existing SLJIT
scalar kernel. `auto` may try native and then continue with portable
execution when broadcast, `single`, complex values, a domain transition, or
another native-only boundary is unsupported. Explicit native execution
returns transactionally to the VM when no native lowering exists. Matrix
operations without a scalar operand, shadowed builtins, unsupported domains,
shape changes, active checkpoints, and malformed contracts never expose a
partial output.

Source contract 1.12 declares `BuiltinTypedLowering::Sum`, `Product`, and
`Mean` reduction identities. Eligible terminal `sum(A)`, `prod(A)`, and
`mean(A)` calls, including dimension and `"all"` forms, share the runtime
reduction-shape authority and empty-array behavior. Portable execution supports
array-valued reductions; native lowering is deliberately limited to real-double
scalar results. Nested reduction expressions and reductions without registry
metadata remain in the VM until they receive the same parity coverage.

`samples/dense_array_jit_demo.m` exercises fusion, unary builtins, scalar
scaling, implicit expansion, and all-element/dimensional `sum`, `prod`, and
`mean` reductions with a deterministic checksum.
`samples/dense_numeric_types_jit_demo.m` adds a single-precision path, complex
input/output, `i`/`j` constants, and real to complex domain crossing. Focused
tests cover 2-D and 3-D broadcasting,
dimensions 1/2/3/all, empty arrays, input/output aliasing, changed profile
shapes, profiled/static type and complexity guards, single/complex portable
execution, native-to-portable selection, shadowing, malformed regions/guards,
diagnostic parity, resource checkpoints, and native/no-JIT result equivalence.

## Batch 3: Source Ownership Layout

The implementation tree now gives the bytecode VM and CLI explicit ownership
boundaries. VM dispatch and adaptive-session sources live under
`src/mparser/execution/bytecode/vm`, while the executable entry point lives
under `src/mparser/cli`. The parent VM headers remain forwarding headers so
internal consumers do not need a coordinated include-path rewrite; new code
should include the headers from the owning VM directory directly.

This batch is behavior-neutral: bytecode IR, RuntimeValue, embedding APIs, and
the execution contracts are unchanged. `source_layout_smoke` checks the new
directories, required source pairs, retired implementation paths, and
forwarding headers. The remaining large implementation units are intentionally
split only in later focused batches, each with its own dependency and regression
boundary.

## Local Performance Characterization

The full suite was collected from the working tree on Windows 10.0.19045,
x86-64 Intel Family 6 Model 140, 8 logical CPUs and 16 GiB memory, using MSVC
19.44, a Release build, native SLJIT enabled, 3 runtime warmups and 20 measured
runtime calls. These numbers characterize this host only.

| Workload | Bytecode ms | Portable ms | Native warm ms | Portable / native coverage |
| --- | ---: | ---: | ---: | --- |
| Nested scalar loop | 4944.023 | 18.474 | 7.955 | executed / executed |
| Linear-array loop | 80.694 | 3.138 | 3.003 | executed / executed |
| Straight-line scalar | 0.429 | 0.598 | 0.627 | guarded fallback / guarded fallback |
| Dense element-wise | 79.711 | 4.055 | 7.370 | executed / executed |
| Reduction/statistics | 26.866 | 19.651 | 26.280 | executed / guarded fallback |
| User-function call | 184.930 | 6.011 | 5.823 | executed / executed |
| Dense linear algebra | 1.118 | 1.108 | 1.115 | uncovered / uncovered |

Dense element-wise fusion is about 19.7x faster through portable Typed
execution and 10.8x faster through the current warm native tier than bytecode
on this run. Aggregate requested C++ allocation activity across the 20 measured
calls falls from 825,826,140 bytes in bytecode to 41,112,920 bytes in portable
execution. Portable is currently the preferred implementation for this
memory-bound expression; native selection remains correct but is not presented
as inherently faster.

The reduction workload improves by about 1.37x through portable execution.
Only its terminal `sum(data .* data, 1)` region is lowered; the final expression
contains several nested reductions and therefore remains in the VM. Native
reports a guarded fallback because that reduction produces an array. The full
no-JIT suite independently reports matching checksums, portable Dense median
4.014 ms versus bytecode 81.100 ms, and native unavailable as required.

The report still prevents benchmark-driven scope inflation. Straight-line
scalar and dense-linear-algebra examples are too small on this host to justify
priority by wall time. Broader reductions, temporary ownership, and matrix
kernels remain evidence-backed candidates, but must continue through shared
shape/alias guards, BuiltinRegistry metadata, and transactional VM fallback.

## Commands

Run the sample:

```powershell
build\windows-msvc-release\mparser.exe --run --jit=off `
  samples\scalar_function_jit_demo.m
build\windows-msvc-release\mparser.exe --run-typed-bytecode `
  --typed-backend=portable samples\scalar_function_jit_demo.m
build\windows-msvc-release\mparser.exe --run-typed-bytecode `
  --typed-backend=native samples\scalar_function_jit_demo.m
build\windows-msvc-release\mparser.exe --run --jit=off `
  samples\dense_array_jit_demo.m
build\windows-msvc-release\mparser.exe --run --jit=portable `
  samples\dense_array_jit_demo.m
build\windows-msvc-release\mparser.exe --run --jit=native `
  samples\dense_array_jit_demo.m
build\windows-msvc-release\mparser.exe --run --jit=portable `
  samples\dense_numeric_types_jit_demo.m
build\windows-msvc-release\mparser.exe --run --jit=native `
  samples\dense_numeric_types_jit_demo.m
build\windows-msvc-release\mparser.exe --run --jit=off `
  samples\dense_reduction_jit_demo.m
build\windows-msvc-release\mparser.exe --run --jit=portable `
  samples\dense_reduction_jit_demo.m
build\windows-msvc-release\mparser.exe --run --jit=native `
  samples\dense_reduction_jit_demo.m
```

Validate the bounded suite contract or collect the full suite:

```powershell
ctest --test-dir build\windows-msvc-release `
  -R "^performance_suite_contract_smoke$" --output-on-failure
cmake --build build\windows-msvc-release --config Release `
  --target mparser_v1_4_performance_suite
```

The full output is written below
`<build>/performance-suite-v1.4`. Commit-bound or cross-platform numbers are
not claimed by this local working-tree report; applicable native/no-JIT and
x64/ARM64 CI evidence remains a later v1.4 candidate gate.

Installed SDKs retain the manifest's repository-relative layout below
`<prefix>/share/mparser/performance-suite`: use that directory as the suite
source root and `benchmarks/v1.4/manifest.json` as the manifest path.

## Remaining v1.4 Scope

- extend reduction metadata and fusion only for measured high-value families;
- evaluate straight-line regions only after the higher-cost array paths;
- add general matrix kernels and optional mature backends only with a complete
  portable C++20 authority and explicit licensing/threading contracts;
- extend Typed coverage to broader numeric classes and matrix families without
  weakening numeric-class guards or VM semantics;
- extend advanced numerical families without Eigen and retain the portable
  repository-owned C++20 authority;
- rerun native/no-JIT, sanitizer, x64/ARM64, packaging, and differential
  validation before changing the project version or freezing v1.4.
