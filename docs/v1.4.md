# MParser v1.4 Development Milestone

v1.4 is the active advanced-mathematics and Typed/JIT performance train. It
is intentionally broader than one optimization: the milestone remains open
until the planned numerical, benchmark, optimization, documentation, and
cross-platform slices form a coherent release candidate. The source and SDK
therefore remain versioned as 1.3.0 during these internal batches.

## Batch 1: Versioned Workloads And Local Function Specialization

The first batch establishes `benchmarks/v1.4/manifest.json` as a versioned
seven-workload authority. It covers nested scalar loops, dense linear-array
loops, straight-line scalar code, dense element-wise expressions, reductions,
user-function calls, and dense linear algebra. Every workload produces one
finite checksum that must agree across bytecode, portable Typed, and native
Typed execution.

`mparser.performance-suite` protocol 1.0 binds the manifest, every source,
every underlying baseline report, the build/environment identity, timing
medians, allocation activity, Typed coverage, and native availability by
SHA-256. Its final integrity pass reopens the emitted index, resolves only
root-relative paths, and recomputes every manifest/source/report digest.
`performance_suite_contract_smoke` validates a quick real suite plus four
structural negative cases. It does not impose host-specific timing thresholds
and is omitted from emulator-based cross-compile CTest runs.

The first evidence-selected optimization specializes a deliberately narrow
but useful local-function contract inside an eligible scalar loop. A call is
accepted only when all of the following are proven from validated bytecode:

- direct `Function` binding with exactly one input and one output;
- an exact semantic symbol-id match to one top-level local function, with no
  class or lexical parent;
- no `varargin`, `varargout`, `arguments` block, defaults, or validation;
- straight-line numeric body using initialized parameters/locals/output only;
- numeric literals, supported scalar operators, and registry-declared pure
  one-input Typed builtins only;
- no free workspace reads, indexing, dynamic calls, control transfer,
  global/persistent state, object access, or other side effects.

The body is inlined into the existing `ScalarKernel`. Function parameters,
locals, and outputs become private SSA operands, so they cannot leak into or
overwrite the caller workspace. Portable C++ and SLJIT native execution lower
the same kernel. Runtime type/domain failure discards all staged writes and
restarts the original loop in the bytecode VM.

Nested-function shadowing is rejected by exact declaration/call identity, and
an active call-depth limit suppresses this specialization so logical calls are
still counted by the VM resource guard. Argument-default validation also keeps
its historical isolated workspace: validation-only bindings are removed from
the reused call frame before validated values and lexical captures are rebound.

`samples/scalar_function_jit_demo.m` is runnable with `--jit=off`, portable,
and native modes. Region, Typed IR, executor, malformed-bytecode, CLI, complex
domain failure, unsupported signature/body, and non-double input tests cover
acceptance, rejection, result parity, local ownership, and transactional
fallback.

## Local Performance Characterization

The full suite was collected from the working tree on Windows 10.0.19045,
x86-64 Intel Family 6 Model 140, 8 logical CPUs and 16 GiB memory, using MSVC
19.44, a Release build, native SLJIT enabled, 3 runtime warmups and 20 measured
runtime calls. These numbers characterize this host only.

| Workload | Bytecode ms | Portable ms | Native warm ms | Typed coverage |
| --- | ---: | ---: | ---: | --- |
| Nested scalar loop | 3108.488 | 11.018 | 3.107 | executed |
| Linear-array loop | 92.123 | 3.520 | 3.432 | executed |
| Straight-line scalar | 0.563 | 0.549 | 0.554 | uncovered |
| Dense element-wise | 91.383 | 94.592 | 86.842 | uncovered |
| Reduction/statistics | 37.583 | 30.519 | 30.487 | uncovered |
| User-function call | 213.140 | 10.562 | 10.512 | executed |
| Dense linear algebra | 1.364 | 1.293 | 1.266 | uncovered |

The selected user-function workload is about 20.2x faster through portable
Typed execution and 20.3x faster through the warm native tier than bytecode on
this run. Aggregate requested C++ allocation activity across the 20 measured
calls falls from 12,021,623,580 bytes in bytecode to 231,583,360 bytes in the
native-warm phase. The native cache records one 389-byte compilation followed
by 23 hits, with matching results and zero Typed fallback.

The report also prevents benchmark-driven scope inflation. Straight-line
scalar and dense-linear-algebra examples are currently too small to justify
priority by wall time. Dense element-wise expressions and reductions remain
the next high-value uncovered candidates because they retain material runtime
and allocation cost. They must still enter through shared shape/alias guards,
BuiltinRegistry metadata, and transactional VM fallback rather than a
benchmark-specific path.

## Commands

Run the sample:

```powershell
build\windows-msvc-release\mparser.exe --run --jit=off `
  samples\scalar_function_jit_demo.m
build\windows-msvc-release\mparser.exe --run-typed-bytecode `
  --typed-backend=portable samples\scalar_function_jit_demo.m
build\windows-msvc-release\mparser.exe --run-typed-bytecode `
  --typed-backend=native samples\scalar_function_jit_demo.m
```

Validate the bounded suite contract or collect the full suite:

```powershell
ctest --test-dir build\windows-msvc-release `
  -R "^performance_suite_contract_smoke$" --output-on-failure
cmake --build build\windows-msvc-release --config Release `
  --target mparser_v1_4_performance_suite
```

The full output is written below
`<build>/performance-suite-v1.4`. Commit-bound or cross-platform numbers are
not claimed by this local working-tree report; applicable native/no-JIT and
x64/ARM64 CI evidence remains a later v1.4 candidate gate.

Installed SDKs retain the manifest's repository-relative layout below
`<prefix>/share/mparser/performance-suite`: use that directory as the suite
source root and `benchmarks/v1.4/manifest.json` as the manifest path.

## Remaining v1.4 Scope

- add general dense numeric shape/stride guards and element-wise fusion;
- lower representative pure reductions through `BuiltinRegistry` metadata;
- evaluate straight-line regions only after the higher-cost array paths;
- extend advanced numerical families without Eigen and retain the portable
  repository-owned C++20 authority;
- rerun native/no-JIT, sanitizer, x64/ARM64, packaging, and differential
  validation before changing the project version or freezing v1.4.
