# v1.5 Rich Data First Batch

This document records the first v1.5 development batch. It is an internal
milestone, not a published product or API freeze. The repository still reports
the current candidate product version and v1.3 public contract; the batch
advances the runtime and builtin source contract to 1.13 so the next release
train can evaluate the result as one coherent change.

## Delivered Slice

The batch adds an immutable, repository-owned C++ temporal value family:

- `datetime` stores a proleptic-Gregorian civil date and fractional day;
- `duration` stores seconds and supports H/M/S construction and unit scaling;
- `NaT` supports scalar and shaped missing datetime values;
- `year`, `month`, `day`, `hour`, `minute`, and `second` return shaped numeric
  components;
- `days`, `hours`, `minutes`, and `seconds` construct or inspect durations;
- `isdatetime`, `isduration`, and `isnat` preserve scalar or array shape;
- ISO-like character/string formatting, temporal member properties, arithmetic,
  comparisons, implicit scalar expansion, and interpreter/VM equality are
  shared through the same runtime helpers.

The implementation is independent of Eigen and platform calendar APIs. Its
initial civil-date range is years 1 through 9999, with NaT represented by a
well-defined missing payload. Time zones, calendar-month arithmetic, locale
format strings, and business-calendar behavior are deliberately outside this
slice.

## Engine And Embedding Boundary

The family is registered through `BuiltinRegistry` and uses the ordinary
`BuiltinCall`/`BuiltinResult` contract. It runs in the reference interpreter,
bytecode VM, production `--run`, and no-JIT fallback paths. It has no Typed/JIT
lowering yet; unsupported optimization coverage therefore remains a legal VM
fallback rather than a semantic error.

Temporal values are immutable value objects and do not retain a module graph.
The C API can transport them across compiled modules and inspect their class
and shape. The current C API has no temporal-payload accessor, and machine
protocol 1.1 continues to encode class objects as opaque objects. Hosts that
need portable text should request `char(value)` or `string(value)` until a
future value-ABI extension is designed and tested.

## Evidence

The focused evidence is:

- `datetime_duration_smoke`: constructor validation, leap dates, ISO parsing,
  shape contracts, arithmetic, missing values, and HIR/bytecode parity;
- `datetime_duration_interpreter_cli_smoke`,
  `datetime_duration_bytecode_cli_smoke`, and
  `datetime_duration_production_cli_smoke`: the runnable sample through all
  user-facing execution paths;
- `c_api_smoke`: ownerless temporal value transport and compile-once/
  invoke-again behavior;
- `machine_protocol_smoke`: explicit preservation of the object/opaque
  protocol boundary;
- `source_layout_smoke`: the new core value and builtin family remain in their
  owning directories and obey the `.cpp`/`.h` ownership rule;
- `v1_3_public_contract_smoke` and `builtin_catalog_snapshot_smoke`: source
  contract 1.13, 291 descriptors, and 293 registered names.

The sample is [datetime_duration_demo.m](../samples/datetime_duration_demo.m).
The next external MATLAB R2024b differential rerun must verify the imported
`datetime` capability independently; until then the measured remaining gap
list is not silently rewritten. `table`, `sparse`, and graphics remain later
families.

## Source Organization Decision

No blanket relocation of `src/mparser` is part of this batch. The existing
ownership graph already separates frontend, semantic, execution, runtime core,
builtin families, I/O, and embedding. New temporal code is placed in
`runtime/core/value` and `runtime/builtins/datetime`. A large file is split
only when a focused ownership boundary, independent test seam, or measurable
compile-time/maintenance benefit exists; file count alone is not a reason to
change include paths during the active iteration.

## Next Rich-Data Work

The next candidates are broader numeric-class parity and one additional rich
family chosen from the differential workload: sparse storage, categorical
values, or table/timetable. Each candidate must add a RuntimeValue/shape/index
contract first, then registry integration, dual-engine tests, a sample,
embedding/protocol limits, and applicable x64/ARM64 validation. Temporal JIT
lowering is deferred until a benchmark demonstrates material value and a
guarded fallback contract is available.
