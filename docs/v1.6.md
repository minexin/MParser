# v1.6 Sparse Numeric First Batch

This is an internal v1.x development batch. It keeps the product and C/C++
embedding API at the current candidate version while advancing the builtin
source contract to 1.14. The goal is a complete, testable sparse numeric
vertical slice, not a claim of general MATLAB compatibility.

## Delivered Slice

MParser now has repository-owned compressed-column sparse storage:

- `RuntimeSparseStorage` stores canonical two-dimensional CSC columns with
  sorted row indices, duplicate-free entries, optional imaginary values, and
  copy-on-write ownership;
- `sparse(A)` and triplet forms `sparse(i,j,v,m,n,nzmax)` construct sparse
  values, including duplicate triplet accumulation and real/complex inputs;
- `spalloc`, `speye`, `spones`, `full`, `nonzeros`, `nnz`, and `issparse` are
  registered through the ordinary `BuiltinRegistry` contract;
- numeric element access, sparse-preserving indexed reads, shape/type/workspace
  queries, equality, transpose, unary sign, dense math fallback, and in-bounds
  indexed assignment share the existing RuntimeValue/indexing machinery;
- `RuntimeValue` validation and recursive byte accounting include the CSC
  payload, and sparse copies detach before mutation.

The implementation is native C++20 and does not link, vendor, or copy Eigen.
It is deliberately two-dimensional and follows the MATLAB R2024b sparse class
boundary: construction accepts double, logical, and complex-double payloads;
single and integer construction fail instead of silently changing class.
Pattern-only `spones` accepts other numeric classes and returns double sparse.

## Engine And ABI Boundary

The reference interpreter, bytecode VM, portable execution, and production
`--run` path use the same runtime value and builtin handlers. Sparse values do
not enter Typed/JIT lowering yet; an optimized region must fall back to the
VM/portable semantic path. Dense fallback is intentional for general sparse
arithmetic and selected transforms, while common construction, inspection,
transpose, sign, and element access retain CSC storage.

The C API and machine result protocol expose sparse values as opaque object
values. No CSC pointer, borrowed view, allocator, or layout becomes an ABI.
`full` is the explicit conversion boundary for hosts that need a contiguous
numeric buffer. Sparse MAT-file persistence, table interoperation, graphics,
additional sparse formats, and sparse-aware BLAS kernels remain later work.

## Evidence

- `sparse_runtime_smoke` checks CSC invariants, duplicate triplets, complex
  round trips, transpose, copy-on-write assignment, sparse-preserving
  indexing, class rejection/pattern conversion, registry metadata, and
  RuntimeValue contract validation;
- `sparse_interpreter_cli_smoke`, `sparse_bytecode_cli_smoke`, and
  `sparse_production_cli_smoke` execute
  [sparse_demo.m](../samples/sparse_demo.m) through the three user-facing
  paths and produce the same summary;
- `source_layout_smoke` checks the new `runtime/core/value` and
  `runtime/builtins/sparse` ownership boundaries;
- the active builtin source contract 1.14 snapshot contains 299 descriptors
  and 301 registered names.

The imported MATLAB R2024b sparse case `cap_290_out_sparse` was rerun directly
with the native production CLI on 2026-08-24 and passed. The companion temporal
case `cap_029_types_datetime` also passed. The full 223-case differential
report has not been regenerated yet, so the compatibility matrix still keeps
the overall imported match count unchanged and records these as targeted
evidence rather than a new suite-wide match count.

## Follow-up Boundaries

The next high-value work remains data-type and mathematical coverage driven by
measured workloads: broader sparse indexing/reshape preservation, integer and
complex-class parity, reductions and array builtins over sparse values, and
optional dense-backend acceleration. None of those should weaken the guarded
fallback rule or require a second builtin dispatch mechanism.
