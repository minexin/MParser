# v1.7 Table Runtime First Batch

This is an internal v1.x development batch. It keeps the product and C/C++
embedding APIs at the current candidate version while advancing the builtin
source contract to 1.15. The goal is a coherent MATLAB-like table vertical
slice, not complete `matlab.tabular` or toolbox compatibility.

## Delivered Slice

MParser now has repository-owned table storage and shared runtime behavior:

- `RuntimeTableStorage` owns an ordered set of named variables, row count,
  optional row names, dimension names, description, and `UserData`, with
  copy-on-write mutation;
- `table` accepts equally tall variables and `VariableNames`, `RowNames`, and
  `DimensionNames` options; variables may themselves be multi-column values;
- member access reads and updates variables, and `Properties` exposes a
  structure snapshot that supports transactional nested copyback;
- two-subscript parenthesis indexing selects rows and variables by numeric,
  logical, colon, or name selectors, while brace indexing extracts variable
  contents through the same HIR and bytecode contracts; repeated read
  selections receive deterministic `_1`, `_2`, ... names as needed;
- nested variable assignment, one-variable brace assignment, table-to-table
  parenthesis assignment, variable addition, and full-variable deletion use
  the existing transactional lvalue machinery; indexed deletion requires a
  literal colon row selector, while `T.Name=[]` is distinguished from storing
  a valid zero-width `height(T)`-by-0 variable;
- `==` and `~=` compare matching numeric, text, temporal, or nested-table
  variables element by element and return a logical table with the same row
  and variable layout;
- `height`, `width`, `istable`, `array2table`, `table2array`, `struct2table`,
  and `table2struct` use the ordinary `BuiltinRegistry` call/result path.

Variable and dimension names are validated together: each set is unique,
the sets do not overlap, and `Properties` remains reserved. A scalar structure
whose fields contain equally tall arrays converts those arrays directly into
table variables; a nonscalar structure array continues to contribute one
table row per structure element, including wide row values without wrapping
them in Cell. Zero-variable array/structure conversions preserve height and
reject a mismatched nonempty `RowNames` list before returning a value.

Default variable names are deterministic `Var1`, `Var2`, and so on. Unlike
MATLAB, the runtime does not recover caller expression names because source
spelling is not part of the builtin call contract. Name lists must be unique,
nonempty text values with exactly the required cardinality.

## Engine And ABI Boundary

The reference interpreter, bytecode VM, portable fallback, and production
`--run` path share the same table storage, indexing, mutation, and builtin
helpers. Tables do not enter Typed/JIT lowering in this batch; optimized code
falls back before a table operation and preserves VM semantics.

The C API and machine result protocol expose table values as opaque object
values. A table whose recursively owned variables and `UserData` are
module-independent can be retained and passed to another compiled module; its
class and dimensions remain inspectable, but no table storage pointer,
variable view, allocator, or layout becomes an ABI. Hosts can use
language-level conversion functions when a homogeneous dense payload or
structure representation is sufficient.

## Deliberate Limits

This first slice does not provide timetable, categorical, joins, grouping,
sorting, row deletion, arbitrary multi-variable brace assignment, table MAT
persistence, display parity, `matlab.tabular.TableProperties` object identity,
the `struct2table(..., AsArray=...)` option, or Typed/JIT lowering.
`table2array` requires variables that can form one homogeneous array, and
table variables must provide stable first-dimension row indexing. Structure
conversions intentionally cover the common rectangular cases.
These limits remain explicit VM-correct fallback work, not reasons to
duplicate table dispatch in an execution engine.
