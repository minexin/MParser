This document tracks the finite compatibility and embedding work imported from
two external consumers after the 1.0.0 release:

- `D:\project\MParserV1.0Test`, baseline `results/20260806-160702`;
- `D:\project\MExecServer\docs\mparser-kernel-iteration-notes.md`.

It supplements `roadmap-v1.x.md`. Historical contracts remain evidence for
their releases. During current development the implementation, compatibility
matrix, and milestone documentation define the forward contract; external

## Baseline

MATLAB R2024b accepted all 223 cataloged capability points. MParser 1.0.0
matched 134 and exposed 89 gaps:

| Classification | Count |
| --- | ---: |
| Missing builtin | 53 |
| Registered but unimplemented builtin | 7 |
| Parse or lowering gap | 9 |
| Runtime semantic mismatch | 15 |
| Explicit product-scope exclusion | 5 |

The five explicit exclusions remain visible evidence, but they do not become
V1.x release blockers unless the product scope is deliberately expanded.
Everything else stays open until a current differential run proves closure.

The V1.x product scope has now deliberately expanded for core numeric data:
`single`, the complete signed/unsigned integer family, and real/complex
`single`/`double` are early targets even where the original v1.0 catalog marked
them out of scope. Sparse, datetime, table, and other rich domain/container
types remain tracked later V1.x families rather than v1.2 blockers.

The v1.1.0 rerun on 2026-08-09 reused the unchanged MATLAB R2024b results
from baseline `20260806-160702` and executed all 223 cases with the v1.1 CLI.
It reports 140 matches and 83 gaps. Exactly the six v1.1 closure cases changed
from gap to match; no previous match regressed.

## V1.x Coverage Tracks

The inventory is delivered in four tracks so a missing function name does not
hide a prerequisite runtime problem:

| Track | Scope | Dependency rule |
| --- | --- | --- |
| Language and data semantics | Core numeric classes, complex values, promotion/conversion, array/operator/indexing behavior, source diagnostics | VM semantics are authoritative and must stabilize before a function or JIT path advertises the affected class |
| Mathematical/function coverage | Elementary math, predicates, ordering/set, statistics, number theory, linear algebra, FFT/convolution, and array helpers | Register through `BuiltinRegistry` or documented `.m` libraries; no interpreter/VM duplicate hardcoding |
| System/host coverage | Output, workspace, path/cwd, environment, filesystem, process, time, random state, introspection, and dynamic evaluation | Requires explicit session-scoped context and permissions; no unannounced process-global mutation |
| Typed/JIT coverage | Straight-line regions, dense arrays, fusion/reductions, backends, call specialization, memory and SIMD | Driven by versioned workload evidence and always guarded by transactional VM fallback |

Core type conformance includes `class`, `isa`, constructors/casts, type
predicates, exact scalar/array transport, complex real/imaginary behavior,
integer range behavior, concatenation, indexing, assignment, transpose,
arithmetic, comparison, and representative reductions. Passing only
`class(int8(5))` is not sufficient evidence for a numeric class.

## Milestone Sequence

Milestone contents are dependency-ordered candidates. They may be rebalanced
when implementation evidence exposes a shared prerequisite, but no imported
item may disappear from this inventory.

Each `0.1` milestone is intentionally broad. It may contain several internal
implementation batches and focused regressions, but version stamping, full
documentation refresh, the 223-point rerun, release packaging, and complete
cross-platform CI are concentrated at the milestone candidate instead of being
repeated for every small function group.

| Milestone | Required outcome |
| --- | --- |
| v1.1 | Complete: close silent or structural core mismatches for left-associated power, comma-separated one-line control forms, matrix-column `for`, and column-shaped `A(:)`. Interpreter, bytecode, production `--run`, typed fallback, six original cases, and the 223-point no-regression rerun agree. |
| v1.2 | Close one full core-runtime train: command-module source/metadata/output contracts; exact core numeric classes and complex dense values through RuntimeValue, bytecode, operators, embedding API and machine protocol; conversions/promotion; a coherent elementary math/predicate tranche; guarded typed/native fallback for new classes. |
| v1.3 | Close one broad host/system train: session capabilities plus workspace/path/cwd/output/environment/filesystem/process/time/random/dynamic-evaluation functions; formatted text, ordering/set, array helpers and number-theory families; Cell-case switch, nested lexical functions, Cell comma-list outputs, and implicit indexed Struct creation. Downstream service adoption follows independently. |
| v1.4 | Close one advanced numerical train: statistics, linear algebra, FFT/convolution and optional mature backends; establish the versioned benchmark and expand straight-line/dense-array/fusion/reduction/function-specialization JIT coverage where evidence justifies it. |
| v1.5 | Close remaining class semantic and cross-module ownership gaps, then add sparse, datetime/duration, categorical and table/timetable in coherent rich-data slices; separately gate debugger frame inspection. |
| v1.6+ | Complete remaining parser, escaping nested-closure lifetime, persistence, dynamic-source-graph, rich-type, function-library, memory/SIMD and advanced-tiering work in similarly substantial functional bundles. |

## Evidence Rules

An item closes only when all applicable evidence is present:

1. A focused repository regression names the imported capability ID.
2. Interpreter and bytecode results agree; typed/native execution either
   agrees or records a guarded fallback to the bytecode authority.
3. The original external `.m` case exits successfully under production
   `mparser --run`.
4. The full native and no-JIT suites pass for runtime or compiler changes.
5. A runnable sample and current user/architecture/milestone documentation
   describe any user-visible behavior.
6. Focused local regression is required at each internal batch. Complete
   platform CI is concentrated at the `0.1` milestone candidate, with an
   intermediate run only when a batch carries unusual cross-platform risk.
   Pure prose or archive-only edits use focused documentation validation.
7. A new numeric class proves scalar and multidimensional values, boundary
   conversion, mixed-class diagnostics, interpreter/VM agreement, C/C++ and
   machine-protocol round trips, and native guard fallback before it is marked
   supported.
8. A performance batch records hardware, OS, compiler, build type, backend and
   timing boundary, plus guard-failure and fallback counts; timing alone cannot
   close a compatibility item.

After every 0.1 milestone, rerun the 223-point catalog and record the new
match/gap counts. A narrow regression cannot by itself prove the broader
external inventory complete.
